# HealthyFac Architecture

This document records the service boundaries and the decisions that connect the services. Read `README.md` for the product domain.

## Services

| Service | Owns | Status |
| --- | --- | --- |
| **Gateway** (YARP) | The only public entry point. Routing, TLS, rate limiting, the edge JWT check, and the token revocation check. It also hosts the realtime hub (see **Realtime**). | Exists |
| **Auth** | A thin back channel to Keycloak: user provisioning, organization membership, and role assignment through the Keycloak Admin API. It also sets the language of the signed-in user (`PUT /api/auth/v1/me/locale`, the only public endpoint). It does not log users in or handle passwords. It may have its own tables when it needs them. | Exists |
| **SPA host** | A small .NET host that serves the built web app, the runtime `/config.json`, and the index file with a content security policy nonce. It has no database and no authentication. | Exists |
| **Core** | Business data: companies, employees, employee invites, roles, machines (with the gateway ID and the state history), the machine drafts, work orders (with their history), employee shifts, and campaigns. | Exists |
| **Telemetry** | The signal model of a machine and the intake of its messages: the unit catalog, metric definitions, status definitions, the metric and status drafts with their proposal entries, schema revisions, machine registrations, received messages, and readings. It consumes the machine messages from Mosquitto. | Exists |
| **Insights** | Ingest attempts, the ingested documents and their chunks (pgvector), the extraction worker (Docling and Gemini), and the draft proposals. The statistic rules that detect anomalies are planned. | Exists |
| **Document** | The file refs (company files, machine files, and embedded images), the machine registrations, and the file bytes in blob storage (Azurite in development). | Exists |

## Data Ownership

- One PostgreSQL server holds one database per service (e.g., `healthyfac_core`, `healthyfac_auth`, `keycloak`).
- A service writes only to its own database.
- **Exception:** Telemetry is the only writer of `healthyfac_telemetry`. Insights reads it for now, with no role defined yet. Revisit this when the warnings feature is designed.
- The company holds the IANA time zone (`Company.TimeZoneId`). Every planned local time of the company and every displayed time use it.
- Core and Telemetry migrations were squashed into one `Initial` each on 2026-11-08, so a database from before needs `docker compose down -v`.
- Core and Telemetry migrations were regenerated into one `Initial` each on 2026-11-17 (the metric and status drafts moved from Core to Telemetry), so a development database needs `docker compose down -v` again.
- **Exception:** the gateway composes draft and machine answers from Core and Telemetry (see **Gateway Composition**). It reads through the public endpoints and stores nothing.
- The PostgreSQL image moved from `postgres:18.6-alpine` to `pgvector/pgvector:0.8.6-pg18-trixie` on 2026-11-09 (the pgvector extension serves Insights). A development database needs one `docker compose down -v`.
- Core is the source of truth for companies, employees, and machines. Other services get the data they need from messages or from the token claims. Telemetry keeps its own copy of a machine (the machine registration: machine ID, gateway ID, company), so every scope check is local.

## Communication

- **Client to service:** the SPA calls the gateway. The gateway forwards to the service. Every service validates the JWT again.
- **Service to service, gRPC:** Insights calls Document (`DocumentClient`) and Telemetry (the `TelemetrySignals` service) with a service token and the actor headers. The client has a retry service config (`GrpcClientConfigurations`, Shared.Infrastructure).
- **Service to service, asynchronous:** RabbitMQ with Rebus. Every service uses the transactional outbox and inbox (`backend-infrastructure.md`, rule **Outbox and Inbox**). A message type name has the form `<service>.v<version>:<Name>` (e.g., `core.v1:EmployeeInvited`).
- **Equipment to Telemetry:** a gateway publishes to Eclipse Mosquitto (MQTT 5), which is separate from RabbitMQ, so a flooding sender cannot slow down the business messages and a device never gets internal broker credentials. The topic is `healthyfac/gateways/{gatewayId}/messages`, and it is the only source of the gateway ID. Two users exist, with a password file and an ACL file: `telemetry` reads the topic, `sender` writes it. Anonymous access is off. A later feature with a user per gateway binds the topic to the user (`pattern write healthyfac/gateways/%u/messages`).
- **Shared contracts:** the producing service owns each integration message in the project `HealthyFac.<Service>.Messaging` (for example `HealthyFac.Core.Messaging` with `core.v1:MachineCreated` and `core.v1:MachineDeleted`). The message file holds its validator and the project holds its error texts. The producer and each consumer reference the project, so no copy can drift. The project references only `Shared.Application`. The consumer keeps the handler and the pre-handler check. The `MessageType` name stays stable, because stored outbox and inbox rows use it. Architecture tests check the location, the copies, and the layer rule.
- **Service to service, synchronous:** OAuth 2.0 Token Exchange when the call acts for a user, or Client Credentials when the service acts for itself. Never put a token into a message.
- **Register a client:** call `AddUserDelegatedToken(audience, scope)` for a call on behalf of a user. Call `AddClientCredentialsToken().AddActorHeaders()` for a call of an own flow to one of our services. Call `AddClientCredentialsToken()` alone for Keycloak and external APIs. The target audience needs an optional client scope on the calling client in the realm file.
- **Message or call:** a feature chooses a message or a synchronous call by its needs. A message fits when the flow does not need the result and the target may be unavailable. A call fits when the flow needs the answer at once. Both carry the actor.
- **Exchanged token:** the handler exchanges the user token for a short token of one audience. The token carries the `organization` scope. It carries the permissions of the user, including those of the calling API, because Keycloak keeps the own client roles of the calling client in its exchanged tokens. The downstream scopes do not narrow it. Keep each permission name unique across all APIs, because the `permissions` claim is flat. The handler keeps it in Redis for each user, audience, and scope, shared by the instances of the service, until `RefreshMarginSeconds` plus a random jitter of up to `RefreshJitterSeconds` before it expires. Redis removes the entry when the token expires. One instance fetches a token that is due: the others wait on a Redis lock and read the new token, and they fetch it themselves when the lock outlives `LockTimeoutSeconds`. The service token cache uses the same store and the same refresh moment. Asynchronous work has no user token, so it never exchanges.
- **Revocation of an exchanged token:** an exchanged token is used only inside a user request that passed the gateway revocation check, so the target needs no revocation check of its own. Keycloak also refuses the exchange for a disabled user.
- **Service token:** it carries the permissions of its service account, narrowed to the downstream scopes of the current flow. A use case declares them with `[DownstreamScopes(...)]`. A worker that is not a use case calls `IDownstreamScopeHolder.Enter`. The handler asks for the scope `{service}-{name}` of each downstream scope. Without a downstream scope, the token carries no permission. The downstream scopes narrow only this token.
- **Keycloak client per service:** each deployable unit has one client and one secret. Its service account holds a service role with the permissions of all its flows. Role scope mappings and `fullScopeAllowed: false` narrow the service token to the downstream scopes that the flow asked for.
- **Failed calls:** a failed outgoing HTTP call throws an `HttpRequestException` with the method, the path without the query, the status, and a reason. One composed reader (`EnsureSuccessAsync`, `HttpErrorReasonReaders.Default`) takes the reason from the allow-listed fields of the three error formats: ProblemDetails, the Keycloak `errorMessage`, and OAuth 2.0. The message never holds the raw body.

## Messaging

- **Transport:** Rebus sends one message type, `IntegrationEnvelope`. It holds the message type name and the JSON payload.
- **Broker:** all topics share one RabbitMQ topic exchange, `RebusTopics`. The routing key is the message type name.
- **Queue:** each service owns one input queue (`Messaging:QueueName`). It subscribes to each message type that the service handles.
- **Outbox processor:** it locks one pending row with `FOR UPDATE SKIP LOCKED`, publishes it, and marks it in one transaction. The row ID is the Rebus message ID. A run ends when no row is due or when a publish fails. The next run starts after the polling interval.
- **Inbox:** a Rebus handler stores each delivery in the inbox. A duplicate message ID creates no second row. The insert runs under the retrying execution strategy of the service context, so a short database outage during delivery is retried inside each Rebus attempt.
- **Inbox processor:** it locks one row per transaction, restores the actor, and calls the use case `IRequestHandler<TMessage>` through the validation and logging decorators. A failure rolls back the transaction and schedules a retry.
- **Inbox attempt limit:** an inbox row stops after `Messaging:InboxMaxAttemptCount` failed attempts (default 10, about 13 minutes) and gets `failed_on`. The processor never claims it again and logs one `Error` entry for it. The outbox has no limit, because its failures are broker outages.
- **Run a failed row again:** after a fix, set `failed_on = NULL`, `attempt_count = 0`, and `next_attempt_on = now()` for that row.
- **Retry delay:** the delay doubles from two seconds and stops at five minutes.
- **Delivery:** the guarantee is at least once. A crash after the publish and before the commit sends a message twice. The inbox drops the duplicate.
- **One use case:** each message type has exactly one use case per service. `AddUseCases` throws at start-up when one request has two handlers. When two steps must react to one message, one use case runs both, or it saves a new message through the outbox. A use case without a result derives from `RequestHandler<TRequest>`, and a caller injects `IRequestHandler<TRequest>`: an internal adapter calls the decorated pipeline, so validation and logging always run.
- **Broker health:** `/health/ready` checks RabbitMQ on one cached connection. A failure reports `Degraded` with status `200`, because the outbox accepts writes while the broker is down. The check times out in 3 seconds, below the gateway probe timeout.
- **Throughput and backlog:** both processors handle one message per transaction. This is enough for business events. The gauges `healthyfac.messaging.pending` and `healthyfac.messaging.oldest_pending.age` show the backlog of each processor (see **Observability**). When the age grows under normal load, change the outbox processor to claim a batch of rows in one transaction. The inbox stays one message per transaction, so a failed handler rolls back only its own message.
- **Actor headers:** `healthyfac-actor-id`, `healthyfac-company-id`, and `traceparent`. A message without a valid actor header, message ID, or company header goes to the `error` queue at the first attempt. The `error` queue holds only messages that the inbox cannot store: these header faults and a payload that `jsonb` cannot store (see **Invalid messages**). No retry can fix them.
- **Invalid messages:** a payload that does not deserialize, or that fails the validator of its contract, gets `failed_on` at the first attempt, with no retries, and the processor writes one `Error` log entry. The payload stays in the database, where it can be queried and run again. The inbox key drops every later copy of the same message ID, so one invalid message gives one row and one log entry. Other rejections (e.g., a missing entity) keep the normal retries, because message order is not guaranteed. A payload that `jsonb` cannot store (not JSON, or a `\u0000` escape in a string) goes to the `error` queue at the first attempt, because the insert would fail on every attempt.
- **Delivery retries:** other delivery failures get 20 attempts, and each attempt retries transient database failures, so a database outage of about 10 minutes loses no message. The `error` queue is final: a message in it is lost.
- **Error logs:** each move to the `error` queue writes an `Error` log entry with the message ID. Rebus logs reach the application logger without extra configuration.
- **Tracing:** the `HealthyFac.Messaging` source writes the spans `send`, `receive`, and `process`. Each span is the parent of the next, so one trace goes from the HTTP request through the handler. The inbox logs `Information` for each handled message. An SQL span is recorded only under a parent span (`ConfigureParentOnlyTracing`), so the idle polls of the processors create no trace. Processor health comes from the metrics of the `HealthyFac.Messaging` meter (see **Observability**).

## Actor Context

- Each DI scope has one actor: the kind, the actor ID, the name of a service actor, the company ID, and the employee ID. `ICurrentUserProvider` reads it.
- An HTTP request, an inbox message, or a job enters the actor once. A second enter throws until the first lease ends.
- A scope outside an HTTP request starts with `CreateActorScope`. It is the only way to start a job scope, a processor step, or the database start-up.
- **Service call:** a service call carries the actor of the calling flow in the actor headers `healthyfac-actor-id` and `healthyfac-company-id`. Messages use the same headers, and the trust is the same: the target trusts the calling service.
- A service token from a client in `ServiceActors:AllowedClients` runs as the actor of the headers, a user included. The target keeps the actor ID as it is, as for a message. A client outside the list, or a missing or invalid actor header, returns `401`. An empty list accepts no service token.
- A token with a client ID and the user shape (for example, an exchanged token) is a user token. The target ignores the actor headers on it.
- The restored actor of a service call gets no rights of its own. The permissions of the call come from the service token, never from the restored user. When the actor context gets permissions, a service call fills them from the service token.
- A request with a user token never sends actor headers on a service token. `AddActorHeaders` throws and sends nothing in that case: the call must use the token exchange. The gateway removes both actor headers from every external request.
- A use case that a service calls takes the company from the request or from the company header, and it checks that the company exists. It never reads `GetCompanyId()` for an actor without a company.
- An outgoing call reads the actor from the asynchronous flow that entered it, because a handler of `IHttpClientFactory` lives in its own DI scope.
- Only Infrastructure and Web can set the actor. `ActorContextHolder` lives in Shared.Infrastructure, so an Application handler cannot replace the actor.
- An actor has one of three kinds: `user`, `service`, and `anonymous`. The values are part of the actor IDs, so a rename changes the IDs.
- A service never acts as a whole. A flow of the service starts the work: the database start-up, the outbox processor, or the inbox processor. Each flow is a service actor with the name `<service>:<flow>` (for example, `core:outboxProcessor`).
- The `Service:Name` setting names the running service (`core`, `auth`, or `gateway`). The processors and the start-up read it to build their service actor. A start-up check rejects any other value.
- Every actor that is not a user has a name-based UUID (version 5) in one fixed HealthyFac namespace. The key is `anonymous` or `service:<service>:<flow>`. The ID is the same in every environment and needs no table. A Keycloak user ID is version 4, so a user ID never equals an actor ID.
- A request without a signed-in user runs as the anonymous actor, never as a service actor. The anonymous actor has no company and no employee. Nothing grants it a right.
- An authenticated HTTP request runs as the user of its token. `ActorContextMiddleware` runs after authentication and reads `sub`, `organization`, and `employee_id`. Each value must be a GUID, and `organization` must hold exactly one value. Any other shape returns `401`, because the tenant is not clear.
- `Outbox.Add` stores the actor in the row. The inbox processor restores the original actor, so audit fields show who started the work.
- A receiver keeps an incoming actor ID as it is. The anonymous ID gives `anonymous`, any other version 5 ID gives `service`, and every other ID gives `user` (`KnownActors.KindOf`). A restored actor has no name, and the company is kept. Only the service that runs a flow knows its name. The trace links the receiver to that flow.
- Each service declares its own flows. The common flows that shared code runs stay in Shared (`ServiceActor`). A flow of one service lives in that service's project and uses `KnownActors.ForServiceFlow`.
- An audit view shows a user by name. It shows a service actor or the anonymous actor as a generic label from `KindOf`. It never shows a flow name.

## Use Case Rules

- **Run order:** logging, input validation, pre-handler check, downstream scope, handler. Input validation rejects bad input before any query.
- **Pre-handler check:** every use case has one `IPreHandlerCheck<TRequest>`. It checks scope only: the actor works inside their own company (`ActorContextScopeChecks`). A failed check returns `403`. A scope check on a parent resource (e.g., the machine of a status definition) loads it in the check and throws `NotFoundException` (`404`); the scope filter of the loaded resource stays in its handler query. Other stateful rules (uniqueness, existence, state) stay in the handler. A use case without a scope rule declares an empty subclass of `PassThroughPreHandlerCheck<TRequest>`. `AddUseCases` fails at start-up for a request without exactly one pre-handler check, so a use case cannot skip the check in silence.
- **Data scope:** a handler that loads one resource filters the query by the company of the actor. A resource outside it is "not found" (`404`), so the answer does not show that it exists.
- **Permissions:** endpoint policies check permissions. The pre-handler check never does.

## Machines

- **Endpoints:** `POST /machines` (`machines:write`), `GET /machines/{id}` (`machines:read`), `PUT /machines/{id}` (`machines:write`), `DELETE /machines/{id}` (`machines:delete`), `POST /machines/search` (`machines:read`), `POST /machines/lookup` (`machines:read`; `{ search? }` answers at most 50 `{ id, displayName }` options of the company by name, for pickers and filters), and `GET /company` (any signed-in user; the name and the IANA time zone of the company of the token). An ID in a path is the encrypted ID. A malformed ID returns `404`.
- **Serial number:** unique per company among the machines that are not deleted, ignoring case. The entity keeps `SerialNumberKey` (lower case) for a unique index with the filter `deleted_at IS NULL`. The handler checks first (`409`), and the index catches a parallel create or update (also `409`).
- **Soft delete:** a shared `ISoftDeletable` entity keeps its row. `SoftDeleteInterceptor` turns `Remove` into an update that sets `DeletedAt` and `DeletedBy`, and a global query filter hides the row. A second delete returns `404`. No restore exists yet. A collection of a root is a child entity (`ISoftDeletable`) with `HasMany` and `OnDelete(Cascade)`, never `OwnsMany`. The interceptor soft-deletes every entry that EF Core marks deleted, so a loaded child is soft-deleted with its root, and a child that leaves the collection is soft-deleted as an orphan. The interceptor also soft-deletes the untracked rows of each `Cascade` relation of a soft-deleted entity, also the grandchildren, with one `UPDATE` per relation; a `Restrict` relation stays unchanged. Such a save runs in one transaction (`TransactionRunner.SaveAsync`). A use case that drops a child loads the collection with `Include`. A hard delete of a root removes its children through the database cascade.
- **Grid contract:** `GridRequest<TFilter, TSortColumn>` (`Offset`, `Limit` 1 to 100, one sort column, a typed filter) and `GridResponse<TItem>` (`Items`, `TotalCount`) live in `Shared.Application/Grids`. A filter field is a `TextFilter` (starts with, ignoring case), a `SetFilter<T>`, or a `DateRangeFilter` (`From` inclusive, `To` exclusive, UTC), or a `DateOnlyRangeFilter` (`From` inclusive, `To` exclusive, plain days without a time zone, for a `DateOnly` column). A sort map links each sort column to a key expression, and the ID is the last sort key, so pages never skip or repeat a row. The web app sends a picked day range as the start of the first day to the start of the day after the last day, in the company time zone (`CLOCK.timeZoneId()`), converted to UTC. For a `DateOnlyRangeFilter`, it sends the plain days (`yyyy-MM-dd`, no zone): `from` is the first picked day, and `to` is the day after the last picked day.
- **Description:** rich text as HTML. The limit counts the **visible text**: at most 5000 characters, not 5000 characters of HTML. A raw cap of 20,000 characters (`RichTextConstants.HtmlMaxLength`) protects the storage and the parser; the column is `text` with a check constraint at the cap. `IRichTextPolicy.Inspect` (HtmlSanitizer, in Shared.Infrastructure) parses the HTML once. It gives the allow-list verdict (a removal means `400`) and the visible length. It never alters the text. The shared rule `RichTextRules.IsRichText` (`Shared.Application/RichText`) runs in this order: raw cap (no parse), allow-list, visible limit. The machine, the status definition, and the metric definition validators call it. The visible length is the text content of the parsed body, in Unicode normalization form C, counted in UTF-16 characters. The web app counts the same way with `DOMParser`, so both sides agree.
- **State history:** the table `machine_state_histories` holds one row per state and its start (`StartedAt`). The current state is the state of the row with the latest `StartedAt`. Every machine starts `operational`. `Machine.ChangeState` keeps the timeline strictly ordered and rejects a repeat of the current state. `PUT /machines/{id}` (with the other fields) and `POST /machines/{id}/state` (state only, `machines:write`) change the state. The new state starts now. The same state changes nothing and returns 204. The change updates the machine row, so a parallel change gets 409. The change adds `core.v1:MachineStateChanged` to the outbox in the same save (see **Events**). A machine delete soft-deletes its history rows in the same save. The grid filters on the current state and does not sort it.
- **Expected go-live:** `ExpectedGoLiveOn` is a required day (`date`) in the company time zone, the expected first day of telemetry. Create: today or later in the company zone. Edit: not before the creation day (`CreatedAt` in the company zone). A create draft gets today unless the drawer sends a date; an update draft keeps the stored date and rejects a date. The grid shows, filters (a half-open range of days), and sorts it. A failed rule returns `400` with the key `expectedGoLiveOn`. The silent sender check that will read it is not built yet.
- **Gateway ID:** the `Machine` constructor generates a random gateway ID of 16 lower-case base32 characters (`a-z2-7`, `GatewayIds` in `Shared.Domain`). It never changes. A unique index covers it without the soft delete filter, because an ID is never reused (a listed exception in `SoftDeleteModelTests`). The machine drawer shows it with a copy button.
- **Events:** `CreateMachine` adds `core.v1:MachineCreated` (machine ID, gateway ID, company) and `DeleteMachine` adds `core.v1:MachineDeleted` (machine ID, company) to the outbox in the same save. `POST /machines/{id}/state` and `PUT /machines/{id}` add `core.v1:MachineStateChanged` (machine ID, company, state, `StartedAt`) to the outbox in the same save when the state changes. It has no consumer yet (the telemetry feature adds it), and the development seeder writes state rows without messages. The delete cascade to the Telemetry definitions is eventual: Telemetry soft-deletes the registration, the status definitions, and the metric definitions when it handles the event. For a few seconds after a create, Telemetry returns `404` for the machine, and after a delete it still accepts requests for it.
- **Seed machines:** the demo seed (see **Demo Seed** in **Identity**) creates the machines through the use cases of Core: the seed job applies 3 machine drafts, and Telemetry registers the machines from the published events.
- **Existing development machines:** machines created before the gateway ID migration have no Telemetry registration, because only the seed and `CreateMachine` publish `MachineCreated`. Recreate a development database once after this change (`docker compose run --rm seeder --reset`, services stopped).

## Work Orders

- **Scope:** Core owns work orders. A work order has a title, a rich text description (the **Description** rule of **Machines**), a priority (`low`, `medium`, `high`, `critical`), a category (`inspection`, `preventive`, `repair`, `other`), an optional machine of the company, an estimate (5 to 720 minutes, steps of 5), and up to 20 file refs of Document. Audit fields and a soft delete apply.
- **History:** the table `work_order_histories` is append-only. One row holds a revision, the status (`backlog`, `staged`, `inProgress`, `blocked`, `completed`, `rejected`), the assignee, the planned start (a local time in the company zone and a UTC copy), and the estimate. Every row stores the estimate of the work order at that revision, and an estimate change adds a row with the current status, assignee, and start. `PUT /work-orders/{id}` also takes the assignee and the planned start (both set, or both `null`): one save changes the schedule and the estimate together and adds one row (`WorkOrder.Reschedule`). The work order keeps `CurrentRevision`. A composite key `(id, current_revision)` to the history row is `DEFERRABLE INITIALLY DEFERRED`, so the work order and its first row enter in one save, and the key still proves that the current row exists. Every change adds a row, never an update. A work order delete soft-deletes its history rows in the same save. The list and the filters read the current row through `WorkOrderCurrentRow`.
- **Status:** a new work order is `backlog` and has no assignee. Assign moves `backlog` to `staged`. Unassign moves a scheduled work order back to `backlog`. A status change accepts `staged`, `inProgress`, `blocked`, `completed`, and `rejected`; it never accepts `backlog` or the current status. Move keeps the status and changes the assignee or the slot.
- **Endpoints:** `POST /work-orders`, `POST /work-orders/search`, `POST /work-orders/search/batch`, `GET /work-orders/{id}`, `PUT /work-orders/{id}`, `POST /work-orders/{id}/status`, `GET /work-orders/{id}/history?limit&after` (a keyset page: the rows with a revision below `after`, the newest first, answered as `{ items, totalCount, nextAfter }`; `nextAfter` is `null` on the last page), `PUT /work-orders/{id}/assignee`, `POST /work-orders/{id}/move`, `DELETE /work-orders/{id}/assignee`, and `DELETE /work-orders/{id}`. Create, update, and status need `work-orders:write`. Search, batch search, get, and history need `work-orders:read`. The batch search takes 1 to 6 searches (`{ searches: [...] }`, each a body of the single search) and answers `{ pages: [...] }` in the same order; every search runs the one query of the single search with the access scope of the token, and the status board sends only batch requests. Assign, move, unassign, and delete need `work-orders:write-company`. A write sends the row version (`rowVersion`); a stale one returns `409`.
- **Access scope:** the Web layer resolves the scope from the token. A read (get, search, history) gives the **company** scope to a token with `work-orders:read-company`. A write that checks the scope (create, status change, update, apply a draft) gives it to a token with `work-orders:write-company`. Any other token has the **own** scope: the actor sees and changes only the work orders that are assigned to the employee of the actor. A work order outside the scope returns `404`. An own-scope actor without an employee sees nothing.
- **Slot rules:** a slot is the planned start plus the estimate. Create, assign, move, and update check four rules in one transaction (`ScheduleChecks`). Rule 1: the assignee is an active employee of the company. Rule 2: the local start is on the 5 minute grid, exists in the zone, is not in the past, and is at most 365 days ahead. Rule 3: the slot fits inside one block of the day of the assignee. Rule 4: the slot overlaps no other scheduled work order of the assignee; the end of one work order may equal the start of the next. A broken rule 2 returns `400`. A broken rule 1, 3, or 4 returns `422`.
- **Occupancy:** a scheduled work order occupies its assignee from the planned start to the later of the planned end and the completion moment, so a late completion blocks the time that it used. The interval is half-open.
- **Completion slide:** when a work order completes after its planned end, the movable work orders of the same assignee at or after its planned start, up to the local completion date, move. A movable work order on a date before the completion date goes back to the backlog. On the completion date, the movable work orders slide forward from the completion moment, in order, to the earliest free start on the grid inside one block. A work order in progress or completed is fixed. A work order on the completion date that has no fitting start goes back to the backlog. A work order after the completion date stays.
- **Serializable guard:** the use cases that schedule run at the isolation level `Serializable` (`RunInTransactionAsync(operation, IsolationLevel, ct)`). The execution strategy retries a serialization failure (`40001`). Two parallel writes for the same assignee never both pass rule 4. A stale row version returns `409`; a broken business rule returns `422` (`backend-application.md`, **Status Choice**).
- **Delayed:** `isDelayed` is true for a staged work order whose planned start is before now. The database computes it, so the grid also sorts by it.
- **Files:** the work order keeps file IDs only. The web app calls `POST /v1/files/lookup` of Document (at most 100 IDs) to show the name, the extension, and the size. A file of another company is left out.

## Shifts

- **Scope:** Core owns the shifts of an employee. A shift is a list of work blocks per day. A day has no limit on the number of blocks, and the blocks do not overlap. The latest block end is 23:55. A block lies inside one local day.
- **Template versions:** `shift_template_versions` holds a weekly template for one employee from `EffectiveFrom` (a local date of the company zone). The block rows (`shift_template_blocks`) hold the weekday, the start, and the end. The version with the latest `EffectiveFrom` on or before a day applies to that day. A change adds a version or replaces its block rows; it never rewrites history.
- **Overrides:** `shift_overrides` holds one date that differs from the template (a day off or other blocks), with block rows (`shift_override_blocks`).
- **Zone:** the shifts use local times of the company zone. A local time that does not exist (the spring DST gap) uses the offset from before the gap, so it falls just after the gap. A repeated local time (the autumn DST overlap) maps to the earlier instant (`LocalTimes`). The shared file `testdata/dst-europe-kyiv-2027.json` holds the expected values for the backend and the web app.
- **Day schedule:** `DayScheduleResolver` gives the blocks of a day: the override when it exists, else the template. `GET /employees/{id}/schedule` and `GET /company/schedule` return the resolved day.
- **Endpoints:** `GET|POST /employees/{id}/shift-templates`, `PUT|DELETE /employees/{id}/shift-templates/{versionId}`, `GET /employees/{id}/shift-overrides`, `PUT|DELETE /employees/{id}/shift-overrides/{date}`, and the schedule reads. A read needs `shifts:read`; a change needs `shifts:write-company`. A token without `shifts:read-company` has the own scope: the actor reads only the shifts of the own employee. The company schedule needs `shifts:read-company` and `employees:read`.
- **Lookups:** `GET /employees/{id}/schedule/days?from=&to=&excludeWorkOrderId=` returns for each date whether the day has blocks and the longest free span in minutes. `GET /employees/{id}/schedule/free-spans?date=&excludeWorkOrderId=` returns the free spans of one date (local and UTC bounds, on the 5-minute grid, from now on the grid for today). Both need `shifts:read`, follow the own scope (another employee is `404`), and have no range limit. `excludeWorkOrderId` counts the slot of that work order as free. A late completed work order occupies up to its completion moment (`FreeSpans`, `EmployeeOccupancyReader`). Every save of a shift joins touching blocks (a block that starts where the previous one ends), and the past-block guard of today compares the joined blocks: an old block that starts at or before now keeps its start and its end up to now. The day schedule lists the work orders that overlap the date, also ones that started on an earlier date; a work order in progress ends at now on the board.
- **Delete of an override:** a delete of a later date removes the override. A delete of today keeps the part that has passed and returns the rest to the template from now on the grid (`TodayOverrideMerge`); only a block that is running at now joins the template block that starts at now on the grid. A delete of a past date returns `400`.
- **Past part of today:** `ShiftChangeGuard` rejects a change that touches the past. For today, a block that ended and the start of a running block must stay as they are. A day before today never changes.
- **Orphaned work orders:** the guard also rejects a change that leaves a scheduled work order outside every block. It checks each scheduled work order that is not completed and whose planned end is after now (a running or delayed work order counts). The answer is `422` and lists the affected work orders (up to 50). Nothing moves automatically. The supervisor moves or unassigns them first.

## Telemetry

- **Units:** the global tables `quantity_kinds` and `measurement_units` hold the unit catalog, seeded in `SeedRequiredDataAsync` with an `INSERT ... ON CONFLICT` upsert from typed UnitsNet 5.75.1 members (the quantity name, the unit name, and the abbreviation come from UnitsNet). A unit is identified by the pair of the quantity kind name and the unit name (`Percent` exists under two kinds). `GET /metric-units` (`metric-definitions:read`) lists the catalog. The abbreviation of `Scalar.Amount` is empty. The `Discrete` kind is an own constant (`DiscreteUnits`) with the units `Boolean` and `State` (empty abbreviation); `GET /metric-units` leaves it out. There is no unit conversion.
- **Machine registration:** `MachineRegistration` (the machine ID as `Id`, gateway ID, company, the schema revision number) is created by the handler of `core.v1:MachineCreated` ("find, else create") and soft-deleted with its definitions by the handler of `core.v1:MachineDeleted`. A delete before the create retries through the inbox. Every metric and status use case checks the registration by company in its pre-handler check (`MachineRegistrationScope`); a machine outside the scope, a deleted machine, and an unknown machine return `404`.
- **Metric definitions:** key (`^[a-z][a-z0-9_]*(\.[a-z][a-z0-9_]*)*$`, at most 100 characters, unique per machine among active definitions, never changes), name, description (rich text), value kind (`numeric`, `boolean`, `stateSet`), unit (always set; numeric: a unit of the catalog from the request, never a `Discrete` unit; boolean and state set: `Discrete.Boolean` or `Discrete.State`, set by the server), min and max (numeric only, `min < max`), and states (state set only, at least 2 unique codes). Key, value kind, and unit never change. A deleted definition frees its key. The audit and soft delete fields apply.
- **Staged apply:** `PUT /machines/{machineId}/metric-definitions` (`metric-definitions:write`) takes `expectedRevision`, `created`, `updated`, and `deleted` and stores all changes, the raised revision of the registration, and a new schema revision in one save. A stale revision returns `409`. The row version of the registration and the unique index on (registration, revision) catch a parallel apply (`409`). A `400` names the failed item by its path (`created[2].key`). `GET /machines/{machineId}/metric-definitions` (`metric-definitions:read`) lists the active definitions with the current revision, and `GET /machines/{machineId}/metric-schema` returns the last schema.
- **Payload schema:** JsonSchema.Net 9.6.0 builds a draft 2020-12 schema per machine and revision (`$id` `urn:healthyfac:gateways:{gatewayId}:metrics:{revision}`). It asserts the envelope (`sampledAt` as `date-time`, `metrics`, `statuses`, no other root field) and the JSON type of each key. The range, the states, the unit, and the title are annotations, never assertions. Every revision is stored (`metric_schema_revisions`, append-only). Each build and each parse uses its own schema registry, because the global registry rejects a second schema with the same ID. The intake keeps no parsed schema in process memory.
- **Status definitions:** a machine has 0 to many statuses with a code (at most 50 characters, unique per machine among active rows, ignoring case), a severity (`info`, `warning`, `error`), and a rich text description. Endpoints are `POST|search|GET|PUT|DELETE /machines/{machineId}/status-definitions` with `status-definitions:read|write|delete`. A status change adds no schema revision. They replace the Core error codes.
- **Definition drafts:** Telemetry stores the metric, status, and phase drafts of an extraction (`metric_definition_drafts`, `status_definition_drafts`, `operating_phase_drafts` with its condition and limit row tables) and the proposal entries that tie them to the machine check of Core. A metric draft carries the four default limits and the behavior. A phase draft carries its conditions and limit rows; each row targets exactly one of a definition ID or a draft ID (a check constraint). Applying a metric or status draft moves the rows of the open phase drafts to the new definition ID in the same save. A phase draft applies only when no row targets a draft (`422 draftUsesDrafts`), and a metric or status draft that an open phase draft uses cannot be dismissed (`422 draftUsedByPhaseDraft`). The condition and limit rows are child entities of the phase draft (database `Cascade`, loaded with `Include`, soft delete). See **Insights**, **Drafts** for the states and the endpoints. The permissions are `definition-drafts:read` (search, list, counts) and `definition-drafts:write` (dismiss).
- **Payload:** `{ "sampledAt": "...", "metrics": { "<key>": <value> }, "statuses": ["<code>"] }`. Every message holds the current value of every metric. A value is in the declared unit of its key. The payload has no gateway field.
- **Validation per value:** an envelope failure (not JSON, a gateway ID that is not in the format, an unknown gateway, a missing or unknown root field, a wrong `sampledAt`, a `sampledAt` more than 1 minute ahead) stores a received message with the error and no reading. A wrong JSON type, an unknown or missing key, an unknown status code, and a repeated status code are value errors in `received_messages.errors`; the other values are stored. A number outside the range and a state outside the set are stored with `is_out_of_range = true`, never as an error. The flag uses the definition at receipt.
- **Storage:** `received_messages` (the raw bytes as `bytea` always, the payload as `jsonb` when storable, the errors as `jsonb`, a unique index on the machine and the sampling time that drops a repeated delivery), `numeric_readings`, `discrete_readings`, and `status_readings`. A reading has the natural primary key (definition, sampling time) and no `Id`. Received messages, schema revisions, and readings have neither `IAuditable` nor `ISoftDeletable`. The architecture tests and the model tests list each exception.
- **Intake:** `MqttIntakeService` subscribes to the shared subscription `$share/{group}/healthyfac/gateways/+/messages` with QoS 1 and a persistent session, and runs the use case `ReceiveMachineMessage` as the actor `telemetry:intake`. It acknowledges a message only after the commit. A transient failure (the database is not reachable, a command timeout, the retry limit) leaves the message unacknowledged, drops the connection, and connects again after a delay, so the broker delivers it again; the unique index drops a repeat. Any other failure is the same on every delivery: the service stores the raw bytes as a received message with the error `processingFailed` (no readings, no machine) in a new scope, logs one `Error` with the exception, and acknowledges. A message that fails input validation is acknowledged and logged without the payload. A received message holds exactly one of `payload` (`jsonb`) and `raw_payload` (`bytea`): the raw bytes only for `malformedJson` (including a duplicate property), `unstorableJson` (a U+0000 character or a lone surrogate), and `processingFailed`. Each instance runs `MqttIntake:ConsumerCount` consumers (default 1, at most 16), each with its own client and the client ID `{ClientId}-{index}`. The shared subscription gives each message to one consumer, so the consumers of all instances share the load. The messages are not processed in order, because the readings are keyed by `sampled_at`. Each instance needs a stable, unique `ClientId` (for example a StatefulSet pod name or a Compose replica name), and the count must stay the same between restarts, because the broker keeps the session and the unacknowledged messages by client ID. Each consumer holds up to 1 database connection during a save, so the count stays below the connection pool size. The session expires after `MqttIntake:SessionExpirySeconds` (default 3600, range 60 to 86400). Measured with Mosquitto: the broker keeps the share of an offline member in its queue while the session is alive, and the member gets it again after a reconnect with the same client ID. When the session expires, the broker drops the queued and unacknowledged messages and does not give them to the other members; new messages then go only to the live members. A message is lost when a consumer stays offline longer than the expiry, or when its queue passes a broker limit: `max_queued_messages 100000` and `max_queued_bytes 104857600` (100 MiB) per session (`docker/mosquitto/mosquitto.conf`; the Mosquitto default of 1000 messages is too low). The limits bound the broker memory. A stop finishes the messages that a consumer already started, within `MqttIntake:DrainTimeoutSeconds` (default 20, range 1 to 29, below the 30 second stop time of the host and of Compose). A message that arrives after the stop signal is neither handled nor acknowledged. The consumer then disconnects with the normal session expiry. It never unsubscribes and never deletes its session, so the broker keeps the session for up to `SessionExpirySeconds`, queues the messages that arrive while the instance is down, and delivers them after the restart (measured with Mosquitto: an offline session keeps its share, and the broker still delivers the messages that it assigned to a member after an unsubscribe). If the finish times out, the broker keeps the unacknowledged messages and delivers them again. At start, the service empties its own orphan sessions: for each client ID `{ClientId}-{index}` with an index from `ConsumerCount` to 15 that has a session, it handles the queued messages, unsubscribes, waits `MqttIntake:DrainIdleSeconds` (default 2) without a new message, disconnects, and deletes the session by a short clean-start connection with a session expiry of 0 (MQTTnet cannot send an expiry of 0 on a disconnect). It keeps the normal session expiry while it works, so a failure leaves the session for the next start. A lower `ConsumerCount` therefore loses nothing at the next start of the instance. Data is lost in 2 cases: an instance that is removed for good (no running instance knows its sessions, so the broker queues their share until the expiry and then drops it), and a stop or crash that lasts longer than the session expiry. The `ClientId` of an instance must stay the same across restarts: a StatefulSet pod name or a fixed Compose value works. A Deployment pod name changes on each start, so each rollout leaves orphan sessions that take their share for up to 1 hour and then lose it. The health check reports `Degraded` while the intake is enabled and fewer than `ConsumerCount` consumers are connected.
- **Intake Telemetry:** Each received message gets one `Consumer` span `process healthyfac/gateways/+/messages` from the source `HealthyFac.Telemetry.Intake`. The name holds the subscription pattern, never the gateway ID. A `traceparent` MQTT user property makes the span continue the trace of the sender. Without it, the span starts a new trace. The use case spans are its children. The span tags hold the topic, the shared group, the consumer index, the result, and the error code of a rejected message. The result is one of `stored`, `stored_with_errors`, `rejected`, `duplicate`, `invalid`, `failed`, or `redelivery`. The last two set the span status to `Error`. The meter `HealthyFac.Telemetry.Intake` counts the messages by result (`healthyfac.intake.messages`). It records the handle duration (`healthyfac.intake.handle.duration`). It records the lag between `sampledAt` and receipt (`healthyfac.intake.lag`, only for stored messages). It reports the messages in flight and the connected consumers. It counts the messages of emptied orphan sessions and the drain timeouts. No metric holds a gateway ID, a topic, or a machine ID as a tag. The service does not measure the queue depth of the broker, because that needs a monitor session on the broker (decided against). A growing lag shows a growing queue indirectly.
- **Evaluator worker:** `EvaluationWorker` (Telemetry) runs a `PeriodicTimer` (`Detection:EvaluationIntervalSeconds`). It claims one due machine from `machine_evaluations` with `FOR UPDATE SKIP LOCKED` and a lease (`Detection:LeaseSeconds`), evaluates it, and sets the next due time. It reads the readings after the watermark and at most `Detection:SettleLagSeconds` before now, in `sampled_at` order, at most `Detection:CatchUpBatchReadings` per run. A longer backlog continues in the next run. A late reading stays stored and shown in the history, but it changes no statistics. The evaluator counts late readings per run in a metric. Episode times come from `sampled_at`, so a catch-up after a restart gives the true times. When no machine of any company sent a message within `Detection:SilenceLimitSeconds`, it opens no `silentMachine` episode, logs one `Warning`, and counts it, because the fault is the intake or the broker.
- **Statistics:** Welford warm-up (`Detection:WarmUpSamples`) per metric and phase; a time-aware EWMA with a fast mean and a slow mean; a measured drift spread that bounds the drift `z` from below with the white noise value; Holt level and slope for the time to the alarm limit; a sigma floor of `Detection:SigmaFloorShare` of `Max - Min`; a gap (`Detection:GapSeconds`) that restarts the fast mean and the Holt state; and a freeze of the baseline while a `threshold`, `drift`, or `trend` episode of the metric is open. A `counter` metric runs no drift rule. Only numeric metrics have statistics. The statistics key is the metric definition and the phase; a machine without phases uses the phase `none`.
- **Rules and severities:** `threshold` (`warning`, `alarm` beyond an alarm limit), `drift` (`warning`), `trend` (`warning`), `status` (`warning` for a `warning` status, `alarm` for an `error` status; an `info` status opens nothing), `silentMachine` (`alarm`), and `unknownMode` (`warning`). The `drift` and `trend` rules also need a streak of `Detection:Persistence` time constants. The threshold rule uses the limit row of the current phase, else the limits of the definition; during a mismatch before a phase switch it opens only beyond the looser of the two limits on each side.
- **Episodes:** a partial unique index allows one open episode per machine, rule, and metric or status. Each open, escalate, and resolve adds `telemetry.v1:SignalEpisodeChanged` to the outbox in the same save. The message holds a snapshot (value, limit, `z`, the forecast, the phase, the times) and a `Sequence` that rises by 1 per change. A consumer drops a message whose `Sequence` is not above the stored one.
- **Operating phases:** `operating_phases` (`code` and `priority` unique per machine, `is_tracked`), `operating_phase_conditions`, and `operating_phase_limits` (one row per metric and phase; a row replaces all four limits, an empty value means no limit on that side). All conditions of a phase hold together. A condition reads a status (`active`, `inactive`), a numeric metric (`greaterThan`, `greaterOrEqual`, `lessThan`, `lessOrEqual`, `between`), a boolean metric (`isTrue`, `isFalse`), or a state set metric (`in`). The phase of a sample is the first matching phase by priority. API: `GET|POST /machines/{machineId}/operating-phases`, `PUT .../operating-phases/order`, `GET|PUT|DELETE .../operating-phases/{id}` (`operating-phases:read` and `operating-phases:write`). A change of the conditions or of `is_tracked` resets the statistics of the phase. A deleted phase keeps its rows. Deleting a definition that an active phase condition uses returns `422`.
- **Phase intervals and times:** `phase_intervals` (machine, phase or `null` for the unknown mode, `started_at`, `ended_at`) is append-only like the readings (no audit, no soft delete). The evaluator closes the open interval and opens the next one at the sample where the current phase switches. It closes the open interval at the last evaluated sample when the machine is skipped (not operational) or the silence rule opens, so the time without data stays outside every interval. A partial unique index allows one open interval per machine, and a machine without phases writes none. `GET /machines/{machineId}/phase-times?from&to` (`signals:read`) clips the intervals to the range and returns the seconds per phase (a deleted phase keeps its name with `isDeleted`), the unknown mode seconds, and the no-data seconds; the three add up to the range. Core answers `GET /machines/{id}/state-times?from&to` (`machines:read`) from the state history: the seconds per machine state and the seconds before the machine existed.
- **Masking rules:** (1) phases describe the mode, so conditions should use statuses, state sets, and booleans; the editor warns for each metric that a numeric condition reads. (2) The phase `none` learns only on a machine without phases. (3) Samples that match no phase for longer than `Detection:UnknownModeDwellSeconds` open an `unknownMode` episode. (4) During a mismatch shorter than `Detection:PhaseDwellSeconds`, the samples keep the last phase and update no statistics; after a switch, the samples of `Detection:SettleTimeSeconds` update none. (5) A phase has no limit row for a metric that its own conditions read; the API returns `400`.
- **Machine state and go-live:** Telemetry consumes `core.v1:MachineStateChanged` and `core.v1:MachineGoLiveDateChanged` and drops a message that is not newer than the stored one. `MachineCreated` carries `ExpectedGoLiveOn` and `GoLiveStartsAt`, and both are required (the registration columns are not null; no step fills a missing date). A message for an unknown machine throws `NotFoundException`, so the inbox retries until `MachineCreated` arrives. `inMaintenance` and `outOfService` make the evaluator skip the machine (the watermarks move, nothing learns, no episode opens, the silence rule is off). `inMaintenance` to `operational` resets the statistics and resolves the open episodes. The silence reference is the later of the last `ReceivedAt` and `GoLiveStartsAt`.
- **gRPC reads:** `HealthyFac.Telemetry.Contracts` holds `telemetry_signals.proto` with `GetMetricHistory` (bucketed `avg`, `min`, `max`, and `count`; the caller sends `from`, `to`, and the bucket count, at most `Detection:HistoryBucketCap`) and `GetSignalEpisodes`. The calls use the service token, the actor headers, and the downstream scope `telemetry`, and they check the machine with `MachineRegistrationScope`. The SPA reads the same use cases over HTTP (`GET /machines/{machineId}/metric-history` and `.../signal-episodes`, `signals:read`).
- **No retention:** received messages and readings grow without limit for now. No retention job exists.
- **Eventual consistency:** the registration appears after the outbox publishes `MachineCreated`, and the definitions disappear after `MachineDeleted`.

## Machine Simulator

The machine simulator (`backend/src/Tools/HealthyFac.MachineSimulator`) sends machine messages to Mosquitto for the machines that exist in Core. It is for development and demos only. It is no service of the product: it has no database, no gateway route, and no login.

- **Discovery:** the simulator reads the machines of `healthyfac_core` and the registrations and definitions of `healthyfac_telemetry`. Both connections are read-only (`Options=-c default_transaction_read_only=on`), so a write fails with the SQL state `25006`.
- **Timing:** the publish loop sends one message each second for each machine. The state poll runs every 5 seconds (state, registration, definitions, go-live date). The discovery runs every minute and once at start (new machines and the stored counter values). A machine that the state poll no longer finds (deleted machine, deleted registration) stops within 5 seconds. The intervals are the `Simulator` section.
- **Binding:** the serial number of a machine picks its scenario, ignoring case: `MTC420-24-0187` (CNC turning center), `HV-EP80-2023-04412` (centrifugal pump), and `NRS37-22-1093` (screw compressor). Every other machine gets the generic scenario, which sends a value for every defined metric (a numeric value stays inside its min and max) and no status code.
- **Scenario library:** the scenarios (`SimulatedMachine`, the curves, the payload builder) live in `backend/src/Tools/HealthyFac.MachineSimulator.Scenarios`. The simulator and the demo seed job both use it, so the seeded history and the live messages come from one code.
- **Modules:** a detailed scenario has modules (for example `spindle`, `hydraulics`). A module drains from `expected` to a failure in the drain time of the drain (a live drain takes 3 minutes, `Simulator:DrainDuration`; the seed job passes a drain time in hours for each drain), passes the milestones 50, 80, and 100 percent, and sends the status codes of its rules. A trip failure stops the machine, and a warning failure keeps it running. The state `inMaintenance` followed by `operational` resets every module.
- **Gates:** a machine sends messages only while all gates are open: the machine is registered in Telemetry, the go-live day (`ExpectedGoLiveOn`, in the company zone) has come, the control API did not stop the machine, and (generic scenario only) the Core state is `operational`.
- **Payload:** `{ "sampledAt": "<UTC>", "metrics": { ... }, "statuses": [ ... ] }` to `healthyfac/gateways/{gatewayId}/messages`, QoS 1, no retain. The simulator drops a key or a code that the definitions do not hold, and a value of the wrong kind, so the Telemetry intake accepts each message. A message that the broker does not take is dropped, never buffered. Each message carries the `traceparent` user property of its `send` span.
- **Control API:** `GET /machines`, `GET /machines/{machineId}`, `PUT /machines/{machineId}/run` (`{ "isRunning": bool }`), and `PUT /machines/{machineId}/modules/{module}/mode` (`{ "mode": "expected" | "draining" | "failure" }`). The page `/scalar` lists them. The API has no login, so Compose binds it to `127.0.0.1`.
- **Health:** `/health/ready` is unhealthy while one database or the MQTT broker is not reachable, because the simulator has no work without them.
- **Single instance:** one simulator runs for each Core database. A PostgreSQL session advisory lock on the read-only Core connection enforces it (`SimulatorInstanceLock`, the first hosted service). A second simulator logs one `Error` and exits. Compose (`restart: unless-stopped`) starts it again with a growing delay.
- **Profile:** the Compose service `simulator` has the profile `simulator`, so `docker compose up` never starts it.
- **Telemetry volume:** one machine sends 86,400 messages each day, and Telemetry stores every reading with no retention. Stop the simulator after a demo, and use `docker compose down -v` to drop the data.

## Document

- **Scope:** Document stores files for the company and for machines. It has its own database (`healthyfac_document`) and one blob container (`files`). Core and Telemetry never read it. Insights reads the file bytes through a gRPC call and a signed link (see **Insights**). Document makes no outgoing service call.
- **File ref:** a file ref holds the owner company, the machine (`null` for a company file), the purpose, the name without the extension, the stored extension, the media type, the size, the SHA-256 hash, and the description. The ID is the name of the blob. The ref has audit fields and a soft delete.
- **Purpose and scope:** the purpose `attachment` shows in the file grids. The purpose `embedded` is an image in a rich text description. An embedded image belongs to the company, has no machine, and shows in no grid. A machine file needs a machine registration in the company of the actor. A company file has no machine rule.
- **Machine registration:** Document copies the machine ID and the company from `core.v1:MachineCreated`. `core.v1:MachineDeleted` soft-deletes the registration and the machine files in one save. A second delete message changes nothing.
- **Allowed types:** `png`, `jpg` (also `jpeg`), `gif`, `webp`, `pdf`, `docx`, `xlsx`, `pptx`, `txt`, `csv`, and `md`. Embedded images allow the four image types only. Limits: 100 MiB for an attachment, 5 MiB for an embedded image, 255 characters for a name, and 500 characters for a description.
- **Type proof:** the service never trusts the client. FileSignatures detects the type from the bytes. The detected type, the client extension, and the declared media type must agree. A text type passes when no binary format matches and the content is strict UTF-8 without a NUL byte. The map compares the exact format type, so a macro-enabled or legacy Office file is refused. An architecture test checks the map.
- **Upload order:** inspect the file, write the blob (it fails when the blob exists), then save the ref. The save uses `CancellationToken.None` (form **Finish**), so a stored blob always gets its ref. A failed save leaves an orphan blob. The service has no blob cleanup yet. A storage failure gives `503`.
- **Concurrency:** four uploads run at the same time and eight wait (`UploadLimits`). The next upload gets `429`. An upload buffers its body on disk (`ASPNETCORE_TEMP`) above 64 KiB.
- **Links:** `POST /v1/files/links` takes at most 1000 encrypted IDs and returns one signed read link for each file that the actor may read. A deleted file, a file of another company, a machine file of another company, and a bad ID are left out. The limit of 1000 comes from the rich text cap: 20,000 HTML characters hold at most about 400 image tags. A change of that cap reviews the limit.
- **Link format:** a link is a service SAS on one blob. It lives 5 minutes (`FileStorage:LinkLifetimeSeconds`), allows read only, and sets the type and the `Content-Disposition` of the response. Images are `inline`; other files are `attachment`. The SAS uses the storage account key. Outside Development the protocol is HTTPS only.
- **Link audience:** a link for a browser goes through the gateway (`PublicBlobBaseUrl`). A link for one of our services (`FileLinkAudience.Internal`, the gRPC `GetFileLink`) points at the blob endpoint of the storage connection string on the private network. Both carry the same signature. A call between our services never goes through the public gateway.
- **Blob route:** the gateway route `document-blobs` serves `GET` and `HEAD` on `/api/document/blobs/{container}/{id}` without a token. The SAS is the credential. The route adds `X-Content-Type-Options: nosniff`, uses the rate limit policy `blob-download` (120 requests per minute for each client address), and has no CORS policy. The gateway logs the path only. The signature never reaches a log or a span tag: the configured log levels keep the ASP.NET Core and YARP entries (they hold the full URL) at `Warning`, and the OpenTelemetry instrumentation redacts the query.
- **Upload size at the gateway:** the route `document` sets `MaxRequestBodySize` to 101 MiB. Every other route keeps the Kestrel default of about 30 MB. A body above the limit gives `413`.
- **Health:** the blob container check reports `Degraded` when the storage fails, never `Unhealthy`. The service starts when the container cannot be created. The first upload then gives `503`.
- **Telemetry:** the source `HealthyFac.Document.Files` has the spans `File.Inspect` and `Blob.Upload`. The tags are the detected type, the purpose, and the result. No tag holds a file name, an ID, or a size.
- **Migration:** Document keeps one migration, `InitialCreate`. A model change regenerates it until the first release.
- **Known limits:** a link works until it expires, also after the file is deleted or the access ends. The service signs links with the account key. It has no antivirus scan and no blob cleanup. The blob of a deleted file stays.

## Insights

- **Scope:** Insights owns `healthyfac_insights` (pgvector `vector(1536)`, HNSW index with cosine distance). It holds the ingest attempts, the ingested documents (one copy of the file metadata), the document chunks with their embeddings, and the metric unit copy. Insights never writes the database of another service.
- **Ingest attempt:** `POST /files/{fileId}/ingest-attempts` (`ingest:write`) starts an attempt (`201`). `GET /files/{fileId}/ingest-attempts`, `GET /ingest-attempts/{id}` (`ingest:read`), and `POST /ingest-attempts/{id}/cancel` (`ingest:write`, `204`) complete the API. States: `queued`, `inProcess`, `completed`, `failed`, `interrupted`. A file has at most one active attempt and one completed attempt (partial unique indexes). A file type that Docling cannot read returns `fileTypeNotIngestable`. A file has at most a fixed number of failed attempts.
- **Worker:** `IngestWorker` claims one attempt with `FOR UPDATE SKIP LOCKED` and a lease. The pipeline runs in this order: read the blob through the signed link, convert with Docling, embed the chunks, extract the draft with the agent, and store the result in one transaction. The final save runs under a row lock and checks that the attempt is still active, so a cancel, a file delete, or a machine change wins a race.
- **Docling:** `docling-serve` (`DOCLING_API_KEY`, GPU image in the Compose profile) converts files with hybrid chunking (`/v1/chunk/hybrid/file/async`), OCR (EasyOCR), and table structure. Insights polls the task. The page limit is `Ingest:MaxPages`. A document with a heading and no body text gives no chunk, and the attempt ends `noText`. `/health/ready` reports `Degraded` while Docling is down.
- **Gemini:** Vertex AI (`Gemini:*`). The embedding model `gemini-embedding-001` produces 1536 dimensions, normalized. The embedder sends one text per call, with a small parallel limit. The extraction agent (`ChatClientAgent` with the four `propose_*` tools, see **Extraction by function calls**) receives the chunk text and the machine signal catalog from Telemetry, and never an identity (company, file ID). A company or a target machine in the arguments of a tool is ignored. Provider calls retry transient failures (Polly).
- **Drafts:** the worker sends `insights.v1:DraftsProposed` through the outbox. Core and Telemetry both consume it. Core stores the machine drafts (`machine_drafts`) and sends `core.v1:MachineDraftApplied`, `core.v1:FileMachineMatched`, and `core.v1:DraftsResolved` (the machine check of each entry: accepted on a machine, accepted on a machine draft, or rejected). Core sends `core.v1:MachineDraftDismissed` when a user dismisses a machine draft. Telemetry stores the metric and status drafts and one proposal entry row for each entry. The entry state is `awaiting`, `onMachineDraft`, `onMachine`, `rejected`, or `machineDraftDismissed`. A metric or status draft whose entry is `awaiting` has the state `awaitingTarget`: it has no target yet and cannot be applied. `DraftsResolved` and `MachineDraftApplied` move its drafts to `pending` on the machine. A rejected entry and a dismissed machine draft soft-delete the drafts that wait for them.
- **Draft API (Core):** `/machine-drafts` and `/machines/{machineId}/drafts` (`drafts:read`), apply (`drafts:write` and `machines:write`), and `/drafts/{id}/dismiss` (`drafts:write`). A concurrent change returns `409` (`DraftChanged`, `MachineChanged`). A draft that is not pending returns `422` (`draftNotPending`).
- **Draft API (Telemetry):** `POST /machines/{machineId}/definition-drafts/operating-phases/{id}/apply` (`definition-drafts:write` and `operating-phases:write`; the body is the reviewed phase; one save creates the phase and marks the draft applied), `/definition-drafts/{id}/dismiss`, `/machines/{machineId}/definition-drafts` (search, dismiss all), `/ingest-attempts/{attemptId}/definition-drafts` (list, search, dismiss all), and `/definition-drafts/pending-counts` (`definition-drafts:read|write`). A metric apply or a status write carries the `draftId` and marks the draft applied in the same save. No `mark-applied` call exists. The mark checks that the draft is pending and belongs to the machine: a draft that is not pending returns `422` (`draftNotPending`), and a draft that does not exist, belongs to another machine or kind, or appears twice in one request returns `400`.
- **Draft paging:** every draft search is keyset paging, not offset paging: `KeysetGridRequest` (`Limit`, one sort column, a typed filter, `After`) and `KeysetGridResponse` (`Items`, `TotalCount`, `NextPosition`) in `Shared.Application/Grids`. The position holds the sort value and the ID. The state rank is `pending`, `awaitingTarget`, `applied`, `dismissed`. The web app has next and previous buttons, a page size select, and no page links.
- **File messages:** Document sends `document.v1:FileDeleted` and `document.v1:FileMachineChanged`, and Insights sends `insights.v1:IngestStateChanged` so Document shows the state of the file. A file delete interrupts the active attempt (`fileDeleted`).
- **Metric units:** Telemetry sends `telemetry.v1:MetricUnitsChanged`. Insights reads the unit list from Telemetry (`TelemetryClient`) and caches it in Redis with a single fetch.
- **Telemetry (observability):** the sources `HealthyFac.Insights.Ingest` and `HealthyFac.Insights.Ai` have the spans `Ingest.Process`, `Docling.Convert`, and `Ingest.Store`. The meter `HealthyFac.Insights.Ingest` counts attempts, pages, chunks, and drafts, and reports the backlog. No tag holds an ID or a file name.
- **Cases and coverage:** Insights consumes `telemetry.v1:SignalEpisodeChanged` and keeps its own copy in `machine_signals`. A machine has at most one open `maintenance_cases` row (partial unique index). The states are `open`, `resolved` (all episodes resolved), and `closed` (a person or an agent closed it, with a reason). An episode without an open case opens one; a new case takes over the open episodes that are not `dismissed`. Coverage of an episode: `new`, `watched`, `dismissed`, `drafted` (a committed `propose_work_order`, with the draft ID), and `linked` (a committed `link_work_order` or an applied draft, with the work order ID). An open episode or an escalation of an uncovered episode queues a run after `Agents:RunDebounceSeconds`. An escalation of a `dismissed` episode makes it `new` again. A run checks first that the case is open and has an uncovered open episode, else it ends `skipped` with no model call (reason `caseNotOpen` when the case is not open, `nothingToReview` when no open signal needs a review). Closing a case sets its uncovered episodes `dismissed`. API: `POST /cases/search` (filters: `states`, `machineIds`, `severities` of the highest open severity, and `isAiUnavailable` with the rule of the row field), `GET /cases/{id}` (the header and the outcome only: the latest committed action, else the AI unavailable state, else the verdict or `noDecision` of the last triage or planner run, with its final text), `POST /cases/{id}/signals/search` (open signals first, then the newest), `POST /cases/{id}/runs/search` (newest first, no tool calls), `GET /cases/{id}/runs/{runId}/tool-calls` (these three take `offset` and `limit` of the shared grid limits and `cases:read`), `POST /cases/{id}/runs` (run again), and `POST /cases/{id}/close` (`cases:read` and `cases:write`); a case that is not open returns `422`.
- **Agent roles:** `AgentWorker` claims queued runs with a lease and runs each one. `triage` (`Gemini:TriageModel`) returns a structured verdict (`dismiss`, `watch`, `escalate`) and has no tools: `dismiss` also closes the case when no open episode is `drafted` or `linked`, `watch` sets the episodes `watched`, and `escalate` starts the planner. `planner` (`Gemini:ChatModel`) has `search_manual`, `get_metric_history`, `get_signal_episodes`, `list_open_work_orders`, `propose_work_order`, `link_work_order`, and `close_case`. `extractor` uses the `propose_*` tools. `screener` (`Gemini:TriageModel`) classifies chunks in batches. Classifiers use structured output; actors use function calls (`FunctionInvokingChatClient`, with the iteration and error limits from the options). Prompts are embedded resources with a version; a run stores the version and the hash.
- **Scope layers:** (1) a fixed tool set per role; (2) each `AIFunction` closes over the case, so the company and the machine never come from the model; (3) each tool runs as the actor `insights:advisor` through `IRequestHandler<T>`, so the pre-handler checks and the tenant checks run; (4) each tool request has `[DownstreamScopes]`, and `list_open_work_orders` uses the scope `work-orders` (client scope `insights-work-orders`); (5) the Core consumer of a proposal checks the machine against the company, and a person applies the draft. Tool results hold no employee names. An architecture test checks the scopes and the role of each tool.
- **AI log and commit:** `agent_runs` (role, case or attempt, model, prompt version and hash, state `queued`, `running`, `completed`, `skipped`, `failed`, or `interrupted`, attempt number, lease, tokens, verdict, error code), `agent_tool_calls` (sequence, call ID, tool, arguments, outcome `succeeded`, `rejected`, or `failed`, result, duration), and `agent_actions` (kind, payload, state `buffered`, `committed`, or `discarded`, unique on run and call ID). A read tool runs at once and is logged at once. A write tool validates, answers the model, and buffers the action. `RunCommit` stores all buffered actions, their outbox messages, and the run state in one transaction. A failed or interrupted run commits no action. A running run renews its lease after each model call and tool call; a run whose lease expires becomes `interrupted` and gets no replacement. When an episode of the case changes during a run, the commit hits the row version, the run ends `failed` with `caseChanged` (a `Warning`), and a new triage run is queued when an uncovered open episode remains.
- **Provider failure:** a provider failure retries with `Agents:ProviderRetryDelaysSeconds` for each model call, not for the whole loop. After the last attempt the run ends `failed` with `providerUnavailable`. A case shows "AI unavailable" when its last run failed with `providerUnavailable` or `unexpectedError`, or was interrupted. The next episode change or "Run again" queues a new run.
- **Screening at ingest:** the pipeline order is convert, screen, embed, extract, store. The screener classifies the chunks in batches of `Insights:Screening:BatchSize` and stops at the first unsafe chunk. An unsafe chunk ends the attempt `failed` with `unsafeContent` and stores the location and the reason in `error_detail`. The extraction never runs, and the earlier ingested document of the same file and its chunks are removed in the same transaction. The `screener` run is stored in the same save as the attempt outcome, also after a later failure. A cancelled attempt stores no screener run. The ingest summary shows the translated description with the location and the reason.
- **Extraction by function calls:** the `extractor` role runs `AgentDraftExtractor` with four `[LocalTool]` requests: `propose_machine` (returns the `machineId`, the draft ID of the machine), `propose_metric` (with the limits and the behavior), `propose_status`, and `propose_operating_phase`. The other tools take the `machineId` that `propose_machine` returned. A phase names the metric of a condition or a limit row by key and a status by code: a key proposed in the same run becomes its draft ID, a key of an existing definition of the machine of the file becomes its definition ID, and any other key is rejected to the model. Each tool runs the validator of its request (the message validators of `Insights.Messaging`). An invalid call returns the errors to the model, which corrects that call; there is no repair turn. The proposals collect in an `ExtractionBuffer` (the machine file rule, the repeat rules, and the message count limits reject the call); `DraftProposalMapper` builds `DraftsProposed` from it, and the message goes into the outbox in the store transaction of the attempt. After `Insights:Agent:MaxConsecutiveErrors` failed calls in a row the loop ends and the attempt fails with `invalidExtraction`. The model loop stops at `Insights:Agent:ExtractorMaxIterations`. The temperature is 0, and the trace holds no prompt and no tool result. The `extractor` run and its tool calls are kept in memory and stored in the save of the attempt outcome (completed or failed), as the `screener` run is; a cancelled attempt stores none. An ID in the arguments and the results is an encrypted token (`AgentJson`, the shared ID encryption modifier), so the model never sees a raw GUID. The `propose_operating_phase` tool is the only way to propose a phase; a user applies the phase draft after its metric and status drafts.
- **Demo snapshot:** `backend/seed/demo/ingest` holds recorded real ingests of three demo documents (2 sets; see `backend/seed/demo/README.md`). The seed job loads them: the attempts, the chunks with their vectors, the `screener` and `extractor` runs with their tool calls (Insights), and the drafts that the completed attempts send through the relay (Core, Telemetry). A seed needs no Docling and no AI call.
- **Work order drafts:** the `planner` proposes through `insights.v1:WorkOrderDraftProposed`. Core stores `work_order_drafts` ("find, else create", after a check that the machine is an active machine of the company). Core API: `POST /work-order-drafts/search` and `GET /work-order-drafts/{id}` (`drafts:read`), `POST .../apply` (`drafts:write` and `work-orders:write`; one save creates the work order, marks the draft `applied`, and adds `core.v1:WorkOrderDraftApplied`), and `POST .../dismiss` (`drafts:write`; adds `core.v1:WorkOrderDraftDismissed`). A draft that is not pending returns `422`, and a changed draft returns `409`. The draft response holds `machineName`, also of a deleted machine. The Core machine lookup (`POST /machines/lookup`) takes optional `ids` (at most 100): it then returns those machines of the company, also deleted ones, and ignores the search and the page cap; the cases list reads the names of the loaded page through it. Insights moves the episodes of an applied draft from `drafted` to `linked` and sets the episodes of a dismissed draft `dismissed`.
- **Telemetry reads:** the planner reads the metric history and the episodes through the gRPC service `TelemetrySignals` (see **Telemetry**). Insights never writes to Telemetry, and no service reads another service's database.
- **Known limits:** the signed blob link uses the public host name. A heading-only scan gives `noText`. The Vertex embedding batch limit is not confirmed. The ingest has no retention job.

## Email

- A service sends email through `IEmailSender` (Shared.Application). The host picks the implementation with one registration method. `AddSmtpEmail` registers the SMTP sender (MailKit). A later provider adds its own `Add...Email` method.
- Development uses Mailpit. It catches all email, and its web UI shows the messages (`MAILPIT_UI_PORT`, default `8025`). Mailpit keeps the messages in the `mailpit-data` volume, and `docker compose down -v` removes them. `docker/config/core.json` holds the `Smtp` host, port, and security mode of Mailpit for Compose.
- Other deployments set the `Smtp` section (`Host`, `Port`, `Security`, `UserName`, `FromAddress`, `FromName`) in their settings file, and `Smtp__Password` as a secret.
- **Invite email:** Core consumes `core.v1:EmployeeInvited` and emails the invited person the link `{InviteLinks:SpaBaseUrl}/invite#token={token}`. The token is in the fragment, so no server log or proxy records it.
- **Rendering:** the email bodies are Razor components in the Web layer. `RazorComponentRenderer` (`Shared.Web/Rendering`) renders them with `HtmlRenderer`, outside an HTTP request. It is not email-specific: a later feature can reuse it for other output. The Application layer sees only `IEmployeeInviteEmailBuilder`. The text body is the HTML-decoded render of its own component.
- **Spans:** the `HealthyFac.Rendering` source writes `Razor.Render` for each rendered body. The `HealthyFac.Email` source writes `Email.Send` for each message. The MailKit source `MailKit.Net.SmtpClient` adds the SMTP steps under `Email.Send`. No span holds a recipient, a body, or a link.
- **Token at send time:** the handler builds the token from the current salt of the invite. The token never enters the database, the outbox, or a log. Two messages for one invite send two links that both work.
- **Skipped invites:** the handler sends nothing and completes when the invite is missing, accepted, or expired. A supervisor resends an expired invite.
- **Failures:** a sender failure makes the inbox retry the message. After `Messaging:InboxMaxAttemptCount` attempts, the inbox row gets `failed_on`. A crash after the send and before the commit sends the email again.

## Public Paths

- The public path has the form `/api/<service>/v{version}/...` (e.g., `/api/core/v1/machines`).
- A service routes under `/v{version}`, without `/api`. The gateway removes the whole `/api/<service>` prefix.
- The gateway sends `X-Forwarded-Prefix: /api/<service>`. A service accepts this header from trusted proxies only (`Proxy:KnownNetworks`). Its `PathBase` then becomes the public prefix, so every link that it builds (e.g., the `Location` header) shows the public path.
- **Logical names:** each public service has its own name, so a move to the cloud changes only the names and the scheme. The domain is `healthyfac.test` (`HEALTHYFAC_DOMAIN`). The `.test` top-level domain is reserved for tests (RFC 6761) and never resolves on the internet.

| Name | Serves | Cloud equivalent |
| --- | --- | --- |
| `https://api.healthyfac.test` | the gateway, Core API routes (`/api/core/v{n}/...`) | `https://api.<domain>` |
| `https://auth.healthyfac.test` | the gateway, Keycloak routes (`/realms/healthyfac/...`, `/resources/...`); the token issuer | `https://auth.<domain>` |
| `https://app.healthyfac.test` | the gateway, the SPA host route (all paths); in container mode the web app, invite links, redirect URIs, CORS origin | `https://app.<domain>` |
| `https://app.healthyfac.test:4200` | `ng serve` of the web app (development mode) | none |

- **TLS:** TLS ends at the gateway, as at a cloud load balancer or ingress.
    - The public URLs use HTTPS and no port. `GATEWAY_PORT` is 443; when it is not, add the port to `HEALTHYFAC_AUTH_URL`, because the issuer must equal the URL that the browser uses.
    - The gateway publishes HTTPS only. Plain HTTP on the public port gets no HTTP response.
    - Internal traffic stays HTTP: gateway to Core, gateway to Keycloak, the health ports, and the Keycloak admin console on `localhost`. The gateway sets `X-Forwarded-Proto: https`, and Core and Keycloak (`KC_PROXY_HEADERS: xforwarded`) read it.
    - A local certificate authority (mkcert) signs the certificate. The files are `docker/certs/healthyfac.test.pem` and `docker/certs/healthyfac.test-key.pem`. Git ignores them, and no image holds them. Compose mounts the folder read-only into the gateway. See `docker/certs/README.md`.
    - The launch profile `https` of the gateway serves `https://localhost:5001` with the same files. With the hosts file, a browser reaches `https://api.healthyfac.test:5001`.

- **Host routing:** each gateway route has a YARP `Match.Hosts` entry with its name. A host without a port matches every port. A request to another name matches no route: `401` without a token, `404` with a token. The names are set per environment (`appsettings.Development.json`, Compose); `appsettings.json` holds none.
- **Development tools** stay on `localhost`: the Keycloak admin console (`KEYCLOAK_PORT`, set by `KC_HOSTNAME_ADMIN`), Mailpit, Grafana, the RabbitMQ console, the database, and the health ports.
- **Auth paths:** the route `/api/auth/v{n}/...` serves the Auth API for `api.<domain>`. It needs a signed-in user and calls the web app with the policy `HealthyFacDefault`.
- **Document paths:** the routes `/api/document/v{n}/...` serve the Document API for `api.<domain>`. The route `/api/document/blobs/...` serves the file links without a token (see **Document**).
- **Hosts file:** map the three names to the local machine, as an administrator (`C:\Windows\System32\drivers\etc\hosts` on Windows):

```text
127.0.0.1 api.healthyfac.test auth.healthyfac.test app.healthyfac.test
```

- **CORS at the gateway only:** the gateway answers the cross-origin requests of browsers (`AddSharedCors`, `UseSharedCors`).
    - Each route that the web app calls (`core`, `core-invite-verify`, `core-invite-accept`) names the policy with `"CorsPolicy": "HealthyFacDefault"`.
    - The CORS middleware runs before authentication. A preflight (`OPTIONS`, no `Authorization` header) gets `204`. It never meets authentication, the revocation check, the rate limiter, or authorization.
    - `Cors:PreflightMaxAgeSeconds` (600) lets the browser cache the answer. Browsers ignore a value above 7200.
    - A service behind the gateway keeps `Cors:IsEnabled = false`. Two layers that write `Access-Control-Allow-Origin` make the browser reject the response.
    - Keycloak answers CORS for its own routes from the `webOrigins` of each client. The gateway adds no CORS headers there.
    - The allowed origins have no default. Each environment sets `Cors:AllowedOrigins` (Compose: `HEALTHYFAC_SPA_URL`).
- **Versioned paths only:** the `core` route matches `/api/core/v{n}/...` only. Paths such as `/api/core/hc`, `/api/core/health/ready`, and `/api/core/openapi/...` match no route, so the gateway makes no call to Core. It answers `401` without a token and `404` with a token.

## Health Endpoints

- Each service serves `/health` (liveness), `/health/ready` (readiness), and `/hc` (every check, with exception texts) on one internal health port.
    - The setting is `HealthEndpoints:Port`. The containers use `8090`. The API port does not serve these paths.
- `UseSharedHealthChecks()` is the first middleware. It compares the local port of the connection, which a client cannot change. It never reads the `Host` header.
- Health requests skip HTTPS redirect, request logging, CORS, authentication, revocation, rate limiting, and authorization.
- Compose publishes the health ports on `127.0.0.1` only (`CORE_HEALTH_PORT`, `GATEWAY_HEALTH_PORT`). No gateway route reaches them. In the cloud, the platform probes use the health port, and no public load balancer routes it.
- The gateway active health check of Core calls the `Health` address of the destination (the health port of Core), with the path `/health/ready`.

## Gateway Composition

A temporary exception to "the gateway only routes": until a backend for the frontend (BFF) exists, the gateway composes the answers that need Core and Telemetry together. It is not a new service.

- **Composed URLs:** `POST /api/core/v1/machines/{machineId}/drafts/search`, `POST /api/core/v1/ingest-attempts/{attemptId}/drafts/search`, `GET /api/core/v1/ingest-attempts/{attemptId}/drafts`, `POST .../drafts/dismiss` of a machine and of an attempt, and `POST /api/core/v1/machines/search`. They keep the Core URLs, so the web app does not change its base. A more specific route beats the YARP catch-all.
- **Calls:** the composer resolves the addresses of the YARP clusters `core` and `telemetry` (`IProxyStateLookup`). It forwards only the `Authorization` header, never retries, and never logs a body. One composed request makes at most one call to each source, in parallel. A page never makes a call for each row (no N+1).
- **Search merge:** each source returns its rows in the sort order. The composer merges them with the same order, with the Core row first on a tie. The composed position holds the position of each source and a finished flag for each. The filter split sends each kind to its own source (`machine` to Core, `metric` and `status` to Telemetry). It sends the 3 shared states (`pending`, `applied`, `dismissed`) to both sources and `awaitingTarget` to Telemetry only. A source whose kind set or state set the split empties is skipped.
- **Failures:** a source that is unavailable gives `503`. Two `400` answers merge into one validation problem. Other `4xx` answers follow the order `401`, `403`, `404`, `409`, `400`.
- **Data ownership:** the composition reads the data of both services through their public endpoints. It never reads a database. The machine search adds the pending draft count of Telemetry to each machine. The draft rows of Telemetry get the machine name from the Core name lookup (`/machines/names`).

## Gateway Failure Policy

- Redis is not a hard dependency of the gateway. When Redis fails, rate limiting falls back to a local limiter per instance. With N instances, the effective limit can reach N times the configured limit during an outage.
- A circuit breaker skips Redis for 30 seconds when at least half of at least 2 calls in 30 seconds fail. Then one request tests Redis, and the others keep the local limiter until the test succeeds. Polly logs the breaker events with its default levels: opened at `Error`, half-opened at `Warning`, and closed at `Information`. During a long outage, each failed test logs one `Error` and one `Warning` every 30 seconds.
- `/health/ready` reports `Degraded` with status `200` while Redis is down. The gateway readiness does not check the services behind it.
- Every error response of the gateway is `application/problem+json`: `429` (rate limit), `502` (destination unreachable or broken response), `503` (no healthy destination), `504` (destination timeout), and `500` (gateway exception, without details). A client cancellation gets no body.
- The gateway never retries a request. A `POST` request is not idempotent, so the client decides on a retry.
- The revocation check passes a request when Redis fails, and the same circuit breaker protects it.
- The gateway skips a destination that the health checks mark unhealthy. It does not fall back to all destinations.

## Realtime

The web app gets live changes over one SignalR connection. A notification is never stored: a lost push is accepted.

- **Hub:** the gateway hosts the one hub, `RealtimeHub`, at `/api/realtime/v1/hub`. This is the second exception to "the gateway only routes", next to the composed URLs (**Gateway Composition**). The mapped endpoint beats the YARP catch-all.
- **Pushers:** Core, Insights, and Telemetry push through `IHubContext<RealtimeHub, IRealtimeClient>`. They register SignalR with the same Redis backplane (on the shared Redis multiplexer) and map no hub. Every gateway instance delivers to its own sockets. The hub uses the JSON protocol only, with the shared JSON options.
- **Transport:** WebSockets only, without negotiate. One HTTP upgrade request makes one connection, so no sticky session is needed.
- **Connect:** the browser sends the token as the `access_token` query parameter. The gateway reads it from the query only on the hub path. The connect passes the edge JWT check, the token revocation check, and the default rate limit for each user. A connect from an origin outside `Cors:AllowedOrigins` gets `403`. The check is `WebSocketOptions.AllowedOrigins`, bound to `Cors:AllowedOrigins`, because CORS does not cover a WebSocket handshake. A connect without an `Origin` header passes, because a client that is not a browser can send any value. The gateway closes the connection when the token expires (`CloseOnAuthenticationExpiration`). A permission change reaches the socket at the next token expiry.
- **Redaction:** no log entry, span, or span tag holds the `access_token` value.
- **Use case groups:** the user ID of a connection is `sub`. At the connect, the hub adds the connection to the group of each notification kind and each hint topic whose permission the token holds. `RealtimeAudiences` (Shared.Application) maps each group kind and each topic to exactly one permission. A user-targeted kind has no entry. A new kind needs one map line.

| Group | Name | Permission |
| --- | --- | --- |
| Kind `workOrderBlocked` | `company:{id}:kind:workOrderBlocked` | `work-orders:write-company` |
| Kind `workOrderDraftCreated` | `company:{id}:kind:workOrderDraftCreated` | `drafts:read` |
| Kind `provisioningFailed` | `company:{id}:kind:provisioningFailed` | `employees:manage` |
| Kind `maintenanceCaseOpened` | `company:{id}:kind:maintenanceCaseOpened` | `cases:read` |
| Topic `workOrders` | `company:{id}:topic:workOrders` | `work-orders:read` |
| Topic `schedule` | `company:{id}:topic:schedule` | `shifts:read` |
| Topic `machines` | `company:{id}:topic:machines` | `machines:read` |
| Topic `cases` | `company:{id}:topic:cases` | `cases:read` |
| Topic `definitionDrafts` | `company:{id}:topic:definitionDrafts` | `definition-drafts:read` |

- **Own action:** the user who made a change gets no entry for it. For a user target, the sender skips the push when the recipient is the actor. For a group target, the notification carries `actorSubject`, and the web app drops an entry with its own `sub`. Hints go to every tab, also the tabs of the actor. Each `AddToUser` and `AddToGroup` call names the rule with the required argument `isActorSkipped`: `true` for a direct action of the actor inside a request, `false` for a result that no user saw at that time (a worker end, an inbox handler, a side effect of the action). With `false`, the actor gets the user push, and a group notification has no `actorSubject`.
- **Push after the commit:** a use case adds its events to the scoped `IRealtimeNotifier` after `SaveChangesAsync` or `RunInTransactionAsync` returned, never inside the operation. The execution strategy repeats the operation, so a push inside it could send twice. An HTTP use case or a worker then calls `Push()`. An inbox handler only adds events. The inbox runner knows no real-time code: it calls the registered `IInboxUnitObserver` instances at the start of each attempt and after the commit. The real-time observer clears the events at the start of each attempt and pushes them after the commit, so a rolled-back or repeated attempt pushes nothing twice.
- **Background queue:** `Push()` is synchronous and only enqueues a `RealtimePush` into a typed background queue. The queue owns an unbounded channel, one handler for each item type, a new DI scope for each item, and the drain at stop. The handler sends through one Polly pipeline: 3 retries (200 ms, exponential, with jitter), then the shared Redis circuit breaker. While the breaker is open, an item drops at once. After the last retry, an item drops with one `Warning`. A use case never fails because of a push. At a stop, the sender drains until the host stop token fires, then drops the rest.
- **Observability:** the meter `HealthyFac.Realtime` counts the pushes (tags: target and result) and records the push duration. The meter `HealthyFac.BackgroundQueues` has a length gauge for each item type. The span `Realtime.Push` covers one push. No tag, span, or log entry holds a user ID, a token, or a notification text.
- **Redis down:** no push reaches a client. The gateway closes a new hub connection with an error, and the web app connects again with its reconnect delays. The readiness of the gateway reports `Degraded` with status `200`.

## Identity

- Keycloak is the identity provider. The SPA signs in with the Authorization Code flow and PKCE.
- Each company is a Keycloak organization. The organization alias is `Company.Id`, so Keycloak holds no other company data.
- The access token carries `sub` (the Keycloak user ID), the permissions, the `organization` claim (the company ID), and `employee_id`. The ID token for the web app carries `permissions` only. The API encrypts every ID in its JSON, so the web app takes the company data from `GET /company`, never from the token.
- The roles `worker` and `supervisor` group the permissions. API policies check permissions, never role names.
- **Realm as code:** one file holds the realm. The two test files (`healthyfac-test-bootstrap.json` and `healthyfac-test-tenant.json`) live in `backend/tests/HealthyFac.Testing/Keycloak` and serve the integration tests only; the stack imports no realm and creates no user. `docker/keycloak/realm/healthyfac-realm.json` holds the realm settings, the user profile, the clients, the client scopes, and the roles. The `keycloak-config` job (`keycloak-config-cli`) applies it after each start and changes only the differences, so a change needs no reset. The job keeps the users, organization members, and role mappings that Auth creates (`IMPORT_MANAGED_ORGANIZATION=no-delete`, `IMPORT_USERS_MERGEROLES=true`). All files use the placeholder `${NAME}` for environment variables; the job reads it through `IMPORT_VARSUBSTITUTION_PREFIX`, `_SUFFIX`, and `_UNDEFINEDISERROR=false`, and leaves the Keycloak message placeholders (`${username}`) unchanged. Because of that, the job does not stop on a missing variable; Compose checks the variables, and the test container class rejects blank values. After a change, run `docker compose up keycloak-config`. The integration tests run the same image. Production applies only `realm/healthyfac-realm.json` with the job; production provisioning of organizations and users is not decided. Edit the user profile in `docker/keycloak/user-profile.json` only, then run `docker/keycloak/embed-user-profile.sh`, which embeds it into the realm file as the string that Keycloak expects; the test `UserProfile_InRealmFile_EqualsSourceFile` fails when the two differ.
- **Refresh tokens:** the realm rotates refresh tokens (`revokeRefreshToken: true`, `refreshTokenMaxReuse: 0`). Each refresh invalidates the used token, and a second use of it fails. `healthyfac-spa` sets `post.logout.redirect.uris` to `{HEALTHYFAC_SPA_URL}/*`, so the logout redirects back to the web app.
- **Clients:** `healthyfac-spa` (public, Authorization Code with PKCE), `healthyfac-core`, `healthyfac-telemetry`, and `healthyfac-document`, and `healthyfac-insights` (confidential, each holds the permission roles of its API), and `healthyfac-auth` (service account for the Auth service). The client has the scope `service_account` explicitly, because the realm import does not add it. A service token carries `client_id` (it identifies the calling service) and no `clientHost` or `clientAddress`, so it holds no host name or IP address of the caller.
- **Permissions:** client roles of `healthyfac-core` for employees and machines: `employees:invite`, `employees:manage`, `machines:read`, `machines:write`, and `machines:delete` (the work order and shift permissions follow below). The client holds permissions only. The job role `supervisor` holds these five, and `worker` holds the three machine permissions. Both are realm roles, composites of those client roles, so a job role can later also hold permissions of other APIs. The mapper `healthyfac-core-permissions` of the scope `healthyfac-claims` writes the effective client roles of `healthyfac-core` into the flat claim `permissions`. The JWT handler splits the array into one `permissions` claim per value, and the endpoint policies check that claim. The name of a policy is the name of the permission. The token has no `resource_access` and no `realm_access`.
- **Document permissions:** client roles of `healthyfac-document`: `files:read`, `files:write`, `files:delete`, `company-files:write`, and `company-files:delete`. The roles `supervisor` and `worker` hold all five. The mapper `healthyfac-document-permissions` adds them to the claim `permissions`, and the mapper `healthyfac-document-audience` adds `healthyfac-document` to `aud`.
- **Work order and shift permissions:** client roles of `healthyfac-core`: `employees:read`, `work-orders:read`, `work-orders:write`, `work-orders:read-company`, `work-orders:write-company`, `shifts:read`, `shifts:read-company`, and `shifts:write-company`. The role `supervisor` holds all of them. The role `worker` holds `work-orders:read`, `work-orders:write`, and `shifts:read`. The permissions `work-orders:read`, `work-orders:read-company`, `work-orders:write`, `work-orders:write-company`, `shifts:read`, `shifts:read-company`, and `shifts:write-company` cover the 7 cases. The read-company permissions give the company scope to a read, the write-company permissions give it to a write; without them a request has the own scope (see **Work Orders**).
- **Languages and locale:** the web app and the login pages offer English (`en`) and Ukrainian (`uk`). The realm sets `internationalizationEnabled`, `supportedLocales`, and the default `en`. The user attribute `locale` holds the choice, and the mapper `locale` writes it into the tokens as the claim `locale`. `PUT /api/auth/v1/me/locale` with `{ "locale": "en" | "uk" }` sets the attribute of the signed-in user through the Admin API (`204`; another value `400`; Keycloak down `503`). It needs no permission. The tokens of the web app carry the audience `healthyfac-auth`.
- **Login theme:** the login pages use the Keycloakify theme `healthyfac` (project `keycloak-theme/`), built into the Keycloak image (`docker/keycloak/Dockerfile`). The pages follow the language of the user (`locale`, or the `kc_locale` parameter that the web app sends).
- **Token validation:** every service validates the JWT itself (`AddSharedJwtAuthentication`). The issuer is the public URL of the realm (the gateway). The service reads the keys from the internal Keycloak address (`Jwt:MetadataAddress`), which works because of `KC_HOSTNAME_BACKCHANNEL_DYNAMIC`. A token needs `healthyfac-core` in `aud`. The service reads the permissions from the `permissions` claim and needs no claims transformation. The access token lives 300 seconds.
- **Core endpoints:** a fallback policy requires a signed-in user. Invite create and resend need `employees:invite`, retry provisioning and deactivate need `employees:manage`, and the machine endpoints need the machine permissions (see **Machines**). Verify, accept, and OpenAPI (Development only) are anonymous. The health endpoints are on the health port (see **Health Endpoints**). The company of a request comes from the token only: a Web request record has no `CompanyId`.
- **Gateway:** the gateway validates the token, checks the revocation list, and then applies the rate limit. It routes `/realms/healthyfac/*` and `/resources/*` to Keycloak. The Keycloak routes answer only `auth.<domain>`, and the Core routes answer only `api.<domain>`. No route reaches `/admin`. The `core` route needs a signed-in user, and the default rate limit counts for each user (`sub`). A fallback policy (`SetAuthenticatedFallbackPolicy`) requires a signed-in user for a route without `AuthorizationPolicy` and for a request that matches no route. Public routes name the `anonymous` policy.
- **Revocation:** the key `revoked:{sub}` holds the revocation time in Unix seconds. The gateway answers `401` when `iat` is earlier. A missing entry passes. Redis failures follow the **Gateway Failure Policy**: the request passes, and the circuit breaker logs a warning.
- **Provisioning:** Auth consumes `core.v1:EmployeeAccepted`, finds the Keycloak organization of the company, finds or creates the user by `employee_id`, adds the user to the organization, maps the realm role, and emails a set-password link while the user has no password. It publishes `auth.v1:IdentityProvisioned`, or `auth.v1:IdentityProvisioningFailed` with the reason `OrganizationNotFound`, `EmailAlreadyRegistered`, or `RoleNotFound`. Auth never creates an organization. A supervisor retries a stuck provisioning with `POST /employees/retry-provisioning`.
- **Employee lookup:** `POST /employees/lookup` (`employees:read`) takes `{ search? }` and answers at most 50 `{ id, displayName }` options (the first and the last name) of the active employees of the company, sorted by name. Pickers and filters read it instead of the employee search, so a page carries no more than an ID and a name.
- **Deactivation:** `POST /employees/deactivate` deactivates the employee and sends `core.v1:EmployeeDeactivated`. Auth disables the Keycloak user, ends the sessions, and then writes the revocation entry with the current time. No token can be issued after the disable, so the entry rejects every access token of the user. A failure of Keycloak or Redis retries through the inbox. An identity that Auth creates for a deactivated employee is revoked at once through a second `EmployeeDeactivated`.
- **Demo Seed:** the Compose job `seeder` (`backend/src/Tools/HealthyFac.Seeder`) seeds a demo company before the 5 services start; each service waits for it with `service_completed_successfully`. The data lives in `backend/seed/demo` (see its README).
    - **Run:** the job builds one host for each of Core, Telemetry, Document, Insights, and Auth from their own `AddApplicationServices` and `AddInfrastructureServices`, and calls their database initializers. A use case runs first wherever one fits (people and invites, uploads, machines, work orders, the draft apply). The domain is the fallback where no use case fits: the company, the first invite, the Insights ingest results, and the case with its signal. The outbox messages of a step go through `IOutbox` in the same save.
    - **Clock:** a `SeedClock` replaces the `TimeProvider` of the hosts. Each file states its moments relative to the start (`d-14 10:30`, `wd-2 13:00`, `h-4`). The clock enters an event moment, then adds 1 microsecond for each read and never goes back. Every event lies in the past.
    - **Relay:** an in-memory relay replaces the broker. It reads the outbox rows in FIFO order, writes the inbox row of each service that handles the message, runs the handler, marks the row published, and drains until no row is open. The relay runs after each event, so a later event sees the stored result of an earlier one.
    - **Check:** before any write, the job checks every file: the moments, the time order, the keys (an event uses only keys that an earlier event created), the request validators of the owning services, and the password rule of the realm. A failure names the file, the item, and the rule, and the job writes nothing.
    - **State:** the seed is complete when Core holds the machine draft of the last entry of ingest set 2 (the marker; no event may come after it). A run on an empty database seeds. A run on a complete seed prints "The demo seed is complete." and changes nothing. A run on an incomplete seed exits with code 1 and prints the reset command.
    - **Reset:** `docker compose stop core telemetry document insights auth`, then `docker compose run --rm seeder --reset`. The job refuses while a client session of another process uses one of the 5 databases. It deletes the mode-2 marker message, then the marker draft, then the Keycloak organization with its members, then every blob of the Document container, then runs one `TRUNCATE ... RESTART IDENTITY` for each database in one transaction (no `CASCADE`). The keep list holds the required data: the Core roles and the Telemetry quantity kinds and units. The normal job then seeds again with the dates of the new day.
    - **Modes:** mode 1 is the job without an argument. Mode 2 is `--telemetry`: mode 1, then the telemetry history of 48 hours for the 3 machines (`backend/seed/demo/telemetry.json`). `--reset --telemetry` seeds mode 2 again.
    - **History steps:** the job simulates each machine with the scenario library and runs the history in steps. Each step writes the samples of all machines, then runs `FleetSilence` and `EvaluateMachine` as the evaluator actor on the seed clock. The episodes and the Insights cases are real, and the relay moves them like a live run.
    - **Bulk write:** `ReadingRowWriter` writes the 4 reading tables with the Npgsql binary import, one transaction per step, with names and types from the EF model. `AcceptedMessageReadings` is the intake mapping that the live handler and the job share, so a seeded row equals a live row.
    - **Drain work orders:** a drain of `telemetry.json` may name a `workOrder`. The job then seeds a Core work order through the use cases of `work-orders.json` (a derived part with the item names of `telemetry.json`): created and assigned by the supervisor, assigned to the person of the maintenance, `inProgress` at the maintenance start, `completed` at its end. The planned start is the maintenance start when it fits one work block of the assignee and overlaps no other work order of his (`DrainPlannedStart` reads the blocks through the Core shift resolution; the busy slots are the stored orders of the assignee and the assigned orders of `work-orders.json`), else the earliest fitting grid moment after it (the search starts at the maintenance start and never goes before the assignment). 1 minute before the maintenance start the job writes the planner result without AI (`DrainCaseLink`): 1 completed `planner` run, 1 committed `linkWorkOrder` action, 1 succeeded `link_work_order` tool call, and the coverage `linked` on the open signals of the case, in one save, as `RunCommit` does. The case outcome then reads `linkedWorkOrder`.
    - **Mode-2 marker:** the anchor sample of the last machine is stored with the fixed message ID `markerMessageId`. Run states: empty data seeds in both modes (exit 0). A seed without the mode-2 marker (a mode-1 seed, or a mode-2 run that stopped inside the history) reads as complete in mode 1 (exit 0); mode 2 prints that the seed has no complete telemetry history, names `--reset --telemetry`, and exits 1. With both markers, both modes print "The demo seed is complete." and exit 0. A company without the mode-1 marker exits 1 in both modes with the reset command of the mode. No resume exists.
    - **Explicit tests:** every test of the seeder unit and integration projects is `Explicit`, so the backend full run skips them. An architecture test enforces it. Run them with `--explicit only`.
    - **Accounts:** the job creates the Keycloak organization of the company and the users with the shared password of `company.json`. Auth provisions the invited people through its own use case after the accept. The realm stays with `keycloak-config`. `scripts/verify-stack.ps1` prints the sign-in of the supervisor and the worker from `company.json`.
- Today, maintenance workers and supervisors sign in. Sign-in for other users (e.g., a platform operator outside every company) is not decided.

- **Insights permissions:** client roles of `healthyfac-insights`: `ingest:read`, `ingest:write`, `cases:read`, and `cases:write`. Core adds `drafts:read` and `drafts:write`. Telemetry adds `definition-drafts:read`, `definition-drafts:write`, `operating-phases:read`, `operating-phases:write`, and `signals:read` (the last one for the Insights service account). The mappers `healthyfac-insights-permissions` and `healthyfac-insights-audience` add them to the token. The client scopes `insights-files`, `insights-telemetry`, and `insights-work-orders` are the downstream scopes of the Insights service token. `insights-work-orders` has the audience `healthyfac-core` and the role `work-orders:read`.

## Text Input

- **Normalize:** the shared JSON options of the API and the messages (`TextInputJson`, Shared.Infrastructure) turn `\r\n` and `\r` into `\n`, trim each string on read, and apply Unicode NFC. Query and route strings hold only IDs today; the first search filter adds a binder.
- **Reject:** each validator gives every string member `SingleLineText()` or `MultilineText()` (`TextInputRuleExtensions`, Shared.Application). The rule rejects the null character in every field and control characters in single-line fields (tabs and line breaks pass in multi-line fields). HTTP returns `400`. A message fails at the first attempt. The error key is the JSON name of the field (camelCase), and the error never holds the value. An architecture test checks that no string is left without a rule. No layer removes a character silently.
- **Field semantics:** `EmailAddresses.Normalize` (Shared.Domain) trims and lower-cases every email in requests, messages, and entities. Keycloak stores emails in lower case too.
- **Form fields:** a multipart form skips the JSON options, so the upload endpoints of Document apply the same policy (`TextInputPolicy.Normalize`) to the description, the file name, and the declared media type. API tests check it.
- **Output:** Razor and the web app encode HTML on output. No layer sanitizes HTML on input. The HTML fields are the machine, status, and metric descriptions, and they may hold images of Document: a rich text policy rejects what is outside the allow-list (see **Machines**), and the web app shows it through the Angular sanitizer.
- **Null character in messages:** PostgreSQL `jsonb` rejects `\u0000`, so such a message never reaches the inbox table. The inbox insert fails, and Rebus moves the message to the error queue after its retries.

## Observability

- **Resource attributes:** traces, metrics, and logs carry the same resource from one function (`TelemetryResource`): `service.namespace=healthyfac`, `service.name` from `Service:Name` (`core`, `auth`, `gateway`), `service.version` (the informational version of the application assembly), `deployment.environment.name` (the host environment in lower case), and one `service.instance.id` per process. `OTEL_SERVICE_NAME` and `OTEL_RESOURCE_ATTRIBUTES` override these values. The deployment or the collector adds platform attributes (`k8s.*`, `host.*`).
- **Metrics:** each service exports OTLP metrics to the trace endpoint (`Metrics:Endpoint`). The meters are `HealthyFac.Messaging`, `System.Runtime`, the built-in ASP.NET Core and `HttpClient` meters, and `Npgsql` in the services with a database (`Metrics:AdditionalMeters`). The health probes answer on the health port, so a dashboard separates them from API traffic by `server.port`.
- **Messaging metrics:** the counters `healthyfac.messaging.published`, `handled`, `retried`, and `failed` (tag `healthyfac.messaging.failure`: `permanent` or `attempt_limit`), and the histograms `healthyfac.messaging.run.duration` and `healthyfac.messaging.handle.duration` (seconds). The tags are the processor (`outbox`, `inbox`), the message type, and the outcome, never a message ID. A cancellation records no failure.
- **Backlog gauges:** a sampler reads the pending count and the oldest pending time of both tables every 15 seconds, with one query per table on the pending index and without a trace. The gauges `healthyfac.messaging.pending` and `healthyfac.messaging.oldest_pending.age` report the last sample, so the export never queries the database. A failed inbox row is not pending. Every instance reports the same table values, so a dashboard aggregates them with `max`, never `sum`.
- **Span names:** an internal span is `<Area>.<Action>` in PascalCase (`Razor.Render`, `UseCase.Validate`). The use case span keeps the request type name, and the tag `healthyfac.use_case` holds the same name. HTTP and messaging spans keep the library names. No span name holds an ID or a user value. The rule `observability` lists the naming conventions.
- **Layer boundary:** Domain, Application, and Infrastructure create spans and metrics only through the .NET API (`ActivitySource`, `Meter`). Only `HealthyFac.Shared.Web` references OpenTelemetry packages, so the host decides where telemetry goes. The architecture tests forbid the `OpenTelemetry` namespace in the inner layers.

- **Stack:** Angular 22.2 (zoneless), PrimeNG 22 with the Lara preset, Tailwind 4, ngx-translate 18, NgRx SignalStore 22, and `temporal-polyfill`.
- **Folders:** `src/app/` holds the app root and `layout/`. `shared/` groups code by intent (`storage/`, `i18n/`, `theme/`, `time/`). Each feature has its own folder under `app/` and one folder per use case. Aliases: `@app/`, `@shared/`, and `@<feature>/`.
- **State scopes:** a global store uses `providedIn: 'root'` and lives in `shared/`. A feature store is a provider on the lazy route. A local store is a provider on the component. Stores save to storage only through `withStorageSync` and `BROWSER_STORAGE`.
- **Theme:** one preset defines the colors. PrimeNG and Tailwind read the same tokens. The class `app-dark` on `<html>` switches both libraries.
- **Time:** all date and time values use Temporal. Code reads the current time only through the `CLOCK` token. Its zone is the company zone. `Date` appears only in the picker wrappers, because PrimeNG needs it.
- **Forms:** all forms use Signal Forms. A form validates with a `zod/mini` schema through `validateStandardSchema`. A wrapper component adapts each PrimeNG date picker to a Temporal value.
- **Text:** ngx-translate loads `public/i18n/<language>.json`. English is the fallback. The keys use capitalized snake case.
- **Runtime config:** the app reads `/config.json` before it starts. `parseAppConfig` validates it with one `zod/mini` schema (`appConfigSchema`) and derives the `AppConfig` type from it. The SPA host is the only source of the file, in every run mode. The file is public and holds only values that every visitor may see. The host caches it for `Spa:RuntimeConfigCacheSeconds` (default 300 seconds), so a configuration change reaches open browsers within that time. A wrong file stops the start with a plain text message. A production build shows only a generic text; a development build names the problem.

- **Authentication:** `keycloak-js` runs in `AuthStore` (`shared/security/`). The tokens live only in memory. A silent SSO check runs at start (`silent-check-sso.html`, which the host serves with its own CSP). `authGuard` protects each route. The policy allows the identity provider origin in `connect-src` and `frame-src` (the silent SSO iframe). It also allows the WebSocket origin of the API in `connect-src`, for the realtime hub. The policy allows the API origin in `img-src`, because the images of a rich text load from the file links of the gateway. The policy allows `style-src-attr 'unsafe-inline'`, because PrimeNG sets inline `style` attributes. The host serves `index.html` only through its endpoint. Hashed files cache for a year.

## Shared Infrastructure

- **Redis:** the token revocation list, the gateway rate limiter counters, and the distributed cache. A service caches data only in Redis, through the shared connection, and keeps no copy in process memory (no FusionCache, no `HybridCache`, no `IMemoryCache`, no `IDistributedCache`), so every instance reads the same value. No service caches data yet. Redis also holds the service tokens and the exchanged tokens of each service, without encryption (an accepted risk), with a time to live of the token lifetime, and the short locks that give one token fetch across the instances. No instance keeps a token in process memory. While Redis is down, every outgoing call fetches its own token from Keycloak (an accepted risk), and the Redis circuit breaker makes each Redis call fail fast. Every Redis call goes through one Polly circuit breaker (from `Microsoft.Extensions.Resilience`); the service reports `Degraded` while it is open, and only the calls that guard copies or load fall back. Redis must stay on a private network with authentication. Redis holds no source data.
- **Azurite:** blob storage for the Document service in development and in tests. It runs the blob service only, with `--skipApiVersionCheck`, because the default service version of the Azure SDK is newer than the newest version of Azurite. The image runs as root, because a non-root user cannot write the data volume. The gateway forwards the file links to it over HTTP, so a link allows HTTP in Development.

## Persistence

- **Retry:** All 5 services use `EnableRetryOnFailure` (at most 5 retries, at most 10 seconds between them). The strategy retries each query and each save on its own. Inside a `RunInTransactionAsync` block, the outermost block retries the whole unit. When the commit result is unknown, the retry resends the unit. The client-generated GUID keys and the row versions make a resend after a successful commit fail, so no row is written twice.
- **Transactions:** `RunInTransactionAsync` calls one shared runner. A nested call joins the open transaction. Only the runner begins a transaction (architecture test). A save with a soft delete cascade runs in a transaction of the runner.
- **Inbox handlers:** They run inside the inbox transaction and never open one. They protect a race with a row lock, a unique index, or a row version (architecture test).
- **Aggregate relations:** a single value of a root is a complex property or `OwnsOne`, never `OwnsMany`. A collection of a root is a child entity with `Cascade`: a soft delete of the root soft-deletes the children through the interceptor, loaded or not. Another aggregate is a reference without a collection navigation, with `Restrict`. The Core cascaded collections are the machine state history, the work order files and history, and the shift override and template blocks. A model test of each service checks the rule.
- **Data drop:** a soft delete is an `UPDATE`, so the database cascade acts only on a real `DELETE` of a root, which removes its children. A `DELETE` of a principal that another aggregate references fails on the foreign key.

## Settings

- **Split:** a setting lives where its value is decided. `appsettings.json` holds a value that is the same in every environment. `appsettings.Development.json` holds the values of a run on the host. `docker/config/<service>.json` holds the fixed values of the Compose network that are no secrets; Compose mounts it as `/app/appsettings.Deployment.json`. Environment variables hold the secrets, the values of the machine, and the values that Compose builds from `.env` (`docker/config/README.md`).
- **Priority:** `appsettings.json`, then `appsettings.<Environment>.json`, then `appsettings.Deployment.json`, then the environment variables. `AddDeploymentSettingsFile` (Shared.Web) inserts the file before the first environment variable source. The file is optional, so a run on the host and a test load none.
- **Other deployments:** a cloud environment mounts its own `appsettings.Deployment.json`, or sets environment variables, and takes its secrets from its secret store. The target is not chosen yet.
