# HealthyFac Architecture

This document records the service boundaries and the decisions that connect the services. Read `README.md` for the product domain.

## Services

| Service | Owns | Status |
| --- | --- | --- |
| **Gateway** (YARP) | The only public entry point. Routing, TLS, rate limiting, the edge JWT check, and the token revocation check. | Exists |
| **Auth** | A thin back channel to Keycloak: user provisioning, organization membership, and role assignment through the Keycloak Admin API. It does not log users in or handle passwords. It may have its own tables when it needs them. | Exists |
| **SPA host** | A small .NET host that serves the built web app, the runtime `/config.json`, and the index file with a content security policy nonce. It has no database and no authentication. | Exists |
| **Core** | Business data: companies, departments, employees, employee invites, roles, machines (with the gateway ID and the state history), and campaigns. | Exists |
| **Telemetry** | The signal model of a machine and the intake of its messages: the unit catalog, metric definitions, status definitions, schema revisions, machine registrations, received messages, and readings. It consumes the machine messages from Mosquitto. | Exists |
| **Insights** | Document ingestion, the LLM worker, and the statistic rules that detect anomalies. | Planned |
| **Document** | A utility service for file storage on Azurite. | Planned |

## Data Ownership

- One PostgreSQL server holds one database per service (e.g., `healthyfac_core`, `healthyfac_auth`, `keycloak`).
- A service writes only to its own database.
- **Exception:** Telemetry is the only writer of `healthyfac_telemetry`. Insights reads it for now, with no role defined yet. Revisit this when the warnings feature is designed.
- Core is the source of truth for companies, employees, and machines. Other services get the data they need from messages or from the token claims. Telemetry keeps its own copy of a machine (the machine registration: machine ID, gateway ID, company, department), so every scope check is local.

## Communication

- **Client to service:** the SPA calls the gateway. The gateway forwards to the service. Every service validates the JWT again.
- **Service to service, asynchronous:** RabbitMQ with Rebus. Every service uses the transactional outbox and inbox (`backend-infrastructure.md`, rule **Outbox and Inbox**). A message type name has the form `<service>.v<version>:<Name>` (e.g., `core.v1:EmployeeInvited`).
- **Equipment to Telemetry:** a gateway publishes to Eclipse Mosquitto (MQTT 5), which is separate from RabbitMQ, so a flooding sender cannot slow down the business messages and a device never gets internal broker credentials. The topic is `healthyfac/gateways/{gatewayId}/messages`, and it is the only source of the gateway ID. Two users exist, with a password file and an ACL file: `telemetry` reads the topic, `sender` writes it. Anonymous access is off. A later feature with a user per gateway binds the topic to the user (`pattern write healthyfac/gateways/%u/messages`).
- **Shared contracts:** the producing service owns each integration message in the project `HealthyFac.<Service>.Messaging` (for example `HealthyFac.Core.Messaging` with `core.v1:MachineCreated` and `core.v1:MachineDeleted`). The message file holds its validator and the project holds its error texts. The producer and each consumer reference the project, so no copy can drift. The project references only `Shared.Application`. The consumer keeps the handler and the pre-handler check. The `MessageType` name stays stable, because stored outbox and inbox rows use it. Architecture tests check the location, the copies, and the layer rule.
- **Service to service, synchronous:** OAuth 2.0 Token Exchange when the call acts for a user, or Client Credentials when the service acts for itself. Never put a token into a message.
- **Register a client:** call `AddUserDelegatedToken(audience, scope)` for a call on behalf of a user. Call `AddClientCredentialsToken().AddActorHeaders()` for a call of an own flow to one of our services. Call `AddClientCredentialsToken()` alone for Keycloak and external APIs. The target audience needs an optional client scope on the calling client in the realm file.
- **Message or call:** a feature chooses a message or a synchronous call by its needs. A message fits when the flow does not need the result and the target may be unavailable. A call fits when the flow needs the answer at once. Both carry the actor.
- **Exchanged token:** the handler exchanges the user token for a short token of one audience. The token carries the `organization` scope. It carries the permissions of the user, including those of the calling API, because Keycloak keeps the own client roles of the calling client in its exchanged tokens. The downstream scopes do not narrow it. Keep each permission name unique across all APIs, because the `permissions` claim is flat. The handler keeps it in Redis for each user, audience, and scope, shared by the instances of the service, until `RefreshMarginSeconds` plus a random jitter of up to `RefreshJitterSeconds` before it expires. Redis removes the entry when the token expires. One instance fetches a token that is due: the others wait on a Redis lock and read the new token, and they fetch it themselves when the lock outlives `LockTimeoutSeconds`. The service token cache uses the same store and the same refresh moment. Asynchronous work has no user token, so it never exchanges.
- **Revocation of an exchanged token:** an exchanged token is used only inside a user request that passed the gateway revocation check, so the target needs no revocation check of its own. Keycloak also refuses the exchange for a disabled user.
- **Service token:** it carries the permissions of its service account, narrowed to the downstream scopes of the current flow. A use case declares them with `[DownstreamScopes(...)]`. A worker that is not a use case calls `IDownstreamScopeHolder.Enter`. The handler asks for the scope `{service}-{name}` of each downstream scope. Without a downstream scope, the token carries no permission. The downstream scopes narrow only this token.
- **Keycloak client per service:** each deployable unit has one client and one secret. Its service account holds a service role with the permissions of all its flows. Role scope mappings and `fullScopeAllowed: false` narrow the service token to the downstream scopes that the flow asked for.
- **Failed calls:** a failed outgoing HTTP call throws an `HttpRequestException` with the method, the path without the query, the status, and a reason. One composed reader (`EnsureSuccessAsync`, `HttpErrorReasonReaders.Default`) takes the reason from the allow-listed fields of the three error formats: ProblemDetails, the Keycloak `errorMessage`, and OAuth 2.0. The message never holds the raw body.

## Messaging

- **Transport:** Rebus sends one message type, `IntegrationEnvelope`. It holds the message type name and the JSON payload.
- **Broker:** all topics share one RabbitMQ topic exchange, `RebusTopics`. The routing key is the message type name.
- **Queue:** each service owns one input queue (`Messaging:QueueName`). It subscribes to each message type that the service handles.
- **Outbox processor:** it locks one pending row with `FOR UPDATE SKIP LOCKED`, publishes it, and marks it in one transaction. The row ID is the Rebus message ID. A run ends when no row is due or when a publish fails. The next run starts after the polling interval.
- **Inbox:** a Rebus handler stores each delivery in the inbox. A duplicate message ID creates no second row. The insert runs under the retrying execution strategy of the service context, so a short database outage during delivery is retried inside each Rebus attempt.
- **Inbox processor:** it locks one row per transaction, restores the actor, and calls the use case `IRequestHandler<TMessage>` through the validation and logging decorators. A failure rolls back the transaction and schedules a retry.
- **Inbox attempt limit:** an inbox row stops after `Messaging:InboxMaxAttemptCount` failed attempts (default 10, about 13 minutes) and gets `failed_on`. The processor never claims it again and logs one `Error` entry for it. The outbox has no limit, because its failures are broker outages.
- **Run a failed row again:** after a fix, set `failed_on = NULL`, `attempt_count = 0`, and `next_attempt_on = now()` for that row.
- **Retry delay:** the delay doubles from two seconds and stops at five minutes.
- **Delivery:** the guarantee is at least once. A crash after the publish and before the commit sends a message twice. The inbox drops the duplicate.
- **One use case:** each message type has exactly one use case per service. `AddUseCases` throws at start-up when one request has two handlers. When two steps must react to one message, one use case runs both, or it saves a new message through the outbox. A use case without a result derives from `RequestHandler<TRequest>`, and a caller injects `IRequestHandler<TRequest>`: an internal adapter calls the decorated pipeline, so validation and logging always run.
- **Broker health:** `/health/ready` checks RabbitMQ on one cached connection. A failure reports `Degraded` with status `200`, because the outbox accepts writes while the broker is down. The check times out in 3 seconds, below the gateway probe timeout.
- **Throughput and backlog:** both processors handle one message per transaction. This is enough for business events. The gauges `healthyfac.messaging.pending` and `healthyfac.messaging.oldest_pending.age` show the backlog of each processor (see **Observability**). When the age grows under normal load, change the outbox processor to claim a batch of rows in one transaction. The inbox stays one message per transaction, so a failed handler rolls back only its own message.
- **Actor headers:** `healthyfac-actor-id`, `healthyfac-company-id`, and `traceparent`. A message without a valid actor header, message ID, or company header goes to the `error` queue at the first attempt. The `error` queue holds only messages that the inbox cannot store: these header faults and a payload that `jsonb` cannot store (see **Invalid messages**). No retry can fix them.
- **Invalid messages:** a payload that does not deserialize, or that fails the validator of its contract, gets `failed_on` at the first attempt, with no retries, and the processor writes one `Error` log entry. The payload stays in the database, where it can be queried and run again. The inbox key drops every later copy of the same message ID, so one invalid message gives one row and one log entry. Other rejections (e.g., a missing entity) keep the normal retries, because message order is not guaranteed. A payload that `jsonb` cannot store (not JSON, or a `\u0000` escape in a string) goes to the `error` queue at the first attempt, because the insert would fail on every attempt.
- **Delivery retries:** other delivery failures get 20 attempts, and each attempt retries transient database failures, so a database outage of about 10 minutes loses no message. The `error` queue is final: a message in it is lost.
- **Error logs:** each move to the `error` queue writes an `Error` log entry with the message ID. Rebus logs reach the application logger without extra configuration.
- **Tracing:** the `HealthyFac.Messaging` source writes the spans `send`, `receive`, and `process`. Each span is the parent of the next, so one trace goes from the HTTP request through the handler. The inbox logs `Information` for each handled message. An SQL span is recorded only under a parent span (`ConfigureParentOnlyTracing`), so the idle polls of the processors create no trace. Processor health comes from the metrics of the `HealthyFac.Messaging` meter (see **Observability**).

## Actor Context

- Each DI scope has one actor: the kind, the actor ID, the name of a service actor, the company ID, the employee ID, and the department IDs. `ICurrentUserProvider` reads it.
- **Departments:** a user token fills the department IDs from the `department_ids` claim (no claim gives an empty set; a value that is not a GUID returns `401`). An anonymous, service, or restored message actor has no departments, so a rule that needs departments fails closed. A later feature that needs departments in messages adds an actor header for them.
- An HTTP request, an inbox message, or a job enters the actor once. A second enter throws until the first lease ends.
- A scope outside an HTTP request starts with `CreateActorScope`. It is the only way to start a job scope, a processor step, or the database start-up.
- **Service call:** a service call carries the actor of the calling flow in the actor headers `healthyfac-actor-id` and `healthyfac-company-id`. Messages use the same headers, and the trust is the same: the target trusts the calling service.
- A service token from a client in `ServiceActors:AllowedClients` runs as the actor of the headers, a user included. The target keeps the actor ID as it is, as for a message. A client outside the list, or a missing or invalid actor header, returns `401`. An empty list accepts no service token.
- A token with a client ID and the user shape (for example, an exchanged token) is a user token. The target ignores the actor headers on it.
- The restored actor of a service call gets no rights of its own. The permissions of the call come from the service token, never from the restored user. When the actor context gets permissions, a service call fills them from the service token.
- A request with a user token never sends actor headers on a service token. `AddActorHeaders` throws and sends nothing in that case: the call must use the token exchange. The gateway removes both actor headers from every external request.
- A use case that a service calls takes the company from the request or from the company header, and it checks that the company exists. It never reads `GetCompanyId()` for an actor without a company.
- An outgoing call reads the actor from the asynchronous flow that entered it, because a handler of `IHttpClientFactory` lives in its own DI scope.
- Only Infrastructure and Web can set the actor. `ActorContextHolder` lives in Shared.Infrastructure, so an Application handler cannot replace the actor.
- An actor has one of three kinds: `user`, `service`, and `anonymous`. The values are part of the actor IDs, so a rename changes the IDs.
- A service never acts as a whole. A flow of the service starts the work: the database start-up, the outbox processor, or the inbox processor. Each flow is a service actor with the name `<service>:<flow>` (for example, `core:outboxProcessor`).
- The `Service:Name` setting names the running service (`core`, `auth`, or `gateway`). The processors and the start-up read it to build their service actor. A start-up check rejects any other value.
- Every actor that is not a user has a name-based UUID (version 5) in one fixed HealthyFac namespace. The key is `anonymous` or `service:<service>:<flow>`. The ID is the same in every environment and needs no table. A Keycloak user ID is version 4, so a user ID never equals an actor ID.
- A request without a signed-in user runs as the anonymous actor, never as a service actor. The anonymous actor has no company and no employee. Nothing grants it a right.
- An authenticated HTTP request runs as the user of its token. `ActorContextMiddleware` runs after authentication and reads `sub`, `organization`, and `employee_id`. Each value must be a GUID, and `organization` must hold exactly one value. Any other shape returns `401`, because the tenant is not clear.
- `Outbox.Add` stores the actor in the row. The inbox processor restores the original actor, so audit fields show who started the work.
- A receiver keeps an incoming actor ID as it is. The anonymous ID gives `anonymous`, any other version 5 ID gives `service`, and every other ID gives `user` (`KnownActors.KindOf`). A restored actor has no name, and the company is kept. Only the service that runs a flow knows its name. The trace links the receiver to that flow.
- Each service declares its own flows. The common flows that shared code runs stay in Shared (`ServiceActor`). A flow of one service lives in that service's project and uses `KnownActors.ForServiceFlow`.
- An audit view shows a user by name. It shows a service actor or the anonymous actor as a generic label from `KindOf`. It never shows a flow name.

## Use Case Rules

- **Run order:** logging, input validation, pre-handler check, downstream scope, handler. Input validation rejects bad input before any query.
- **Pre-handler check:** every use case has one `IPreHandlerCheck<TRequest>`. It checks scope only: the actor works inside their own company and departments (`ActorContextScopeChecks`). A failed check returns `403`. A scope check on a parent resource (e.g., the machine of a status definition) loads it in the check and throws `NotFoundException` (`404`); the scope filter of the loaded resource stays in its handler query. Other stateful rules (uniqueness, existence, state) stay in the handler. A use case without a scope rule declares an empty subclass of `PassThroughPreHandlerCheck<TRequest>`. `AddUseCases` fails at start-up for a request without exactly one pre-handler check, so a use case cannot skip the check in silence.
- **Data scope:** a handler that loads one resource filters the query by the company and the departments of the actor. A resource outside them is "not found" (`404`), so the answer does not show that it exists.
- **Permissions:** endpoint policies check permissions. The pre-handler check never does.

## Machines

- **Endpoints:** `POST /machines` (`machines:write`), `GET /machines/{id}` (`machines:read`), `PUT /machines/{id}` (`machines:write`), `DELETE /machines/{id}` (`machines:delete`), `POST /machines/search` (`machines:read`), and `GET /departments` (any signed-in user; the departments of the current employee). An ID in a path is the encrypted ID. A malformed ID returns `404`.
- **Serial number:** unique per company among the machines that are not deleted, ignoring case. The entity keeps `SerialNumberKey` (lower case) for a unique index with the filter `deleted_at IS NULL`. The handler checks first (`409`), and the index catches a parallel create or update (also `409`).
- **Soft delete:** a shared `ISoftDeletable` entity keeps its row. `SoftDeleteInterceptor` turns `Remove` into an update that sets `DeletedAt` and `DeletedBy`, and a global query filter hides the row. A second delete returns `404`. No restore exists yet.
- **Grid contract:** `GridRequest<TFilter, TSortColumn>` (`Offset`, `Limit` 1 to 100, one sort column, a typed filter) and `GridResponse<TItem>` (`Items`, `TotalCount`) live in `Shared.Application/Grids`. A filter field is a `TextFilter` (starts with, ignoring case), a `SetFilter<T>`, or a `DateRangeFilter` (`From` inclusive, `To` exclusive, UTC). A sort map links each sort column to a key expression, and the ID is the last sort key, so pages never skip or repeat a row. The web app sends a picked day range as the start of the first day to the start of the day after the last day, in the browser time zone, converted to UTC.
- **Description:** rich text as HTML. The limit counts the **visible text**: at most 5000 characters, not 5000 characters of HTML. A raw cap of 20,000 characters (`RichTextConstants.HtmlMaxLength`) protects the storage and the parser; the column is `text` with a check constraint at the cap. `IRichTextPolicy.Inspect` (HtmlSanitizer, in Shared.Infrastructure) parses the HTML once. It gives the allow-list verdict (a removal means `400`) and the visible length. It never alters the text. The shared rule `RichTextRules.IsRichText` (`Shared.Application/RichText`) runs in this order: raw cap (no parse), allow-list, visible limit. The machine, the status definition, and the metric definition validators call it. The visible length is the text content of the parsed body, in Unicode normalization form C, counted in UTF-16 characters. The web app counts the same way with `DOMParser`, so both sides agree.
- **State history:** the table `machine_state_histories` holds one row per state and its start (`StartedAt`). The current state is the state of the row with the latest `StartedAt`. Every machine starts `operational`. `Machine.ChangeState` keeps the timeline strictly ordered and rejects a repeat of the current state. A machine delete soft-deletes its history rows in the same save. The grid filters on the current state and does not sort it.
- **Gateway ID:** the `Machine` constructor generates a random gateway ID of 16 lower-case base32 characters (`a-z2-7`, `GatewayIds` in `Shared.Domain`). It never changes. A unique index covers it without the soft delete filter, because an ID is never reused (a listed exception in `SoftDeleteModelTests`). The machine drawer shows it with a copy button.
- **Department:** a machine keeps its department. `UpdateMachine` has no department.
- **Events:** `CreateMachine` adds `core.v1:MachineCreated` (machine ID, gateway ID, company, department) and `DeleteMachine` adds `core.v1:MachineDeleted` (machine ID, company) to the outbox in the same save. The delete cascade to the Telemetry definitions is eventual: Telemetry soft-deletes the registration, the status definitions, and the metric definitions when it handles the event. For a few seconds after a create, Telemetry returns `404` for the machine, and after a delete it still accepts requests for it.
- **Seed machines:** `backend/seed/seed.Development.json` (read in Development by Core and Telemetry; an environment variable overrides a value) lists `SeedMachines` (machine ID, gateway ID, department index) and the names of the test tenant. Core seeds these machines. The Telemetry dev seed creates their registrations, status definitions, and sample metrics itself, because it runs before Core publishes the events.
- **Existing development machines:** machines created before the gateway ID migration have no Telemetry registration, because only the seed and `CreateMachine` publish `MachineCreated`. Recreate a development database once after this change (`HEALTHYFAC_SEED_RECREATE=true`).

## Telemetry

- **Units:** the global tables `quantity_kinds` and `measurement_units` hold the unit catalog, seeded in `SeedRequiredDataAsync` with an `INSERT ... ON CONFLICT` upsert from typed UnitsNet 5.75.1 members (the quantity name, the unit name, and the abbreviation come from UnitsNet). A unit is identified by the pair of the quantity kind name and the unit name (`Percent` exists under two kinds). `GET /metric-units` (`metric-definitions:read`) lists the catalog. The abbreviation of `Scalar.Amount` is empty. The `Discrete` kind is an own constant (`DiscreteUnits`) with the units `Boolean` and `State` (empty abbreviation); `GET /metric-units` leaves it out. There is no unit conversion.
- **Machine registration:** `MachineRegistration` (the machine ID as `Id`, gateway ID, company, department, the schema revision number) is created by the handler of `core.v1:MachineCreated` ("find, else create") and soft-deleted with its definitions by the handler of `core.v1:MachineDeleted`. A delete before the create retries through the inbox. Every metric and status use case checks the registration by company and departments in its pre-handler check (`MachineRegistrationScope`); a machine outside the scope, a deleted machine, and an unknown machine return `404`.
- **Metric definitions:** key (`^[a-z][a-z0-9_]*(\.[a-z][a-z0-9_]*)*$`, at most 100 characters, unique per machine among active definitions, never changes), name, description (rich text), value kind (`numeric`, `boolean`, `stateSet`), unit (always set; numeric: a unit of the catalog from the request, never a `Discrete` unit; boolean and state set: `Discrete.Boolean` or `Discrete.State`, set by the server), min and max (numeric only, `min < max`), and states (state set only, at least 2 unique codes). Key, value kind, and unit never change. A deleted definition frees its key. The audit and soft delete fields apply.
- **Staged apply:** `PUT /machines/{machineId}/metric-definitions` (`metric-definitions:write`) takes `expectedRevision`, `created`, `updated`, and `deleted` and stores all changes, the raised revision of the registration, and a new schema revision in one save. A stale revision returns `409`. The row version of the registration and the unique index on (registration, revision) catch a parallel apply (`409`). A `400` names the failed item by its path (`created[2].key`). `GET /machines/{machineId}/metric-definitions` (`metric-definitions:read`) lists the active definitions with the current revision, and `GET /machines/{machineId}/metric-schema` returns the last schema.
- **Payload schema:** JsonSchema.Net 9.6.0 builds a draft 2020-12 schema per machine and revision (`$id` `urn:healthyfac:gateways:{gatewayId}:metrics:{revision}`). It asserts the envelope (`sampledAt` as `date-time`, `metrics`, `statuses`, no other root field) and the JSON type of each key. The range, the states, the unit, and the title are annotations, never assertions. Every revision is stored (`metric_schema_revisions`, append-only). Each build and each parse uses its own schema registry, because the global registry rejects a second schema with the same ID. The intake keeps no parsed schema in process memory.
- **Status definitions:** a machine has 0 to many statuses with a code (at most 50 characters, unique per machine among active rows, ignoring case), a severity (`info`, `warning`, `error`), and a rich text description. Endpoints are `POST|search|GET|PUT|DELETE /machines/{machineId}/status-definitions` with `status-definitions:read|write|delete`. A status change adds no schema revision. They replace the Core error codes.
- **Payload:** `{ "sampledAt": "...", "metrics": { "<key>": <value> }, "statuses": ["<code>"] }`. Every message holds the current value of every metric. A value is in the declared unit of its key. The payload has no gateway field.
- **Validation per value:** an envelope failure (not JSON, a gateway ID that is not in the format, an unknown gateway, a missing or unknown root field, a wrong `sampledAt`, a `sampledAt` more than 1 minute ahead) stores a received message with the error and no reading. A wrong JSON type, an unknown or missing key, an unknown status code, and a repeated status code are value errors in `received_messages.errors`; the other values are stored. A number outside the range and a state outside the set are stored with `is_out_of_range = true`, never as an error. The flag uses the definition at receipt.
- **Storage:** `received_messages` (the raw bytes as `bytea` always, the payload as `jsonb` when storable, the errors as `jsonb`, a unique index on the machine and the sampling time that drops a repeated delivery), `numeric_readings`, `discrete_readings`, and `status_readings`. A reading has the natural primary key (definition, sampling time) and no `Id`. Received messages, schema revisions, and readings have neither `IAuditable` nor `ISoftDeletable`. The architecture tests and the model tests list each exception.
- **Intake:** `MqttIntakeService` subscribes to the shared subscription `$share/{group}/healthyfac/gateways/+/messages` with QoS 1 and a persistent session, and runs the use case `ReceiveMachineMessage` as the actor `telemetry:intake`. It acknowledges a message only after the commit. A transient failure (the database is not reachable, a command timeout, the retry limit) leaves the message unacknowledged, drops the connection, and connects again after a delay, so the broker delivers it again; the unique index drops a repeat. Any other failure is the same on every delivery: the service stores the raw bytes as a received message with the error `processingFailed` (no readings, no machine) in a new scope, logs one `Error` with the exception, and acknowledges. A message that fails input validation is acknowledged and logged without the payload. A received message holds exactly one of `payload` (`jsonb`) and `raw_payload` (`bytea`): the raw bytes only for `malformedJson` (including a duplicate property), `unstorableJson` (a U+0000 character or a lone surrogate), and `processingFailed`. Each instance runs `MqttIntake:ConsumerCount` consumers (default 1, at most 16), each with its own client and the client ID `{ClientId}-{index}`. The shared subscription gives each message to one consumer, so the consumers of all instances share the load. The messages are not processed in order, because the readings are keyed by `sampled_at`. Each instance needs a stable, unique `ClientId` (for example a StatefulSet pod name or a Compose replica name), and the count must stay the same between restarts, because the broker keeps the session and the unacknowledged messages by client ID. Each consumer holds up to 1 database connection during a save, so the count stays below the connection pool size. The session expires after `MqttIntake:SessionExpirySeconds` (default 3600, range 60 to 86400). Measured with Mosquitto: the broker keeps the share of an offline member in its queue while the session is alive, and the member gets it again after a reconnect with the same client ID. When the session expires, the broker drops the queued and unacknowledged messages and does not give them to the other members; new messages then go only to the live members. A message is lost when a consumer stays offline longer than the expiry, or when its queue passes a broker limit: `max_queued_messages 100000` and `max_queued_bytes 104857600` (100 MiB) per session (`docker/mosquitto/mosquitto.conf`; the Mosquitto default of 1000 messages is too low). The limits bound the broker memory. A stop finishes the messages that a consumer already started, within `MqttIntake:DrainTimeoutSeconds` (default 20, range 1 to 29, below the 30 second stop time of the host and of Compose). A message that arrives after the stop signal is neither handled nor acknowledged. The consumer then disconnects with the normal session expiry. It never unsubscribes and never deletes its session, so the broker keeps the session for up to `SessionExpirySeconds`, queues the messages that arrive while the instance is down, and delivers them after the restart (measured with Mosquitto: an offline session keeps its share, and the broker still delivers the messages that it assigned to a member after an unsubscribe). If the finish times out, the broker keeps the unacknowledged messages and delivers them again. At start, the service empties its own orphan sessions: for each client ID `{ClientId}-{index}` with an index from `ConsumerCount` to 15 that has a session, it handles the queued messages, unsubscribes, waits `MqttIntake:DrainIdleSeconds` (default 2) without a new message, disconnects, and deletes the session by a short clean-start connection with a session expiry of 0 (MQTTnet cannot send an expiry of 0 on a disconnect). It keeps the normal session expiry while it works, so a failure leaves the session for the next start. A lower `ConsumerCount` therefore loses nothing at the next start of the instance. Data is lost in 2 cases: an instance that is removed for good (no running instance knows its sessions, so the broker queues their share until the expiry and then drops it), and a stop or crash that lasts longer than the session expiry. The `ClientId` of an instance must stay the same across restarts: a StatefulSet pod name or a fixed Compose value works. A Deployment pod name changes on each start, so each rollout leaves orphan sessions that take their share for up to 1 hour and then lose it. The health check reports `Degraded` while the intake is enabled and fewer than `ConsumerCount` consumers are connected.
- **Intake Telemetry:** Each received message gets one `Consumer` span `process healthyfac/gateways/+/messages` from the source `HealthyFac.Telemetry.Intake`. The name holds the subscription pattern, never the gateway ID. A `traceparent` MQTT user property makes the span continue the trace of the sender. Without it, the span starts a new trace. The use case spans are its children. The span tags hold the topic, the shared group, the consumer index, the result, and the error code of a rejected message. The result is one of `stored`, `stored_with_errors`, `rejected`, `duplicate`, `invalid`, `failed`, or `redelivery`. The last two set the span status to `Error`. The meter `HealthyFac.Telemetry.Intake` counts the messages by result (`healthyfac.intake.messages`). It records the handle duration (`healthyfac.intake.handle.duration`). It records the lag between `sampledAt` and receipt (`healthyfac.intake.lag`, only for stored messages). It reports the messages in flight and the connected consumers. It counts the messages of emptied orphan sessions and the drain timeouts. No metric holds a gateway ID, a topic, or a machine ID as a tag. The service does not measure the queue depth of the broker, because that needs a monitor session on the broker (decided against). A growing lag shows a growing queue indirectly.
- **No retention:** received messages and readings grow without limit for now. No retention job exists.
- **Eventual consistency:** the registration appears after the outbox publishes `MachineCreated`, and the definitions disappear after `MachineDeleted`.

## Email

- A service sends email through `IEmailSender` (Shared.Application). The host picks the implementation with one registration method. `AddSmtpEmail` registers the SMTP sender (MailKit). A later provider adds its own `Add...Email` method.
- Development uses Mailpit. It catches all email, and its web UI shows the messages (`MAILPIT_UI_PORT`, default `8025`). Mailpit keeps the messages in the `mailpit-data` volume, and `docker compose down -v` removes them. Compose sets the `Smtp__*` variables of `core`.
- Other deployments set `Smtp__Host`, `Smtp__Port`, `Smtp__Security`, `Smtp__UserName`, `Smtp__Password`, `Smtp__FromAddress`, and `Smtp__FromName`.
- **Invite email:** Core consumes `core.v1:EmployeeInvited` and emails the invited person the link `{InviteLinks:SpaBaseUrl}/invite#token={token}`. The token is in the fragment, so no server log or proxy records it.
- **Rendering:** the email bodies are Razor components in the Web layer. `RazorComponentRenderer` (`Shared.Web/Rendering`) renders them with `HtmlRenderer`, outside an HTTP request. It is not email-specific: a later feature can reuse it for other output. The Application layer sees only `IEmployeeInviteEmailBuilder`. The text body is the HTML-decoded render of its own component.
- **Spans:** the `HealthyFac.Rendering` source writes `Razor.Render` for each rendered body. The `HealthyFac.Email` source writes `Email.Send` for each message. The MailKit source `MailKit.Net.SmtpClient` adds the SMTP steps under `Email.Send`. No span holds a recipient, a body, or a link.
- **Token at send time:** the handler builds the token from the current salt of the invite. The token never enters the database, the outbox, or a log. Two messages for one invite send two links that both work.
- **Skipped invites:** the handler sends nothing and completes when the invite is missing, accepted, or expired. A supervisor resends an expired invite.
- **Failures:** a sender failure makes the inbox retry the message. After `Messaging:InboxMaxAttemptCount` attempts, the inbox row gets `failed_on`. A crash after the send and before the commit sends the email again.

## Public Paths

- The public path has the form `/api/<service>/v{version}/...` (e.g., `/api/core/v1/machines`).
- A service routes under `/v{version}`, without `/api`. The gateway removes the whole `/api/<service>` prefix.
- The gateway sends `X-Forwarded-Prefix: /api/<service>`. A service accepts this header from trusted proxies only (`Proxy:KnownNetworks`). Its `PathBase` then becomes the public prefix, so every link that it builds (e.g., the `Location` header) shows the public path.
- **Logical names:** each public service has its own name, so a move to the cloud changes only the names and the scheme. The domain is `healthyfac.test` (`HEALTHYFAC_DOMAIN`). The `.test` top-level domain is reserved for tests (RFC 6761) and never resolves on the internet.

| Name | Serves | Cloud equivalent |
| --- | --- | --- |
| `https://api.healthyfac.test` | the gateway, Core API routes (`/api/core/v{n}/...`) | `https://api.<domain>` |
| `https://auth.healthyfac.test` | the gateway, Keycloak routes (`/realms/healthyfac/...`, `/resources/...`); the token issuer | `https://auth.<domain>` |
| `https://app.healthyfac.test` | the gateway, the SPA host route (all paths); in container mode the web app, invite links, redirect URIs, CORS origin | `https://app.<domain>` |
| `https://app.healthyfac.test:4200` | `ng serve` of the web app (development mode) | none |

- **TLS:** TLS ends at the gateway, as at a cloud load balancer or ingress.
    - The public URLs use HTTPS and no port. `GATEWAY_PORT` is 443; when it is not, add the port to `HEALTHYFAC_AUTH_URL`, because the issuer must equal the URL that the browser uses.
    - The gateway publishes HTTPS only. Plain HTTP on the public port gets no HTTP response.
    - Internal traffic stays HTTP: gateway to Core, gateway to Keycloak, the health ports, and the Keycloak admin console on `localhost`. The gateway sets `X-Forwarded-Proto: https`, and Core and Keycloak (`KC_PROXY_HEADERS: xforwarded`) read it.
    - A local certificate authority (mkcert) signs the certificate. The files are `docker/certs/healthyfac.test.pem` and `docker/certs/healthyfac.test-key.pem`. Git ignores them, and no image holds them. Compose mounts the folder read-only into the gateway. See `docker/certs/README.md`.
    - The launch profile `https` of the gateway serves `https://localhost:5001` with the same files. With the hosts file, a browser reaches `https://api.healthyfac.test:5001`.

- **Host routing:** each gateway route has a YARP `Match.Hosts` entry with its name. A host without a port matches every port. A request to another name matches no route: `401` without a token, `404` with a token. The names are set per environment (`appsettings.Development.json`, Compose); `appsettings.json` holds none.
- **Development tools** stay on `localhost`: the Keycloak admin console (`KEYCLOAK_PORT`, set by `KC_HOSTNAME_ADMIN`), Mailpit, Grafana, the RabbitMQ console, the database, and the health ports.
- **Hosts file:** map the three names to the local machine, as an administrator (`C:\Windows\System32\drivers\etc\hosts` on Windows):

```text
127.0.0.1 api.healthyfac.test auth.healthyfac.test app.healthyfac.test
```

- **CORS at the gateway only:** the gateway answers the cross-origin requests of browsers (`AddSharedCors`, `UseSharedCors`).
    - Each route that the web app calls (`core`, `core-invite-public`) names the policy with `"CorsPolicy": "HealthyFacDefault"`.
    - The CORS middleware runs before authentication. A preflight (`OPTIONS`, no `Authorization` header) gets `204`. It never meets authentication, the revocation check, the rate limiter, or authorization.
    - `Cors:PreflightMaxAgeSeconds` (600) lets the browser cache the answer. Browsers ignore a value above 7200.
    - A service behind the gateway keeps `Cors:IsEnabled = false`. Two layers that write `Access-Control-Allow-Origin` make the browser reject the response.
    - Keycloak answers CORS for its own routes from the `webOrigins` of each client. The gateway adds no CORS headers there.
    - The allowed origins have no default. Each environment sets `Cors:AllowedOrigins` (Compose: `HEALTHYFAC_SPA_URL`).
- **Versioned paths only:** the `core` route matches `/api/core/v{n}/...` only. Paths such as `/api/core/hc`, `/api/core/health/ready`, and `/api/core/openapi/...` match no route, so the gateway makes no call to Core. It answers `401` without a token and `404` with a token.

## Health Endpoints

- Each service serves `/health` (liveness), `/health/ready` (readiness), and `/hc` (every check, with exception texts) on one internal health port.
    - The setting is `HealthEndpoints:Port`. The containers use `8090`. The API port does not serve these paths.
- `UseSharedHealthChecks()` is the first middleware. It compares the local port of the connection, which a client cannot change. It never reads the `Host` header.
- Health requests skip HTTPS redirect, request logging, CORS, authentication, revocation, rate limiting, and authorization.
- Compose publishes the health ports on `127.0.0.1` only (`CORE_HEALTH_PORT`, `GATEWAY_HEALTH_PORT`). No gateway route reaches them. In the cloud, the platform probes use the health port, and no public load balancer routes it.
- The gateway active health check of Core calls the `Health` address of the destination (the health port of Core), with the path `/health/ready`.

## Gateway Failure Policy

- Redis is not a hard dependency of the gateway. When Redis fails, rate limiting falls back to a local limiter per instance. With N instances, the effective limit can reach N times the configured limit during an outage.
- A circuit breaker skips Redis for 30 seconds when at least half of at least 2 calls in 30 seconds fail. Then one request tests Redis, and the others keep the local limiter until the test succeeds. Polly logs the breaker events with its default levels: opened at `Error`, half-opened at `Warning`, and closed at `Information`. During a long outage, each failed test logs one `Error` and one `Warning` every 30 seconds.
- `/health/ready` reports `Degraded` with status `200` while Redis is down. The gateway readiness does not check the services behind it.
- Every error response of the gateway is `application/problem+json`: `429` (rate limit), `502` (destination unreachable or broken response), `503` (no healthy destination), `504` (destination timeout), and `500` (gateway exception, without details). A client cancellation gets no body.
- The gateway never retries a request. A `POST` request is not idempotent, so the client decides on a retry.
- The revocation check passes a request when Redis fails, and the same circuit breaker protects it.
- The gateway skips a destination that the health checks mark unhealthy. It does not fall back to all destinations.

## Identity

- Keycloak is the identity provider. The SPA signs in with the Authorization Code flow and PKCE.
- Each company is a Keycloak organization. The organization alias is `Company.Id`, so Keycloak holds no other company data.
- The access token carries `sub` (the Keycloak user ID), the permissions, the `organization` claim (the company ID), `employee_id`, and `department_ids` (the department IDs of the employee). The ID token for the web app carries `permissions` only. The API encrypts every ID in its JSON, so the web app takes the departments from `GET /departments`, never from the token.
- **Departments in the token:** the multi-value user attribute `department_ids` (admin view and edit only) holds them. Auth writes it when it creates the user, from the `DepartmentIds` of `core.v1:EmployeeAccepted`. An existing user keeps its attributes. A later department-change feature updates the attribute and revokes the tokens of the user.
- The roles `worker` and `supervisor` group the permissions. API policies check permissions, never role names.
- **Realm as code:** three files hold the development realm. `docker/keycloak/realm/healthyfac-realm.json` holds the realm settings, the user profile, the clients, the client scopes, and the roles. The `keycloak-config` job (`keycloak-config-cli`) applies it after each start and changes only the differences, so a change needs no reset. `docker/keycloak/dev/healthyfac-test-tenant.json` holds the test organization and the supervisor with a password. The job applies it after the realm file. It never reaches production. `docker/keycloak/import/healthyfac-test-bootstrap.json` holds the realm name and the supervisor with the fixed ID. Keycloak imports it (`--import-realm`) on a fresh database, because only the import keeps a fixed user ID (the Core seed uses it). The job finds that user by its name and keeps its ID. The job keeps the users, organization members, and role mappings that Auth creates (`IMPORT_MANAGED_ORGANIZATION=no-delete`, `IMPORT_USERS_MERGEROLES=true`). All files use the placeholder `${NAME}` for environment variables; the job reads it through `IMPORT_VARSUBSTITUTION_PREFIX`, `_SUFFIX`, and `_UNDEFINEDISERROR=false`, and leaves the Keycloak message placeholders (`${username}`) unchanged. Because of that, the job does not stop on a missing variable; Compose checks the variables, and the test container class rejects blank values. After a change, run `docker compose up keycloak-config`. The integration tests run the same image. Production applies only `realm/healthyfac-realm.json` with the job; production provisioning of organizations and users is not decided. Edit the user profile in `docker/keycloak/user-profile.json` only, then run `docker/keycloak/embed-user-profile.sh`, which embeds it into the realm file as the string that Keycloak expects; the test `UserProfile_InRealmFile_EqualsSourceFile` fails when the two differ.
- **Refresh tokens:** the realm rotates refresh tokens (`revokeRefreshToken: true`, `refreshTokenMaxReuse: 0`). Each refresh invalidates the used token, and a second use of it fails. `healthyfac-spa` sets `post.logout.redirect.uris` to `{HEALTHYFAC_SPA_URL}/*`, so the logout redirects back to the web app.
- **Clients:** `healthyfac-spa` (public, Authorization Code with PKCE), `healthyfac-core` (confidential, holds the permission roles), and `healthyfac-auth` (service account for the Auth service). The client has the scope `service_account` explicitly, because the realm import does not add it. A service token carries `client_id` (it identifies the calling service) and no `clientHost` or `clientAddress`, so it holds no host name or IP address of the caller.
- **Permissions:** client roles of `healthyfac-core`: `employees:invite`, `employees:manage`, `machines:read`, `machines:write`, and `machines:delete`. The client holds permissions only. The job role `supervisor` holds all five, and `worker` holds the three machine permissions. Both are realm roles, composites of those client roles, so a job role can later also hold permissions of other APIs. The mapper `healthyfac-core-permissions` of the scope `healthyfac-claims` writes the effective client roles of `healthyfac-core` into the flat claim `permissions`. The JWT handler splits the array into one `permissions` claim per value, and the endpoint policies check that claim. The name of a policy is the name of the permission. The token has no `resource_access` and no `realm_access`.
- **Token validation:** every service validates the JWT itself (`AddSharedJwtAuthentication`). The issuer is the public URL of the realm (the gateway). The service reads the keys from the internal Keycloak address (`Jwt:MetadataAddress`), which works because of `KC_HOSTNAME_BACKCHANNEL_DYNAMIC`. A token needs `healthyfac-core` in `aud`. The service reads the permissions from the `permissions` claim and needs no claims transformation. The access token lives 300 seconds.
- **Core endpoints:** a fallback policy requires a signed-in user. Invite create and resend need `employees:invite`, retry provisioning and deactivate need `employees:manage`, and the machine endpoints need the machine permissions (see **Machines**). Verify, accept, and OpenAPI (Development only) are anonymous. The health endpoints are on the health port (see **Health Endpoints**). The company of a request comes from the token only: a Web request record has no `CompanyId`.
- **Gateway:** the gateway validates the token, checks the revocation list, and then applies the rate limit. It routes `/realms/healthyfac/*` and `/resources/*` to Keycloak. The Keycloak routes answer only `auth.<domain>`, and the Core routes answer only `api.<domain>`. No route reaches `/admin`. The `core` route needs a signed-in user, and the default rate limit counts for each user (`sub`). A fallback policy (`SetAuthenticatedFallbackPolicy`) requires a signed-in user for a route without `AuthorizationPolicy` and for a request that matches no route. Public routes name the `anonymous` policy.
- **Revocation:** the key `revoked:{sub}` holds the revocation time in Unix seconds. The gateway answers `401` when `iat` is earlier. A missing entry passes. Redis failures follow the **Gateway Failure Policy**: the request passes, and the circuit breaker logs a warning.
- **Provisioning:** Auth consumes `core.v1:EmployeeAccepted`, finds the Keycloak organization of the company, finds or creates the user by `employee_id`, adds the user to the organization, maps the realm role, and emails a set-password link while the user has no password. It publishes `auth.v1:IdentityProvisioned`, or `auth.v1:IdentityProvisioningFailed` with the reason `OrganizationNotFound`, `EmailAlreadyRegistered`, or `RoleNotFound`. Auth never creates an organization. A supervisor retries a stuck provisioning with `POST /employees/retry-provisioning`.
- **Deactivation:** `POST /employees/deactivate` deactivates the employee and sends `core.v1:EmployeeDeactivated`. Auth disables the Keycloak user, ends the sessions, and then writes the revocation entry with the current time. No token can be issued after the disable, so the entry rejects every access token of the user. A failure of Keycloak or Redis retries through the inbox. An identity that Auth creates for a deactivated employee is revoked at once through a second `EmployeeDeactivated`.
- **Test tenant:** one set of `.env` values (`HEALTHYFAC_TEST_*`) feeds the realm import and the Core development seed. The seed creates the company, two departments, and an active supervisor with the fixed IDs, and no `EmployeeAccepted` message. The department IDs (`HEALTHYFAC_TEST_DEPARTMENT_A_ID` and `_B_ID`) are fixed too, because Keycloak lists them in the `department_ids` attribute of the supervisor. `HEALTHYFAC_SEED_RECREATE=true` deletes the Core business data, outbox, and inbox and seeds again on every start; set it back to `false` after one start.
- Today, maintenance workers and supervisors sign in. Sign-in for other users (e.g., a platform operator outside every company) is not decided.

## Text Input

- **Normalize:** the shared JSON options of the API and the messages (`TextInputJson`, Shared.Infrastructure) turn `
` and `` into `
`, trim each string on read, and apply Unicode NFC. Query and route strings hold only IDs today; the first search filter adds a binder.
- **Reject:** each validator gives every string member `SingleLineText()` or `MultilineText()` (`TextInputRuleExtensions`, Shared.Application). The rule rejects the null character in every field and control characters in single-line fields (tabs and line breaks pass in multi-line fields). HTTP returns `400`. A message fails at the first attempt. The error key is the JSON name of the field (camelCase), and the error never holds the value. An architecture test checks that no string is left without a rule. No layer removes a character silently.
- **Field semantics:** `EmailAddresses.Normalize` (Shared.Domain) trims and lower-cases every email in requests, messages, and entities. Keycloak stores emails in lower case too.
- **Output:** Razor and the web app encode HTML on output. No layer sanitizes HTML on input. The only HTML field is the machine description: a rich text policy rejects what is outside the allow-list (see **Machines**), and the web app shows it through the Angular sanitizer.
- **Null character in messages:** PostgreSQL `jsonb` rejects `\u0000`, so such a message never reaches the inbox table. The inbox insert fails, and Rebus moves the message to the error queue after its retries.

## Observability

- **Resource attributes:** traces, metrics, and logs carry the same resource from one function (`TelemetryResource`): `service.namespace=healthyfac`, `service.name` from `Service:Name` (`core`, `auth`, `gateway`), `service.version` (the informational version of the application assembly), `deployment.environment.name` (the host environment in lower case), and one `service.instance.id` per process. `OTEL_SERVICE_NAME` and `OTEL_RESOURCE_ATTRIBUTES` override these values. The deployment or the collector adds platform attributes (`k8s.*`, `host.*`).
- **Metrics:** each service exports OTLP metrics to the trace endpoint (`Metrics:Endpoint`). The meters are `HealthyFac.Messaging`, `System.Runtime`, the built-in ASP.NET Core and `HttpClient` meters, and `Npgsql` in the services with a database (`Metrics:AdditionalMeters`). The health probes answer on the health port, so a dashboard separates them from API traffic by `server.port`.
- **Messaging metrics:** the counters `healthyfac.messaging.published`, `handled`, `retried`, and `failed` (tag `healthyfac.messaging.failure`: `permanent` or `attempt_limit`), and the histograms `healthyfac.messaging.run.duration` and `healthyfac.messaging.handle.duration` (seconds). The tags are the processor (`outbox`, `inbox`), the message type, and the outcome, never a message ID. A cancellation records no failure.
- **Backlog gauges:** a sampler reads the pending count and the oldest pending time of both tables every 15 seconds, with one query per table on the pending index and without a trace. The gauges `healthyfac.messaging.pending` and `healthyfac.messaging.oldest_pending.age` report the last sample, so the export never queries the database. A failed inbox row is not pending. Every instance reports the same table values, so a dashboard aggregates them with `max`, never `sum`.
- **Span names:** an internal span is `<Area>.<Action>` in PascalCase (`Razor.Render`, `UseCase.Validate`). The use case span keeps the request type name, and the tag `healthyfac.use_case` holds the same name. HTTP and messaging spans keep the library names. No span name holds an ID or a user value. The rule `observability` lists the naming conventions.
- **Layer boundary:** Domain, Application, and Infrastructure create spans and metrics only through the .NET API (`ActivitySource`, `Meter`). Only `HealthyFac.Shared.Web` references OpenTelemetry packages, so the host decides where telemetry goes. The architecture tests forbid the `OpenTelemetry` namespace in the inner layers.

## Frontend

- **Stack:** Angular 22.2 (zoneless), PrimeNG 22 with the Lara preset, Tailwind 4, ngx-translate 18, NgRx SignalStore 22, and `temporal-polyfill`.
- **Folders:** `src/app/` holds the app root and `layout/`. `shared/` groups code by intent (`storage/`, `i18n/`, `theme/`, `time/`). Each feature has its own folder under `app/` and one folder per use case. Aliases: `@app/`, `@shared/`, and `@<feature>/`.
- **State scopes:** a global store uses `providedIn: 'root'` and lives in `shared/`. A feature store is a provider on the lazy route. A local store is a provider on the component. Stores save to storage only through `withStorageSync` and `BROWSER_STORAGE`.
- **Theme:** one preset defines the colors. PrimeNG and Tailwind read the same tokens. The class `app-dark` on `<html>` switches both libraries.
- **Time:** all date and time values use Temporal. Code reads the current time only through the `CLOCK` token. `Date` appears only in the picker wrappers, because PrimeNG needs it.
- **Forms:** all forms use Signal Forms. A form validates with a `zod/mini` schema through `validateStandardSchema`. A wrapper component adapts each PrimeNG date picker to a Temporal value.
- **Text:** ngx-translate loads `public/i18n/<language>.json`. English is the fallback. The keys use capitalized snake case.
- **Runtime config:** the app reads `/config.json` before it starts. `parseAppConfig` validates it with one `zod/mini` schema (`appConfigSchema`) and derives the `AppConfig` type from it. The SPA host is the only source of the file, in every run mode. The file is public and holds only values that every visitor may see. The host caches it for `Spa:RuntimeConfigCacheSeconds` (default 300 seconds), so a configuration change reaches open browsers within that time. A wrong file stops the start with a plain text message. A production build shows only a generic text; a development build names the problem.
- **HTTP errors:** `apiBaseUrlInterceptor` prefixes `/api/` paths with the API URL. `problemDetailsInterceptor` shows a translated toast and rethrows the error. A validation error (`400` with `errors`) shows no toast.
- **Authentication:** `keycloak-js` runs in `AuthStore` (`shared/security/`). The tokens live only in memory. A silent SSO check runs at start (`silent-check-sso.html`, which the host serves with its own CSP). `authGuard` protects each route. On a `401`, `authInterceptor` forces one refresh and retries once, then sends the user to login. Every refresh runs through one shared promise in `AuthStore`. Only an ended session (a `400` from Keycloak, or no refresh token) sends the user to login. A transient failure (network, `5xx`) shows the network toast and keeps the page. Sign-out returns to the app root.
- **CSP:** the SPA host answers the index with a content security policy and a new nonce per response (`__CSP_NONCE__` in `index.html`). Angular and PrimeNG read the nonce from `ngCspNonce`. The policy allows the identity provider origin in `connect-src` and `frame-src` (the silent SSO iframe). The policy allows `style-src-attr 'unsafe-inline'`, because PrimeNG sets inline `style` attributes. The host serves `index.html` only through its endpoint. Hashed files cache for a year.
- **Run modes:** `ng serve` serves `https://app.healthyfac.test:4200` (default `HEALTHYFAC_SPA_URL`). It needs the Compose stack with the `spa` and `gateway` services, and it proxies `/config.json` to `https://app.healthyfac.test` (the gateway on port 443). The proxy does not check the certificate (`secure: false` in `proxy.conf.json`), because Node does not trust the mkcert root and the target is the local gateway. The `spa` Compose service serves `https://app.healthyfac.test` through the gateway. Set `HEALTHYFAC_SPA_URL=https://app.healthyfac.test` in `.env` for it.
- **Components:** a route page (`*-page.ts`) and an action host (`*-host.ts`) are smart: only they inject stores. Every other component is dumb (`input()`, `output()`, `model()`). ESLint checks the store imports and requires a display class in `host: { class }` on every component.
- **Layout:** `h-dvh` is set once on `hf-root`. The chain from the root to the grid carries `min-h-0` and `min-w-0`, so only the grid scrolls, never the page. The smallest target is 1024 × 600 CSS pixels (`min-w-5xl` on the shell).
- **Employee and permissions:** `AuthStore` reads `permissions` from the ID token and offers `hasPermission`. `EmployeeStore` (root) loads the departments from `GET /departments`.
- **Actions:** `ActionStore.dispatch({ type, payload })` loads the registered host module, validates the payload with its schema, and `ActionHost` (placed once in the shell) shows the host. An agent or a page opens the machine drawer the same way. A host reports a result with `complete(type)`, and the machines grid reloads on `machines.saved`. The payload schema of a machine action is the partial machine form schema.
- **PrimeUI license:** PrimeNG checks the PrimeUI Community key in the browser, so the key is public by design. The SPA host reads it from `PRIMEUI_LICENSE_KEY` (`.env`, Compose `Spa__PrimeUiLicenseKey`) and sends it in `/config.json`. `main.ts` builds the providers with `createAppConfig(config)`, so `providePrimeNG` gets the key before the app starts. The image holds no key: a key change needs only a restart of `spa`. Local `ng serve` reads `/config.json` through the proxy, so it gets the key too. The key never comes from git.
- **Open items:** the typed API client.

## Shared Infrastructure

- **Redis:** the token revocation list, the gateway rate limiter counters, and the distributed cache. A service caches data only in Redis, through the shared connection, and keeps no copy in process memory (no FusionCache, no `HybridCache`, no `IMemoryCache`, no `IDistributedCache`), so every instance reads the same value. No service caches data yet. Redis also holds the service tokens and the exchanged tokens of each service, without encryption (an accepted risk), with a time to live of the token lifetime, and the short locks that give one token fetch across the instances. No instance keeps a token in process memory. While Redis is down, every outgoing call fetches its own token from Keycloak (an accepted risk), and the Redis circuit breaker makes each Redis call fail fast. Every Redis call goes through one Polly circuit breaker (from `Microsoft.Extensions.Resilience`); the service reports `Degraded` while it is open, and only the calls that guard copies or load fall back. Redis must stay on a private network with authentication. Redis holds no source data.
- **Azurite:** blob storage for the Document service in development.
