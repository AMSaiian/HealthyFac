# Testing Rules
*   **Testing Stack:** Use xUnit, Testcontainers (PostgreSQL, RabbitMQ, Keycloak, Redis), FluentAssertions v7, and Bogus. Give every faker a fixed seed (`new Faker { Random = new Randomizer(seed) }` or `Faker<T>.UseSeed(seed)`). Keep exact literals for values that an assertion checks by content.
*   **FluentAssertions v7:** Never upgrade to v8 or later (commercial license). Never use xUnit `Assert.*`.
*   **Containers:** Start each container type through its class in `HealthyFac.Testing/Containers` (e.g., `PostgreSqlTestDatabase`), with an image constant from `TestImages`. Keep each tag equal to the same service in `docker-compose.yml`. Never repeat a tag, use a module default image, or reference a Testcontainers module from a test project. A fixture holds an instance and adds only its own services and schema.
*   **Fixture Helpers:** Write the shared arrange and query helpers of a feature as an `extension(<Fixture> fixture)` block in `Data/` (e.g., `Employees/Data/EmployeeInviteFixtureExtensions.cs`). Do not derive a fixture only to add helpers. Keep test data constants in static `<Feature>TestData` classes.
    *   **Scopes:** A fixture exposes `IServiceScopeFactory` and the singletons that tests use, never the root `IServiceProvider`. Every database helper opens its own scope per call, so it reads what is stored, not tracked objects.
*   **Fakers:** Reuse the service fakers (`<Feature>/Seeding/<Entity>Faker` in Infrastructure, exposed with `InternalsVisibleTo`), so tests and the development seed share one shape. Write a test faker in `Data/` only for another shape or extra behavior.
*   **Theory Data:** Never use `[InlineData]`. Use `[MemberData(nameof(...), MemberType = typeof(...))]`, `TheoryData<...>`, or `[ClassData]`, from a file in a `Data/` folder next to the test class (e.g., `Feature/Data/FeatureTestData.cs`). Never put test data inside the test class.
*   **Naming:** Name test methods `UnitOfWork_StateUnderTest_ExpectedBehavior` (e.g., `Encrypt_WithSameGuidAndKey_ProducesExactSameCiphertext`).
*   **Structure:** Arrange, Act, Assert, separated by one blank line each, with no section comments.
    *   **Act:** One statement: the call under test with its result in a variable, or `var act = () => ...;` for an expected exception. Never call the code under test inside an assertion.
    *   **Assert:** Read the state first (e.g., `var invite = await fixture.LoadInviteAsync(...)`), one blank line, then the assertions. Never query between assertions. Keep the assertions on one object together, and separate the groups by one blank line.
*   **Modifiers:** Declare a test class `public sealed class` (`public class` only when another test class derives from it), and test methods `public void` or `public async Task`.
*   **Global Usings:** Declare `<Using Include="Xunit" />` and `<Using Include="FluentAssertions" />` in the `.csproj`, never `using Xunit;` or `using FluentAssertions;` in a file.
*   **No Tests for Boilerplate:** Write a test only when the code can fail for a reason other than a typo. Never test auto-properties, DTO or record construction, initializers, constructor assignment, pass-through delegation, EF Core configurations, service registration, or framework and library behavior. Test business rules, own validation logic, branching, calculations, error paths, and integration boundaries.
    *   **Validators:** Test a rule only when it has logic of its own: a custom predicate (test it once, where it is defined), a `When` or `Unless` condition, a rule across properties or items, or a business boundary (test both edge values). Never test a single built-in rule (`NotEmpty`, `MaximumLength`, `EmailAddress`, a comparison with a constant).
    *   **Registration Guarantee Exception:** Test a registration helper that enforces a shared-instance or transaction guarantee (e.g., `AddMessagingDbContext`), because a wrong registration there breaks data integrity without an error.
*   **Prove a Test Can Fail:** A test of a guard, a retry, a transaction, a filter, or another safety measure must fail when that measure is missing, not pass for another reason (e.g., a framework retry).
    *   **Red Step:** A test written before the measure proves itself when it fails on its assertion in the TDD red step. A compile error proves nothing: compile against an empty stub first.
    *   **Extra Proof:** Disable the measure for one extra run only when the measure existed before the test, when the test proves a concurrency guard, or when the plan names the proof. Run only that test (`dotnet test --filter`), restore the code, and check it with `git diff`.
    *   **Report:** One line per proof: the test, the red step or the disabled measure, and the failure message.
*   **Absence Tests:** A test that asserts that something does not happen (no span, no row, no email) needs a sibling test that asserts that it happens under the right condition.
*   **Race Tests:** A test of a concurrency guard (a row version, a unique index, a lock) must force the race: `Task.WhenAll` does not make calls overlap. Run each call through `ConcurrentSaveGate.StartRace(n)` and `RunAsync` (`HealthyFac.Testing`), which holds each first save until every call has read its data. Assert the save count of each call, then one exact outcome (e.g., one success and one `ConflictException`). Never accept "succeeds or conflicts".
*   **Test Runs:** While you work, run only the tests of the changed projects (`dotnet test <project> --filter ...`). Run the full solution (`dotnet test backend/HealthyFac.slnx`) once before the report, unless the plan asks for more.
*   **Architecture Tests:** Keep one `<Service>.ArchitectureTests` project per service.
    *   **Layer Dependencies:** Use `NetArchTest.eNhancedEdition`, with each forbidden dependency as a `(layer, namespace)` pair in the test data.
    *   **Conventions:** `ConventionChecks` (`HealthyFac.Testing/Conventions`) checks rules by reflection: options section names, extension prefixes, technical root folder names, boolean prefixes, `Internal` step names, captured primary constructor parameters, positional records, direct `IRequestHandler<TRequest>` implementations, controllers, convention-based middleware, and concrete `DbContext` injection in Application. Run every check over every assembly of the service. Add a check there when a rule can be verified by reflection.
