# Testing Rules
*   **Testing Stack:** Use `xUnit` as the test runner, `Testcontainers` for integration environments (PostgreSQL, RabbitMQ, Keycloak), and `FluentAssertions` (v7.x) for all assertions. Use `Bogus` for generated test data. Give every faker a fixed seed (`new Faker { Random = new Randomizer(seed) }` or `Faker<T>.UseSeed(seed)`), so every test run uses the same data. Keep exact literals for values that an assertion checks by content.
*   **Container Images:** Start every Testcontainers container with a constant from `TestImages` in `HealthyFac.Testing`. Never repeat an image tag in a test project, and never use the default image of a Testcontainers module. Keep each tag equal to the image of the same service in `docker-compose.yml`.
*   **Shared Containers:** Start each container type through its class in `HealthyFac.Testing/Containers` (e.g., `PostgreSqlTestDatabase`). A fixture holds an instance and adds only its own services and schema. Add a class there for each new container type (e.g., RabbitMQ, Keycloak). Do not reference a Testcontainers module from a test project directly.
*   **Fixture Helpers:** Write the shared arrange and query helpers of a feature as an `extension(<Fixture> fixture)` block in `Data/` (e.g., `Employees/Data/EmployeeInviteFixtureExtensions.cs`), so tests call `fixture.LoadInviteAsync(id)`. Do not derive a feature fixture only to add helpers. Keep test data constants in static `<Feature>TestData` classes.
    *   **Scopes:** A fixture exposes `IServiceScopeFactory` and the singleton services that tests use, never the root `IServiceProvider`. Every database helper opens its own scope per call, so each step uses a fresh context and reads what is stored, not tracked objects.
*   **Fakers:** Reuse the feature fakers of the service (`<Feature>/Seeding/<Entity>Faker` in Infrastructure), so tests and the development seed share one entity shape. Infrastructure exposes them to its test projects with `InternalsVisibleTo`. Write a test faker in `Data/` only when a test needs another shape or extra behavior.
*   **FluentAssertions v7:** Always use `FluentAssertions` v7 (Apache 2.0). Never use `Assert.*` methods from xUnit. Never upgrade to FluentAssertions v8+ due to commercial licensing restrictions.
*   **Theory Data (No InlineData):** Never use `[InlineData]`. Always use `[MemberData(nameof(...))]` with strongly-typed static member properties/methods, or dedicated `TheoryData<...>` / `ClassData` providers.
*   **Test Data Separation (Data/ Subfolder):** Never inline test data or `TheoryData` properties inside the test class. Always extract test data into a dedicated file located in a `Data/` subfolder adjacent to the test class (e.g., `Feature/Data/FeatureTestData.cs`). Reference it via `[MemberData(nameof(FeatureTestData.DataProperty), MemberType = typeof(FeatureTestData))]` or `[ClassData]`.
*   **Naming Convention:** Test methods must follow `UnitOfWork_StateUnderTest_ExpectedBehavior` (e.g., `Encrypt_WithSameGuidAndKey_ProducesExactSameCiphertext`).
*   **Structure:** Follow Arrange-Act-Assert flow without writing inline `// Arrange`, `// Act`, `// Assert` comments. Separate the sections with one blank line each.
    *   **Act:** Write one statement: the call under test, with its result in a variable (e.g., `var isValid = service.IsValid(token, salt);`), or `var act = () => ...;` for an expected exception. Never call the code under test inside an assertion.
    *   **Assert:** First read the state to check (e.g., `var invite = await InviteQueries.LoadInviteAsync(...)`), then one blank line, then the assertions. Never open a scope or run a query between assertions; put the query in a helper in `Data/`.
    *   **Grouping:** Keep the assertions on one object together. Separate the groups for different objects with one blank line.
*   **Modifiers:** Declare a test class as `public sealed class`. Use `public class` only when another test class derives from it. Declare test methods as `public void` or `public async Task`.
*   **Global Usings:** Test projects must declare global usings for `Xunit` and `FluentAssertions` via `<Using Include="Xunit" />` and `<Using Include="FluentAssertions" />` in their `.csproj` file. Individual test files must not declare local `using Xunit;` or `using FluentAssertions;`.
*   **No Tests for Boilerplate:** Never write tests for boilerplate or trivial code. Do not test auto-properties, plain DTO or record construction, object initializers, constructor assignment, pass-through methods that only delegate to a dependency, EF Core entity configurations, or service registration. Do not test the framework or third-party library behavior. Test real logic instead: business rules, validation outcomes, branching, calculations, error paths, and integration boundaries. Apply one check before you write a test: can this code fail for a reason other than a typo? Write the test only when the answer is yes.
*   **Prove a Test Can Fail:** A test of a guard, a retry, a transaction, a filter, or another safety measure must fail when that measure is missing. Check it once: disable the measure, run the test, see it fail, then restore the code. Report this check. A test that passes for another reason (e.g., a framework retry that hides the missing measure) proves nothing.
    *   **Absence Tests:** A test that asserts that something does not happen (e.g., no span, no row, no email) needs a sibling test that asserts that it happens under the right condition. Then the absence test cannot pass only because the capture or the query is broken.
*   **Race Tests:** A test that proves a concurrency guard (a row version, a unique index, a lock) must force the race. `Task.WhenAll` only starts the calls; it does not make them overlap. Run each call through `ConcurrentSaveGate.StartRace(n)` and `RunAsync` (`HealthyFac.Testing`). The gate holds the first save of each call until every call has reached it, so every call has read its data before any call saves. Assert the save count of each call, so a new earlier save in the handler fails the test. Then assert one exact outcome (e.g., one success and one `ConflictException`). Never accept "succeeds or conflicts": that test passes when the guard is missing.
*   **Registration Guarantee Exception:** Test a registration helper when it enforces a shared-instance or transaction guarantee (e.g., `AddMessagingDbContext`). A wrong registration there breaks data integrity without an error.
*   **Architecture Tests:** Use `NetArchTest.eNhancedEdition` for layer dependency tests. Keep one `<Service>.ArchitectureTests` project per service (e.g., `HealthyFac.Core.ArchitectureTests`). List each forbidden dependency as a `(layer, namespace)` pair in the test data.
