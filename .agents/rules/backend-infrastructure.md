# Infrastructure Layer Rules
*   **ORM:** Use Entity Framework Core.
*   **Datetimes:** Use the BCL types. Do not add NodaTime.
    *   **Past Instants:** Store a moment that already happened (e.g., `CreatedAt`) as `timestamp with time zone`, in a `DateTime` with `DateTimeKind.Utc`.
    *   **Future Local Times:** Store a planned local time (e.g., a shift start) as `timestamp without time zone` in a `DateTime` with `DateTimeKind.Unspecified`, plus the IANA zone ID in a `text` column. The local time and the zone are the source of truth.
    *   **Derived UTC Column:** Add a UTC copy only when a use case must filter, sort, or index future local times across zones. Store it as `timestamp with time zone` next to the local time (`StartsAtLocal`, `StartsAtUtc`). Compute it with `TimeZoneInfo.ConvertTimeToUtc` in the entity method that sets the local time or the zone. Zone rules can change, so display the local time and the zone, never the copy.
    *   **Dates and Times Only:** Use `DateOnly` (`date`) or `TimeOnly` (`time`) only when the use case has no time or no date part.
    *   **Time Zone IDs:** Store every zone as an IANA ID (e.g., `Europe/Kyiv`). Validate it with `TimeZoneInfo.TryFindSystemTimeZoneById`.
*   **Text Comparison:** Every text column compares case-insensitively through the `case_insensitive` collation (`UseCaseInsensitiveText()`). Opt out per property with `IsCaseSensitive()`. Never lower-case a column or a value to compare. A regular expression on a text column needs `COLLATE "default"`. `TextCollationModelTests` checks the Core model.
*   **Query Filters:** Give every query filter a name from a constant (`HasQueryFilter(name, ...)`). A query that must see filtered rows ignores only the filters it names (`IgnoreQueryFilters([name])`). Never ignore all filters. The banned API analyzer checks it (`backend/BannedSymbols.txt`).
*   **Auditing:** The `AuditableEntityInterceptor` (a `SaveChangesInterceptor`) sets `CreatedAt`, `CreatedBy`, `UpdatedAt`, and `UpdatedBy` for `Added` and `Modified` entries.
*   **DbContext Implementation:** Name the context after its service (`CoreDbContext`). Derive it directly from `DbContext`; add no shared base context. Implement the Application interface of the service, `IOutboxDbContext`, and `IInboxDbContext`.
    *   **Messaging Tables:** In `OnModelCreating`, call `ApplyOutboxConfiguration()` and `ApplyInboxConfiguration()` before `ToSnakeCaseConventions()`, because the pending-message index filters use snake case column names.
    *   **Registration:** Register the context only with `AddMessagingDbContext<TInterface, TContext>()`. It maps all its interfaces, `IOutbox`, and `IInbox` to one scoped instance. A separate registration creates a second instance and splits the transaction.
    *   **One Scope:** Never create a DI scope or use `IDbContextFactory` inside a use case. A second context leaves the business transaction.
    *   **Transactions:** Copy both `RunInTransactionAsync` methods and the private attempt method from `CoreDbContext` without changes. Never move them into a helper, an extension, or a default interface method. Each attempt runs inside `Database.CreateExecutionStrategy().ExecuteAsync(...)`, because the retry strategy (`EnableRetryOnFailure`) rejects any other transaction. The method never calls `SaveChangesAsync`: the operation saves.
*   **Entity Configuration:** Give every entity its own `IEntityTypeConfiguration<TEntity>` file in the feature `Persistence/` folder (`/Machines/Persistence/MachineConfiguration.cs`). Apply the baseline with `ConfigureEntity()` and `ConfigureAuditable()`. `OnModelCreating` holds only model-wide settings (extensions, snake case), never entity properties or keys.
*   **Relationship Configuration:** Configure each relationship once, in the configuration of the dependent entity. Pass a lambda for each declared navigation (`HasMany(employee => employee.Departments)`), and use the overload without a lambda for a side without one (`HasOne<Company>().WithMany()`). A missing lambda for a declared navigation makes EF Core create a second relationship (`backend-domain.md`, **Navigations**).
*   **Check Constraints:** Mirror each stateless validator rule (not blank, length, range, not empty GUID, enumeration values) with a check constraint from `HealthyFac.Shared.Infrastructure.Persistence.CheckConstraints` (`HasNotBlankCheck`, `HasLengthCheck`, `HasRangeCheck`, `HasNotEmptyGuidCheck`, `HasEnumerationCheck`). Do not mirror stateful rules. Register every enumeration with `HaveEnumerationConversion<T>()` in `ConfigureConventions`, or EF Core treats it as an entity. Add a migration with each new constraint or enumeration member change.
*   **Outbox and Inbox:** Use them only when a use case sends or receives messages across services.
    *   **Outbox:** Save each outgoing message as an outbox row in the transaction of the business change. A background processor publishes the pending rows and sets `ProcessedOn`.
    *   **Inbox:** Save each received message as an inbox row, keyed by the unique message ID, before you handle it, so a duplicate makes no second row. A background processor handles the pending rows and sets `ProcessedOn` in the transaction of the business change.
    *   **Filtered Index:** Index both tables with the filter `processed_on IS NULL`, so the processors scan only pending rows.
*   **linq2db:** Use EF Core for every query and write. Use `linq2db.EntityFrameworkCore` only in Infrastructure, only for what EF Core cannot express: row lock hints (`FOR UPDATE SKIP LOCKED` in the claim queries) and other PostgreSQL hints.
    *   Never write through linq2db: EF Core writes keep the interceptors, the `xmin` check, and the transaction.
    *   Never expose a `LinqToDB` type to Application or Web (architecture tests check it). Reference the package only in `HealthyFac.Shared.Infrastructure`.
    *   Start each query from a `DbSet` with `ToLinqToDB()`, never a separate `DataConnection`, so it shares the connection and the transaction. Run it inside `RunInTransactionAsync`, or a row lock ends at once.
    *   linq2db returns untracked entities. Attach them before you change them, so the save checks concurrency.
*   **Caching:** Cache data only in Redis, through the shared `IConnectionMultiplexer` of `AddSharedRedis`. Never keep cached data in process memory. Every instance then reads the same value, and one delete removes an entry for all instances. Never use FusionCache, `HybridCache`, `IMemoryCache`, or `IDistributedCache`.
    *   **Layer Boundary:** Hide the cache behind an Application interface (e.g., a permission reader). Implement it in Infrastructure. Never inject `IConnectionMultiplexer` in Domain or Application.
    *   **Entries:** Give every entry a time to live and a fixed key format that starts with the service name (`{Service:Name}:...`), so two services never share a key by accident. Add a random jitter to the time to live, so entries written at the same moment do not expire together. Delete the entry in the use case that changes the source data.
    *   **One Fetch:** When an entry is missing, one call fetches it from the source. Every other call, in every instance, waits on a Redis lock with a time to live and reads the entry again (as in `TokenStore`). Keep no lock or state in process memory.
    *   **Source of Truth:** The cache holds copies only. A Redis failure must never fail the request: log a `Warning` and read the source. Never return an old value for permissions.
    *   **Shared State Is Not a Cache:** A value that services exchange through Redis (e.g., the token revocation list) or a Redis operation (e.g., the rate limiter counters) uses `IConnectionMultiplexer` directly, with a fixed key format. It gets no jitter: a revocation entry lives exactly as long as the token that it blocks.
    *   **Redis Circuit Breaker:** Run every Redis call through the shared Redis pipeline of `AddSharedRedis` (Polly, through `Microsoft.Extensions.Resilience`). An open breaker throws `BrokenCircuitException` at once, so no call waits for a Redis timeout. Catch it in the same `catch` as `RedisException` and `RedisTimeoutException`. Never reference a `Polly.*` package directly.
        *   **Fallback:** A call may go on without Redis only when Redis holds a copy or protects load (a cache entry, a token, the token lock, the rate limiter counters, the revocation read). A Redis lock that guards correctness (e.g., one writer or one run of a job) never falls back: when the breaker is open or the lock call fails, the call fails at once.
        *   **Health:** The breaker health check reports `Degraded` while the breaker is not closed, never `Unhealthy`.
    *   **Tokens:** Keep access tokens only in the token store of `AddServiceTokens` (Redis, `TokenCacheKeys`, the token lifetime as the time to live). The tokens are not encrypted, so Redis stays on a private network with authentication. Never put a token in process memory, a database, a message, or a log.
*   **HTTP Failures:** When a failed outgoing call must throw, call `await response.EnsureSuccessAsync(cancellationToken)` (`HealthyFac.Shared.Infrastructure.HttpFailures`). Never call `EnsureSuccessStatusCode` or the `HttpClient` methods that check the status inside (`GetFromJsonAsync`, `GetStringAsync`, `GetByteArrayAsync`, `GetStreamAsync`). Handle the expected codes (e.g., a `409` "already a member") before the check, and read the content after it.
    *   **Error Formats:** For an API with a new error format, add a format reader to `HttpErrorReasonReaders.Default`. A reader reads only allow-listed root fields of the JSON kind that its standard defines. Never put a raw response body, a request body, or a query string into an exception or a log.
*   **Health Checks:** A dependency that the service can work without (e.g., the broker, because the outbox keeps messages) reports `Degraded`, never `Unhealthy`, because `Unhealthy` takes the service out of the load balancer and the gateway. Reuse one cached connection or client per check, and give each check its own short timeout.
