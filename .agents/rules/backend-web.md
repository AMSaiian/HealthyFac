# Web Layer Rules
*   **API Paradigm:** No MVC Controllers. Use Minimal APIs exclusively.
*   **API Contracts:** Bind the Application request directly in the endpoint, and return the Application response. Do not define Web request or response records, and do not map between Web and Application types, except for server-owned values.
    *   **Server-Owned Values:** When the Application request holds a value that comes from the server and not from the client (e.g., `CompanyId` from the token), define a Web request record without that value. Give it the name of the Application request (e.g., `CreateEmployeeInviteRequest`), and put it in its own file in the Web feature folder. In the same file, add a static class `<UseCase>RequestExtensions` with an extension method `ToApplicationRequest(<server values>)` on the Web request (C# 14 `extension` block) that builds the Application request. The endpoint binds the Web request and calls `request.ToApplicationRequest(...)`; it never builds the Application request itself. Never use `[JsonIgnore]` for this. The response stays the Application response.
        *   **Application Prefix:** Inside the Web namespace, the short name means the Web request. Write the Application request with the `Application.` namespace prefix (e.g., `Application.Employees.CreateEmployeeInvite.CreateEmployeeInviteRequest`), in the extension method and in the handler type of the endpoint. Never add a `using` alias for it.
*   **Endpoint Grouping:** Put all endpoints of one feature in one `<Feature>Endpoints.cs` file (e.g., `Employees/EmployeeInviteEndpoints.cs`) with one `Map<Feature>Endpoints` method and its route constants class next to it (e.g., `EmployeeInviteRoutes`). Write each route handler as a private static method in that file and map it as a method group. Do not create a file or a folder per route.
*   **Handler Injection:** Inject the specific generic `IRequestHandler<TRequest, TResponse>`, or `IRequestHandler<TRequest>` for a use case without a result, directly into the Minimal API delegate. Do not inject a mediator or dispatcher.
*   **Request Logging:** Call `UseSerilogRequestLogging()` in `UseApiPipeline` before `UseSharedExceptionHandling`. The request log then records the status code that the client receives. Never write logs with `Console` or `Debug`.
*   **Middleware:** Write each middleware as a class that implements `IMiddleware`, with its dependencies in a primary constructor (`backend-general.md`, rule **Dependency Fields**). The container creates it through `IMiddlewareFactory`.
    *   **Registration:** Register it next to the services of its concern, with the lifetime of its shortest-lived dependency: `AddSingleton` when every dependency is a singleton (e.g., `ProxyErrorMiddleware`), `AddScoped` when one dependency is scoped (e.g., `ActorContextMiddleware`). A singleton middleware never injects a scoped service.
    *   **Pipeline:** Add it with `UseMiddleware<TMiddleware>()` inside a `Use...` extension method. A missing registration fails at the first request, so the tests of the pipeline cover it.
    *   **Forbidden:** convention-based middleware (a constructor with `RequestDelegate next` and an `InvokeAsync(HttpContext, ...)` that takes services as parameters), and inline middleware lambdas (`app.Use(async (context, next) => ...)`).
*   **Health Endpoints:** Serve `/health`, `/health/ready`, and `/hc` only on the internal health port (`HealthEndpoints:Port`). Call `UseSharedHealthChecks()` as the first middleware of the pipeline. It compares the local port of the connection, which a client cannot change. Never use `RequireHost` for this, because it reads the `Host` header that a client sends. Never publish the health port through the gateway or a public load balancer. The gateway forwards only the versioned API paths of a service (e.g., `/api/core/v1/...`).
*   **Public URLs:** Address each public service by its logical name: `api.<domain>` (the gateway API routes), `auth.<domain>` (Keycloak through the gateway, the token issuer), and `app.<domain>` (the web app). Use these names for the issuer, redirect URIs, links in emails, and CORS origins. Never use `localhost` in a public URL. Every public URL uses HTTPS: the gateway ends TLS with the certificate in `docker/certs/` (created with mkcert, never committed), and the traffic behind the gateway stays HTTP, as behind a cloud ingress. Development tools (admin consoles, Mailpit, Grafana, health ports) stay on `localhost`. The gateway matches each route to its name with YARP `Match.Hosts`. Set the names per environment (`appsettings.Development.json`, Compose); `appsettings.json` holds no names.
*   **CORS:** The gateway owns CORS. Register it with `AddSharedCors`, call `UseSharedCors()` before `UseAuthentication`, and set `"CorsPolicy"` on each YARP route that the web app calls. A service behind the gateway keeps `Cors:Enabled = false`, because two layers that write `Access-Control-Allow-Origin` make the browser reject the response. Keycloak answers CORS for its own routes from the `webOrigins` of each client; the gateway adds no CORS headers there.
*   **Fallback Policy:** Every service that maps endpoints, and the gateway, call `SetAuthenticatedFallbackPolicy()` on their authorization builder. A service without endpoints (e.g., a message worker that serves only the health port) registers no authentication and no authorization. An endpoint or a YARP route without authorization metadata, and a request that matches no endpoint, then require a signed-in user. Mark each public endpoint with `AllowAnonymous()`, and each public YARP route with `"AuthorizationPolicy": "anonymous"`. Health requests and CORS preflights do not reach authorization, because their middleware answers first.
*   **Permissions:** Define the permissions of a service in one `<Service>Permissions` class in the Web folder `Authorization/` (e.g., `CorePermissions`). Give each feature a nested static class with a `const string` for each permission and a `public static readonly FrozenSet<string> All` that lists them with a collection expression. The service class has its own `All`, which spreads the `All` of every feature. Register the policies once with `AddPermissionPolicies(<Service>Permissions.All)`. Reference a permission as `<Service>Permissions.<Feature>.<Action>` (e.g., `CorePermissions.Employees.Invite`). Never list permission names inline.
    *   **Roles and Permissions in Keycloak:** Each permission is a client role of the API client of the service (e.g., `healthyfac-core`). That client holds permissions only. A job role (e.g., `supervisor`, `worker`) is a composite realm role that groups permissions, and it may group permissions of several APIs. A client role mapper writes the effective client roles of the API client into the flat `permissions` claim (`KeycloakClaimTypes.Permissions`), and the policies read that claim. Never tell a permission from a role by the format of its name.
*   **Configuration & FluentValidation:** Strongly-typed configuration options (classes bound to configuration sections via the Options pattern) must be validated using FluentValidation (`AbstractValidator<TOptions>`). Enforce validation at application startup with `.ValidateOnStart()` (e.g., via `AddValidatedOptions<TOptions, TValidator>()`) so misconfigured settings fail fast before requests are served. Never rely on unvalidated configurations or ad-hoc manual checks scattered across services.
*   **Service Registration Grouping:** Group related service registrations under dedicated extension classes (`ConfigureServices.cs`). Do not scatter registrations in `Program.cs`. Encapsulate related dependencies into private extension methods named after their concern (see Concern Grouping). Expose a high-level registration method (e.g., `AddApiServices`) for the Web project.
*   **Concern Grouping:** Group registrations that serve one concern into a private `Add...` method named after the concern, such as `AddApiLogging`, `AddApiSerialization`, `AddApiSecurity`, or `AddApiObservability`. Create a group only when the concern needs three or more calls. Leave one or two calls in the caller. `AddApiServices` calls the groups and the loose calls in order. Apply the same rule to `UseApiPipeline` (group by pipeline stage) and `MapApiEndpoints` (group by feature). Do not split by line count.
*   **Pipeline and Route Grouping:** Group middleware pipeline configuration into dedicated `Use...` extension methods (e.g., `UseApiPipeline`). Group API route mappings into dedicated `Map...` extension methods (e.g., `MapApiEndpoints`).
*   **Database Initialization and Seeding Hooks:** Provide an initialization extension method (e.g., `InitializeDatabaseAsync`) on `IServiceProvider` in the Infrastructure layer, so every host shape can call it. `Program.cs` calls it after the host builds. Resolve the initializer of the service (e.g., `ICoreDbInitializer`) within a created service scope. Execute database migrations using `ApplyDatabaseStructureAsync`. The initializer migrates only when the environment is Development. Apply migrations in every other environment through a deployment step. Execute required data seeding (e.g., measurement units) using `SeedRequiredDataAsync`. Execute optional data seeding (e.g., Bogus mock data) using `SeedOptionalDataAsync` when enabled in configuration.
