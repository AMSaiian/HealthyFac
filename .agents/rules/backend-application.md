# Application Layer Rules
*   **Use Cases:** Do not use MediatR. Use the interfaces in `HealthyFac.Shared.Application.UseCases` (`IRequest`, `IRequest<TResponse>`, `IRequestHandler`). Register use cases only with `AddUseCases`.
    *   **Without a Result:** The request implements `IRequest`. The handler derives from `RequestHandler<TRequest>` and implements `HandleInternalAsync`. Never implement `IRequestHandler<TRequest>` directly: only the shared adapter does, so every call runs through the decorators (architecture tests check it).
    *   **One File:** Put the request, its response, its input validator, its pre-handler check, and its handler in one use-case file, `<UseCase>.cs`. An integration message keeps its own file (**Integration Messages**).
    *   **Response Records:** Return a response record, never a bare value such as a `Guid` (e.g., `CreateMachineResponse { Id }`). The endpoint returns it unchanged. A use case without a result returns nothing, and its endpoint returns `204 No Content`.
*   **Validation:** Use FluentValidation only for stateless input checks (lengths, nulls, ranges). Put stateful business rules (e.g., uniqueness queries) in the handler. Never call `.ValidateAsync()` in a handler: the `ValidationRequestHandlerDecorator` runs the validators.
    *   **Pre-Handler Check:** Every use case has one `IPreHandlerCheck<TRequest>` in its use-case file. It checks the company scope only. A scope check on a parent resource (e.g., the machine of a status definition) loads it in the check and throws `NotFoundException` (`404`); the scope filter of the loaded resource stays in its handler query. Other stateful rules stay in the handler. A use case without a scope rule derives an empty sealed class from `PassThroughPreHandlerCheck<TRequest>`. `AddUseCases` fails at startup without one pre-handler check for a request. Run order: logging, validation, pre-handler check, downstream scope, handler.
    *   **Integration Messages:** A consumed message implements `IRequest`, and its handler derives from `RequestHandler<TMessage>`. Its `AbstractValidator<TMessage>` stays in the contract file (**Message Contracts**). The validator runs when the inbox processes the row. A failure marks the row failed at the first attempt, with no retries, because no retry can fix it. Never validate a message inside its handler.
    *   **Text Input:** The shared JSON options of the API and the messages normalize every string on read (CRLF to LF, trim, NFC). Every validator gives each string member `SingleLineText()` or `MultilineText()`, and each string list `RuleForEach(...).SingleLineText()`. Never trim a string or remove a character in a handler: reject it. `ConventionChecks` checks that no string is left without a text rule.
*   **Message Contracts:** The producing service owns each integration message. Put it in the project `HealthyFac.<Service>.Messaging` (e.g., `HealthyFac.Core.Messaging`), one file per message with its `AbstractValidator<TMessage>`. The producer and every consumer reference that project. Never copy a contract into a consumer: two messages with the same `MessageType` or the same type name count as a copy. The project references only `Shared.Application`, never a layer of any service (architecture tests check it). The contract implements `IIntegrationMessage`, and `IRequest` too when a service consumes it. The consumer keeps the handler and the pre-handler check. Define the error messages and limits in the project (`<Feature>MessageErrors`).
*   **Authorization:** Split each check by what it needs.
    *   **Static Permission (Web):** A check that the token alone answers is an endpoint policy (`backend-web.md`, **Permissions**). Never repeat it in the handler.
    *   **Rule That Needs Data (Application):** A check that needs stored data (the company, the owner, stored permissions) belongs in the use case, so HTTP, messages, and jobs all apply it. Never write it as a Web authorization handler, a middleware, or an endpoint filter.
    *   **Data Scope:** Filter the query by the actor scope (e.g., `invite.CompanyId == request.CompanyId`). A resource outside the scope is "not found" (`NotFoundException`), so the answer does not show that it exists.
    *   **Repeated Rule:** When many use cases need the same check in the same form (e.g., company-configured permissions), the request declares its need, and an authorization decorator checks it before the validation decorator. Infrastructure loads the stored permissions behind an Application interface, with a cache.
    *   **Actor Data:** Read the actor through `ICurrentUserProvider`. Never read ASP.NET claims in Application. The actor holds no permissions: endpoint policies check the token permissions in Web (**Static Permission**). A message-triggered use case needs none, because the sender checked them. Add permissions to `ActorContext` only when a use case must read the token permissions, and fill them in the Web reader.
    *   **Service Calls:** A flow that calls another of our services declares its downstream scopes: a use case with `[DownstreamScopes(...)]` on its request, other work with `IDownstreamScopeHolder.Enter(...)`. A nested use case gets only its own downstream scopes. The scopes narrow only the service token: a call on behalf of a user carries the user permissions. Prefer one downstream scope per use case, and run background work as a use case. The target restores the actor of the call and gives it no rights of its own.
    *   **Message or Call:** Send a message when the flow does not need the result and the target may be down for a while. Call when the flow needs the answer or the change at once.
*   **Time:** Inject `TimeProvider` and read `timeProvider.GetUtcNow().UtcDateTime`. Register it with `AddSharedTime()`. Never use `DateTime.UtcNow` or `DateTimeOffset.UtcNow`. Tests use `FakeTimeProvider`.
*   **Cross-Cutting Concerns:** When every use case needs a concern in the same form, implement it as a request handler decorator registered with Scrutor (e.g., `LoggingRequestHandlerDecorator`). Keep logic that varies between use cases in the handler.
*   **DbContext Access:** Declare every `DbSet<TEntity>` on `ICoreDbContext` and inject that interface. Never inject `CoreDbContext` or a plain `DbContext` (architecture tests check it).
    *   **Allowed Leak:** `ICoreDbContext` exposes EF Core types and may mirror a `DbContext` member that a use case calls (e.g., `SaveChangesAsync`). Add a member only when a use case calls it. Do not add repositories.
    *   **Business Sets Only:** Never add the outbox or inbox sets to it.
    *   **Tracking:** Track only the entities that the use case changes. Load a read-only entity with `AsNoTracking()`. A query helper that a changing use case also uses stays tracked (e.g., `EmployeeInviteResolver`); do not split it. Never connect an untracked entity to a saved entity; load it tracked. Use `AsNoTrackingWithIdentityResolution()` when one result holds the same row more than once. A `Select` into a response or a scalar needs neither.
    *   **Transactions:** The service interface inherits `ITransactionalDbContext`. Call one `SaveChangesAsync` by default; generated IDs make a second save unnecessary (`backend-domain.md`, **ID Generation**). Use `RunInTransactionAsync` only when one save is not enough (e.g., lock a row, handle it, mark it processed). Inside the operation, read and change every entity and save with `SaveChangesAsync` as often as needed. The method only commits, and it throws on unsaved changes. Never commit or roll back inside the operation. Keep it safe to repeat, because a transient failure runs it again. Never open a transaction in another way.
*   **Cross-Service Messages:** Inject `IOutbox`, call `Add`, then call `SaveChangesAsync` once, so the outbox row and the business change commit together. Do not open a transaction only for this. Never publish to the broker from a handler (`backend-infrastructure.md`, **Outbox and Inbox**).
