# Application Layer Rules
*   **CQRS Pattern:** Do not use MediatR. Implement Use Cases via custom CQRS interfaces in `HealthyFac.Shared.Application.UseCases` (`IRequest`, `IRequest<TResponse>`, `IRequestHandler`).
    *   **Use Case Without a Result:** The request implements `IRequest`. The handler derives from `RequestHandler<TRequest>` and implements `HandleInternalAsync`. Never implement `IRequestHandler<TRequest>` directly: only the shared adapter does, so every call runs through the decorators. Register use cases only with `AddUseCases`.
*   **Validation Boundaries:** Use `FluentValidation` strictly for **simple, stateless input validation** (e.g., string lengths, null checks, safe ranges). **Do NOT** use FluentValidation for stateful business rules (e.g., querying the DbContext for uniqueness). Stateful business validation must remain in the application code inside the `IRequestHandler`.
    *   **Integration Messages:** A consumed message implements `IRequest`, and its handler derives from `RequestHandler<TMessage>`. Validate it with an `AbstractValidator<TMessage>` next to its contract (e.g., `Employees/Messages/EmployeeInvitedValidator.cs`). The validator runs in the validation decorator, when the inbox processes the row. A failure marks the row failed at the first attempt, with no retries, because no retry can fix it. Never validate a message inside its handler.
*   **Decorator Execution:** Do not call `.ValidateAsync()` manually inside the handler; stateless input validation is executed automatically by the `ValidationRequestHandlerDecorator`.
*   **Time:** Inject `TimeProvider` and read `timeProvider.GetUtcNow().UtcDateTime` for time. Register it with `AddSharedTime()` (from `Shared.Infrastructure.Time`). Never use `DateTime.UtcNow` or `DateTimeOffset.UtcNow` directly in application logic. Tests replace it with `FakeTimeProvider`.
*   **Cross-Cutting Concerns:** Implement a concern as a request handler decorator, registered with Scrutor, when every use case needs it in the same form (e.g., `ValidationRequestHandlerDecorator`, `LoggingRequestHandlerDecorator`). Keep logic that varies between use cases in the handler.
*   **Use Case Co-location:** Place the `IRequest`, its use-case-specific response, and its `IRequestHandler` in one use-case file.
    *   **Response Records:** A use case returns a response record, never a bare value such as a `Guid` or a `DateTime` (e.g., `CreateMachineResponse { Id }`). The Web endpoint returns it unchanged (`backend-web.md`, rule **API Contracts**). A use case without a result returns nothing, and its endpoint returns `204 No Content`.
    *   **Message Contracts:** A consumed message contract stays in `<Feature>/Messages/`, because the sender and the consumer both use it. Its handler is in the use case folder (e.g., `Employees/SendEmployeeInviteEmail/SendEmployeeInviteEmailRequestHandler.cs`).
*   **DbContext Access:** Declare every `DbSet<TEntity>` on the `ICoreDbContext` interface in the Application layer. Inject `ICoreDbContext` into handlers. Never inject the concrete `CoreDbContext` or a plain `DbContext`. Never reference the Infrastructure layer from Application.
    *   **Allowed Abstraction Leak:** `ICoreDbContext` exposes EF Core types such as `DbSet<TEntity>`. It may mirror a `DbContext` member signature that a handler needs (e.g., `SaveChangesAsync`). Add a member only when a use case calls it. Do not hide EF Core behind repositories.
    *   **Query Tracking:** Track only the entities that the use case changes.
        *   **Read-Only Entities:** Load an entity that the use case only reads with `AsNoTracking()`. A query helper that a changing use case also uses stays tracked (e.g., `EmployeeInviteResolver` for verify and accept); do not split it into a tracked and a read-only copy. Never connect an untracked entity to an entity that the use case saves; load it tracked instead.
        *   **Repeated Rows:** Use `AsNoTrackingWithIdentityResolution()` when one result holds the same row more than once (e.g., a list of invites that share departments), so each row becomes one instance.
        *   **Projections:** A `Select` into a response or a scalar needs neither.
    *   **Business Sets Only:** `ICoreDbContext` declares business sets only. Do not add the outbox or inbox sets to it.
    *   **Explicit Transactions:** The Application interface of the service inherits `ITransactionalDbContext` (Shared.Application). Call one `SaveChangesAsync` by default. Use `RunInTransactionAsync` only when one save is not enough (e.g., a message processor that locks a row, handles it, and marks it processed as one unit). The application generates IDs, so a dependent row never needs a second save (`backend-domain.md`, rule **ID Generation**). Read and change every entity inside the operation. The operation saves its own changes with `SaveChangesAsync`, as often as it needs. The method only commits, and it throws on changes that the operation did not save. Never commit or roll back inside the operation. Keep the operation safe to repeat, because a transient failure runs it again. Never open a transaction in another way.
*   **Cross-Service Messages:** When a handler sends a message to another service, inject `IOutbox` and call `Add`. Then call `SaveChangesAsync` on `ICoreDbContext` once, so the outbox row and the business change commit in one transaction. Do not open an explicit transaction only for this. Never publish to the broker from a handler. Read the **Outbox and Inbox** rule in `backend-infrastructure.md`.
