# Backend General Rules
*   **Variable Inlining:** Inline every expression. Declare a local variable only when:
    *   No other way resolves the value.
    *   It holds an `await` result, a LINQ query, or a chained call.
    *   Its name gives a business term to a condition or an intermediate result (e.g., `isMaintenanceDue`). When no business term fits, inline the expression.
*   **Awaited Results:** Store each awaited result in a variable before you use it. Never read a member of a parenthesized `await` (e.g., `(await LoadAsync()).Name`). Never block on a task (`.Result`, `.Wait()`, `.GetAwaiter().GetResult()`). The banned API analyzer checks it (`backend/BannedSymbols.txt`). An async method that uses an awaited result has a block body. Name an awaited condition (`var isEmailEmployed = await ...AnyAsync(...);`). In tests, chain FluentAssertions on the awaited task (`await act.Should().ThrowAsync<T>().WithMessage(...)`).
*   **Method Groups:** Pass a method group instead of a lambda that only forwards its parameters, in order, to one method (`.Select(ToResponse)`). The build reports it (IDE0200). Keep the lambda when the receiver can change before the call, the arguments differ (added, dropped, reordered, optional, `params`), the lambda does more than one call, or the group is ambiguous.
*   **Cancellation Tokens:** Every async operation that does I/O or waits observes a `CancellationToken`. Cancellation never leaves a unit of work half stored.
    *   **Signature and Flow:** Add `CancellationToken cancellationToken` as the last parameter. Keep `= default(CancellationToken)` only where the interface already has it. Pass the token to every call that accepts one (EF Core, `SaveChangesAsync`, HTTP, broker, `Task.Delay`, `SemaphoreSlim.WaitAsync`). An endpoint binds it, and a `BackgroundService` passes its `stoppingToken`. A framework signature without a token reads it from its context (`HttpContext.RequestAborted`, the Rebus message context). Pass `CancellationToken.None` only at a safe point or in tests.
    *   **Safe Points:** A unit of work is the set of changes that must be stored together. Inside one `SaveChangesAsync` or one `RunInTransactionAsync` operation, pass the token to every call: a rollback undoes the unit. After a durable step that a rollback cannot undo (a committed save, a published message, a Keycloak change, a sent email), choose one form and write the reason in the `<remarks>` of the method:
        *   **Finish:** Pass `CancellationToken.None` to the remaining steps. Keep them short.
        *   **Resume:** Store the progress after each step, and make each step safe to repeat ("find the user, else create it"). Example: the outbox processor leaves the row pending after a cancelled save, publishes it again with the same message ID, and the receiver inbox drops the duplicate.
        *   **Between Units:** A loop over units checks the token before each unit starts, never inside a unit that has a durable step.
    *   **Not a Failure:** Let `OperationCanceledException` propagate. Never record it as a failure (retry count, error text, `Error` log entry). A `catch` that records a failure adds `when (!cancellationToken.IsCancellationRequested)`.
    *   **Own Timeout:** For a shorter limit, link a source (`CancellationTokenSource.CreateLinkedTokenSource(cancellationToken)` with `CancelAfter`) and dispose it. `CancelAfter` uses the system clock: when a test must drive the limit with `FakeTimeProvider`, link `new CancellationTokenSource(delay, timeProvider)` with the caller token instead. Never use an unlinked token instead of the caller token.
*   **No Sentinel Values:** A method that can find nothing returns a nullable type (`Guid?`, `InboxMessage?`) or uses `Try...(out ...)`. Never let a valid value mean "nothing" (`Guid.Empty`, `-1`, `string.Empty`, `DateTime.MinValue`).
*   **Boolean Naming:** Prefix every boolean variable, field, property, and parameter with `is`, `has`, or `can` (architecture tests check all but local variables).
*   **Documentation (All or Nothing):** Decide for each type, member, and constant on its own.
    *   **Trivial:** Its name, signature, and types explain it. Write no comment.
    *   **Non-Trivial:** The code cannot show the reason: a constraint, a unit of measure, a side effect, an ordering requirement, a workaround, or complex logic. Write a `<summary>`, a `<typeparam>` and a `<param>` for each one, and a `<returns>` for a non-void result. Put the reason in `<summary>` or `<remarks>`. Never restate the name or the code. Reference symbols with `<see cref="..."/>` and parameters with `<paramref name="..."/>`.
    *   **Exceptions:** Document only the exceptions that the method throws itself, not the ones that bubble up. Name each with `<see cref="..."/>` in the description, and add an `<exception cref="...">` with the exact condition.
    *   **No Inline Comments:** Write no `//` comments that explain what code does, unless the user asks.
*   **Primary Constructors:** Use them only to inject dependencies into classes. Never use them for records: declare `{ get; init; }` properties. Assign each dependency to a `private readonly` field with the `_` prefix at the top of the class (`private readonly ICoreDbContext _dbContext = dbContext;`), and use only the fields, because a captured parameter is mutable. Fix CS9124; never suppress it. A parameter that only passes to the base constructor (`: DbContext(options)`) needs no field. Architecture tests check positional records and captured parameters.
*   **Layer Boundaries:** Keep Web -> Infrastructure -> Application -> Domain. `<Service>.Messaging` sits beside Domain: Application and Infrastructure of any service may reference it, and it references no service layer. The architecture tests check it.
*   **Screaming Architecture:** Name folders after what the code does, not after its technical type.
    *   Shared projects group by intent (`/IdEncryption/`, `/ErrorHandling/`). Services group by feature. A use case is one file in its feature folder (`/Machines/CreateMachine.cs`); it gets a folder only when it has 2 or more files (`/Employees/AcceptEmployeeInvite/`). Web groups by feature only (`backend-web.md`, **Endpoint Grouping**). Feature-wide definitions (`MachineErrors`) stay at the feature root.
    *   Root folders and their namespaces are plural (`/Machines/`), so they do not collide with the singular entity (CS0118).
    *   Move several files of one technical matter into a sub-folder of the business folder (`/Machines/Persistence/`). Never create technical root folders (`/Services/`, `/Models/`, `/Handlers/`; architecture tests check the names).
    *   **Nesting:** When 2 or more files of a folder serve one sub-intent that is narrower than the folder (one use case, one mechanism, one integration), move them into a sub-folder named after it (`/HttpFailures/ReasonReaders/`). Apply it in the service and the shared projects. Never create a sub-folder for one file, except the `Persistence/` and `Seeding/` folders that other rules name. No tool checks the sub-intent.
*   **Assembly Labels:** Read an assembly for a scan (e.g., `AddUseCases`, `ApplyConfigurationsFromAssembly`, `AddValidatorsFromAssembly`) only through its label class: a `public static class <Service><Layer>Assembly` at the project root with one member, `public static readonly Assembly Instance = typeof(<Service><Layer>Assembly).Assembly;`. Never read the assembly through another type (e.g., `typeof(MachineErrors).Assembly`), because a move or a rename of that type changes the scan without a compile error.
*   **Interfaces vs. Base Classes:** Use an interface to label a type, define a contract, or limit the types an API accepts (`IEntity`). Use a base class only to lock steps that every derived class must follow, never only to reuse logic; reuse through composition. `PassThroughPreHandlerCheck<TRequest>` is the one allowed base class that neither locks steps nor shares logic: it labels "no scope rule". Keep the public method non-virtual. Name the `protected abstract` step after it with `Internal` before `Async` (`HandleAsync` calls `HandleInternalAsync`), never `Core` or `Impl` (architecture tests check it).
*   **Object Initialization:** Use `init` properties and object initializers for plain data. Put logic where its inputs are:
    *   **One Property:** Logic that reads only that value (trim, normalize, a guard) goes into its `init` or `set` accessor with the `field` keyword (`init => field = EmailAddresses.Normalize(value);`). Every path then runs it: initializer, deserialization, constructor, entity method.
    *   **Several Properties:** Use a constructor or an entity method. It assigns through the properties, never through the backing fields.
    *   **Requests and Messages:** Their accessors only normalize, accept `null`, and never throw, because they run during deserialization. The validator checks the normalized value. Give each string a text rule in its validator (`backend-application.md`, **Text Input**).
    *   **One Definition:** When several types need the same logic, the accessors call one shared function (e.g., in Domain). Never copy it.
*   **No Magic Values:** In web, infrastructure, and business code, extract a literal into a named constant when a change to it would need edits in more than one place (numbers, strings, URLs, configuration keys, routes, policy names, validation limits). Put constants in a dedicated `static class` (`ValidationConstants`, `PolicyNames`, `CacheKeys`).
    *   **Always Inline:** `0`, `1`, `-1`, `true`, `false`, `null`, `string.Empty`, `Guid.Empty`, and log message templates.
    *   **Library Constants:** First search .NET and the referenced packages for a constant with the same meaning (`HeaderNames.RetryAfter`, `MediaTypeNames.Application.ProblemJson`, `StatusCodes.Status499ClientClosedRequest`, `JwtRegisteredClaimNames.Sub`), and compose from them (`$"{MediaTypeNames.Application.Json}; charset=utf-8"`). Add your own only when none fits or the project cannot reference that library.
    *   **One Definition:** Define each value once, in the lowest project that all users reference (e.g., Shared.Application). A route template of one feature stays in its routes class.
*   **Error Definitions:** Never inline error messages or throw exceptions with raw strings. Define errors in a feature `static class` (`MachineErrors`, `IdentityErrors`) with static instances or factory methods.
    *   **Data in Messages:** A message that names a checked value (a limit, a range, a count) interpolates the same constant into a `static readonly string`, so the text and the check cannot differ. A value known only at run time goes through a factory method parameter.
    *   **Numbers as Digits:** Write every number in a message as digits ("above 0 seconds", "at least 1 machine").
*   **File Separation:** Put each type in its own file. An options class keeps its `AbstractValidator<TOptions>` in its file, after the options class (`OptionsValidatorPlacementTests` checks it). Inline a type only when it is a helper that only that file uses. An Application use-case file holds the request, its response, its validator, its pre-handler check, and its handler (`backend-application.md`, **One File**). A nested request type (e.g., a grid filter) or an integration message and its validator also share one file. The Web layer defines no contracts, except a request record for server-owned values (`backend-web.md`, **API Contracts**).
*   **Required Modifier:** Use `required` with `init` for non-nullable properties of DTOs, requests, responses, and entities without invariants. Never use dummy defaults (`= string.Empty;`, `= default!;`). An entity with invariants sets its properties in a constructor and uses `private set` (`required` fails there with CS9032). A required reference navigation uses `= null!` (`backend-domain.md`, **Navigations**).
*   **Extension Method Prefixes:** `Add...` on `IServiceCollection` or `OptionsBuilder<TOptions>`, `Use...` on `IApplicationBuilder` or `WebApplication`, `Map...` on `IEndpointRouteBuilder` (architecture tests check every method that returns a value).
*   **Options Section Names:** Each options class (`*Options`) declares `public const string SectionName`; a child section needs none (architecture tests check it). Never put it in another constants class or hardcode it at registration. Compose a full path from it (`$"{IdEncryptionOptions.SectionName}:Keys"`), never as an extra constant.
*   **Constant Grouping:** When a constants class has 5 or more members or more than one concern, group the members into nested `static class` blocks named after their concern (`ProblemDetailsConstants.NotFound.Title`, `DatabaseConstants.Retry.MaxCount`). Never nest a class with 1 member.
*   **No Suppressions:** Never suppress an analyzer warning unless the user asks (`[SuppressMessage]`, `#pragma warning disable`, `GlobalSuppressions.cs`, `.editorconfig` severity overrides). Report the warning and why it may be a false positive. The user decides.
