# Backend General Rules
*   **Coding Style:** Do not write inline comments (//) explaining what code does unless explicitly asked by the user.
*   **Variable Inlining & Declaration:** Do not declare unnecessary local variables. Inline expressions if a variable does not improve semantic clarity. Declare local variables only in these situations:
    *   Cannot resolve the value without an intermediate variable.
    *   Captures the result of an `await` expression.
    *   Stores the result of a LINQ query or chained operation.
    *   Breaks down complex multilayer computations.
    *   Clarifies complex or non-transparent boolean operations.
*   **XML Documentation Standards:** Do not write trivial one-line comments for all code. Never add boilerplate comments to self-explanatory properties, fields, or constants. Document public interfaces, extension methods, and complex domain logic. When you document a method, describe all inputs using `<param name="...">` tags and outputs using `<returns>` tags. Reference code symbols and parameters using `cref` attributes (e.g., `<see cref="..."/>`, `<paramref name="..."/>`).
*   **Comment Only the Non-Obvious:** Write a comment only when the code cannot show the reason: a constraint, a unit, a side effect, an ordering requirement, a deliberate workaround, or complex logic such as a cryptographic algorithm. Never restate the member name or the code. Put the reason in the XML documentation (`<summary>` or `<remarks>`), not in a `//` comment. A member whose name and type explain it needs no comment. Document a public interface on the type, and document its members only when they add information that the name lacks.
*   **Exception Documentation:** Document exceptions that a method throws directly by itself. Do not document exceptions that a method merely proxies or bubbles up from dependencies. List the thrown exception in the method description using `<see cref="..."/>`. Add an `<exception cref="...">` tag explaining the exact condition that triggers the exception.
*   **Output Rules (80% ASD-STE100):** Write documentation and technical text following ~80% Simplified Technical English (ASD-STE100): short sentences (<= 25 words), active voice, one instruction per sentence, and direct wording.
*   **Primary Constructors:** Use C# 12 Primary Constructors **only** for injecting dependencies into classes (the parameters act as your private fields). **Do NOT** use primary constructors for record types (e.g., DTOs, Commands, Events). For records, declare explicit properties with init setters (e.g., public string Name { get; init; }).
*   **Architecture & Screaming Architecture:** Adhere to strict Clean Architecture boundaries (Web -> Infrastructure -> Application -> Domain). Organize top-level folders by **Feature/Business Domain** (e.g., `/Machines/`, `/MaintenanceTickets/`), NOT by technical concern (e.g., do not create root folders like `/Services/`, `/Models/`, `/Handlers/`). Always use plural nouns for feature folders and namespaces (e.g., `/Machines/`, `/Orders/`). Plural namespaces prevent collisions with singular entity classes (CS0118). The folder structure must scream the business intent. Inside each business folder, group files into logical sub-folders (e.g., by use case like `/Machines/CreateMachine/`). Do not place all files flatly under the business folder root. Feature-wide shared definitions (e.g., `MachineErrors`, `MachineValidationConstants`) may remain at the business folder root.
*   **Shared Project:** Microservices must reference their corresponding HealthyFac.Shared.* layer (e.g., Core.Domain references Shared.Domain).
*   **Object Initialization:** For simple data assignment without logic, rely on init properties and object initializers (e.g., new Dto { Prop = value }). However, if object creation involves **any** kind of logic (e.g., validation, generating IDs, derived fields), you must use an explicit constructor.
*   **No Magic Values:** Never hardcode literal numbers, strings, URLs, or configuration keys directly in code. Extract them into named constants inside a dedicated `static class` (e.g., `ValidationConstants`, `PolicyNames`, `CacheKeys`). The only acceptable inline literals are `0`, `1`, `-1`, `true`, `false`, `null`, `string.Empty`, and `Guid.Empty`.
*   **Error Definitions:** Never inline error messages or instantiate ad-hoc exceptions with raw strings directly in logic. Define errors in dedicated `static class` definitions (e.g., `MachineErrors`, `AuthErrors`) scoped to their feature, exposing static error instances or factory methods, and reference them.
*   **File Separation:** Do not co-locate API Request or Response contracts with Endpoints in the same file; keep them in separate files. In the Application layer, however, an `IRequest` and its corresponding `IRequestHandler` may be placed together in the same use-case file. Classes/types may otherwise be inlined ONLY if they are utility/helper types used strictly within that file.
*   **Required Modifier:** Use the `required` modifier instead of dummy default values (e.g., avoid `= string.Empty;` or `= default!;`) for non-nullable properties on DTOs, Requests, Responses, and Entities. This guarantees compile-time initialization safety without silencing nullable analysis with placeholders.
*   **Centralized Package Management (CPM):** Manage all NuGet package versions centrally in `Directory.Packages.props` using `<PackageVersion Include="..." Version="..." />`. Individual `.csproj` files must define `<PackageReference Include="..." />` without an inline `Version` attribute.
*   **Extension Method Conventions:** Use correct conventional `Add...`, `Use...` prefixes for extension methods involving application configuration and setup. Use `Add...` for service registrations and options configuration on `IServiceCollection` / `OptionsBuilder<TOptions>`, `Use...` for request pipeline and middleware configuration on `IApplicationBuilder` / `WebApplication`, and `Map...` for endpoint route registration on `IEndpointRouteBuilder`.
*   **Options Section Names:** Every strongly-typed options class bound through the Options pattern must declare its configuration section name as a `public const string SectionName` on that options class. Never place an options section name in a separate constants class, and never hardcode it at the registration call site. Do not store composite paths (e.g. `"IdEncryption:Keys"`) as extra constants. Compose them from `SectionName` where a full path is required.
*   **Constant Grouping:** Group related constants into nested `static class` blocks inside the owning constants class once that class holds five or more members or covers more than one concern. Name each nested class after the concern it serves, not after the member type (e.g. `ProblemDetailsConstants.NotFound.Title`, `HealthCheckConstants.Routes.Liveness`, `DatabaseConstants.Retry.MaxCount`). Keep a constants class flat only while it stays small and single-purpose. Never introduce a nested class that holds a single member.
